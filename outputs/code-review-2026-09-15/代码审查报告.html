5. 详细发现与修复建议

F01 · P1 · 保存早期失败会破坏原本有效的项目文件

位置： src/main/store/projects.repo.ts:222–240，特别是 225、234–237 行。

根因： 临时文件写入、旧文件轮转、新文件转正和数据库更新共用一个 catch。回滚不知道已经完成哪一步，始终把现有主文件移到 tmp，再恢复 bak，最后删除 tmp。

触发： 主文件为有效 v2，在写 .tmp 时发生磁盘满等错误。此时旧主文件尚未轮转。回滚却把 v2 移走并删除：如果有 bak，只剩旧 v1；如果没有 bak，则唯一有效主文件消失。新建或导入后尚无备份的项目尤其受影响。

证据： 关键源码已复核；隔离文件系统中注入 ENOSPC，观察到有备份时 v2 退回 v1、数据库仍为 v2，无备份时主文件消失。未对用户真实项目制造磁盘故障。

修复： 保存事务引入明确阶段标记；旧文件未成功轮转前，失败只清理本次 tmp；只有旧文件确已转为 bak 时才恢复 bak。回滚失败保留全部可恢复副本，不能继续清理唯一有效副本。后续评估 fsync 与崩溃一致性。

回归验收： 在序列化、tmp 写入、旧文件轮转、tmp 转正、SQLite 更新每一阶段注入异常，分别覆盖有/无 bak。断言最近一次成功保存的内容仍可读取、版本不错误回退。现有 test/agent/graph-write-transaction.test.ts 的数据库失败测试没有覆盖写 tmp 失败。

F02 · P1 · 关闭窗口时可覆盖已经提交的外部更改

位置： src/renderer/src/canvas/CanvasEditor.tsx:536–545；src/main/ipc/project.ipc.ts:124–133；src/main/store/projects.repo.ts:204–208。

根因： 普通保存使用 expectedGraphVersion；关窗调用却显式传 expectedGraphVersion: undefined，变成最后写入者覆盖。

触发： 桌面仍显示版本 N，CLI/MCP 已保存 N+1，桌面尚未完成外部通知重载时关闭窗口。旧画布随后覆盖外部节点、连线或结果，并推进为 N+2。即使桌面没有未保存修改，当前关闭逻辑仍可能写整份图。

证据： 版本检查及关闭调用已复核。隔离对照中，同一旧载荷携带版本号会被拒绝，删除版本号后成功覆盖。未执行真实 Electron 关窗竞态。

修复： 关窗不应降低保存一致性标准。保留版本校验；冲突时阻止关闭并提供合并/恢复副本方案。没有 dirty 状态时不重复保存整份图；对本地未保存更改保留可恢复数据。

回归验收： 外部提交后、通知重载前关闭窗口；外部修改不能消失，本地未保存内容也必须有恢复路径。添加双入口竞态集成测试。

F03 · P1 · 同步保存失败结果丢失，关闭仍继续

位置： src/preload/index.ts:65–67；src/main/ipc/project.ipc.ts:126–132；src/renderer/src/canvas/CanvasEditor.tsx:539–545。

根因： 主进程返回 FLUSH_FAILED，但 preload 将 sendSync 返回值丢弃，接口类型是 void；beforeunload 没有成功检查和阻止关闭逻辑。

触发： 用户仍有防抖队列中的修改，关闭时碰到写锁冲突或磁盘错误。保存失败，页面销毁，修改丢失。该问题独立于 F01，即使回滚完全正确，写锁占用也足以触发。

证据： 隔离 IPC 返回失败信封时，实际 preload 方法仍返回 undefined；关闭路径静态确认不会检查失败。

修复： 将同步 API 改为返回保存结果；更稳妥的是主进程协调关闭确认，保存成功才退出，失败保留窗口和 dirty 状态。项目不存在等空结果也不能当作保存成功。

回归验收： 写锁、I/O 错误、项目不存在分别触发关闭；确认错误可见、窗口保留、内容不丢失，成功重试后才允许退出。避免只测试 repo 而遗漏 preload 到界面的结果传播。

F04 · P1 · headless VM 不是可靠的不可信代码安全边界

位置： src/main/headless/run-code.ts:119–128，尤其宿主 args 注入点 122 行。入口包括 src/cli/index.ts:46、src/mcp/server.ts:666 附近的 headless 执行装配。

前提： 必须显式开启 CANVAS_AGENT_EXECUTE=enabled，再执行代码节点；不是默认只读模式下任意文件一打开就可触发。

根因： 宿主创建的 args 对象直接放入 VM。对象的跨上下文构造器链可到达宿主动态函数能力；仅把上下文内 process、require、Function 赋值为禁用值，不能构成完整权限隔离。

证据与边界： 审查隔离验证仅设置一个无害宿主字符串标记，实际代码节点能够读出该标记。没有读取系统秘密、访问网络或修改文件。该结果确认越过上下文边界；不将其描述为已完成真实系统破坏验证。

影响： 对用户主动编写且可信的脚本，这是权限模型问题；对外部工作流或自动生成且尚未可信审核的脚本，则违反“离线数据转换、禁用网络/模块访问”的承诺，需要优先修复。

修复： 不依赖 node:vm 加关键词黑名单执行不可信代码。采用可限制文件与网络能力的隔离运行时，或具有操作系统权限约束的独立执行进程；输入输出走序列化边界，设置资源限额与可终止机制。普通子进程如果仍拥有同样权限，也不等于安全隔离。

回归验收： 宿主假标记不可读；输入对象及嵌套对象不能提供跨边界能力；网络/文件/模块能力受实际权限约束；超时后执行真正终止。test/headless-run-code.test.ts 已有直接 fetch/require/new Function 测试，但没有覆盖跨上下文对象路径。

F05 · P1 · headless 错误解释桌面节点配置

位置： src/main/headless/run-executor.ts:186–208，198 行；对照 src/shared/graph-snapshot-sync.ts:148 与 src/shared/engine/executors/processor.ts:52。

根因： 桌面协议将真实配置字符串放在 node.params.config；headless 却使用 JSON.stringify(node.params) 作为 props.config，多包一层。

触发样例： 桌面 processor 的 params.config 为 {"fallback":"固定值","valueType":"string"}。headless 传入的是含 config 字符串属性的外层对象，executor 找不到顶层 fallback。

证据： 相同业务配置直接交给 shared executor 返回 done，经真实 headless 适配返回 skipped，原因为“没有输入变量或固定值”；整体 Run 仍可能显示 succeeded。

修复： 建立唯一 Node-to-Shape 适配器，明确从 params.config 还原配置。确需兼容其他输入格式时，在边界显式规范化并标注版本，不能各入口自行猜测。

回归验收： 同一个桌面保存 fixture 分别由 renderer/headless 执行，比较状态和完整结果。覆盖 processor fallback、路径选择、结构化 Schema，以及模型选项的读取，不能只测试 params 为空的文本节点。

F06 · P1 · headless 输出投影与节点协议分离

位置： src/main/headless/run-executor.ts:96–111,237–282；src/shared/engine/values.ts:142 起；对照 src/renderer/src/nodes/specs/outputProjections.ts:77–108,174–208。

根因： headless 将 nodeResult 仅写到临时 shape，然后使用通用 NodeValue 解析及按端口类型回退。它没有复用节点注册的 projectOutputs，也没有完整保存节点结果、运行来源及多端口输出语义。

场景一： text A 输入 structured 模板 {"message":"{{text}}"}。executor 产生 structured-result，其 data 正确为 A；通用解析无法识别此封装，转而从正文投影，输出仍带模板占位符。

场景二： 图片裁剪网关替身返回新媒体。真实 executor 已写入 media-source，但通用解析无法识别，输出为空，Artifact 数为 0，保存图没有新媒体结果引用；Run 却可以显示成功。

证据： 已复核实际适配与解析实现，上述两条路径完成隔离验证。确认的是结果引用、输出和运行关联丢失，不是证明媒体服务一定没有生成文件。

修复： 将纯数据输出投影抽到 shared，与节点协议共同注册，renderer/headless 都使用；保存用户正文、运行记录和结果时保持边界；成功节点必须完成输出契约校验，多端口/集合产物均可追溯。

回归验收： structured 插值后接下游、mock crop 后接下游与 Artifact、保存重开、多输出节点均验证具体值。现有 renderer 投影测试通过不能证明 headless 采用相同语义。

F07 · P1 · JSON 输出保存后清空桌面正文

位置： src/main/headless/run-executor.ts:274–278；src/shared/graph-snapshot-sync.ts:146–164；src/application/stores/desktop-store.ts:86 附近。

根因： headless 将 JSON 输出保存为 content.kind=json；快照同步器只把 text content 转成 props.text，其他情况统一写空字符串。

触发： 桌面 JSON 节点正文合法，经 headless 执行和生产保存适配后，其 graph content 仍有 JSON 数据，但 tldraw 节点 props.text 为空。重开桌面后正文显示和复跑语义被破坏。

证据： 真实 headless 与快照同步函数的隔离组合验证观察到该不一致；生产 DesktopProjectStore 保存入口已静态核对。未声称 SQLite 内 JSON 数据整体被删除。

修复： 明确 CanvasNode.content 与桌面正文的双向转换；JSON 内容应采用一致序列化。不要为补正文而把 structured 的用户模板直接换成运行产物，应区分编辑内容和结果。

回归验收： JSON 新建/更新/运行/保存/重开全流程，含已有快照、无快照、不同缩进；断言 graph 与 snapshot 表达一致且再次运行得到相同数据。

F08 · P1 · 循环取消后的部分结果会被续跑复用

位置： src/renderer/src/engine/executor.ts:701–735；src/shared/engine/executors/iterate.ts:228–263,338–345。

根因： 子流程取消后 break 并返回已经完成节点的部分输出；runItem 在 await 返回后不重新检查取消，只要输出非空就将列表项记为 done。resume 随后复用 done/reused。

触发： 带稳定 id 的列表进入 iterate，循环体 A 已成功，B 执行期间停止。循环本身显示 cancelled，但该项被记 done；同列表续跑后该项变 reused，B 没有完成却不再运行。

证据： 使用真实 renderer 编排、契约投影与 shared executor，配合内存 Editor/store 和受控代码执行替身：正常对照包含 A/B，停止时只含 A，续跑 B 调用次数不增加。

修复： 子流程以显式 cancelled 结果或异常传播；runItem 在异步返回后再次检查 token。只有完整子流程完成才能进入可复用状态，部分产物可以留作诊断但不能代表完成。

回归验收： 多节点循环体在每个等待点取消→恢复；已完整完成项复用，未完成项重新执行。稳定 id/指纹检查仍需保留，但不能替代完成状态正确性。

F09 · P2 · 持久化多上游输入静默截断

位置： src/main/headless/run-executor.ts:211–234，对比 221 行追加和 232 行覆盖。

根因： 本轮 packet 分支追加到端口数组；持久化回退分支却直接 map.set 为仅包含当前值的新数组。

触发： A、B 两个文本源连接到支持 many 的 T.in-text，仅运行正文为空的 T。A/B 都属于范围外持久化上游，T 最终只收到 B，不是协议约定的两段合并文本。

证据： 该双上游路径隔离复现。混合本轮与持久化来源也存在覆盖/顺序问题，应一并修复和验证。

修复： 逐条按稳定边顺序决定取本轮或持久化输出，再追加；不能简单在第二轮末尾追加而改变混合来源顺序。

回归验收： 两个范围外上游、两个本轮上游、混合来源、重复和缺失端口分别断言值、个数与顺序。扩展 test/agent/headless-runner.test.ts 的单上游场景。

F10 · P2 · 拆图单图输出不是选中项

位置： src/shared/engine/executors/imageSplit.ts:34；src/renderer/src/nodes/specs/outputProjections.ts:54,86–108；协议见 NODE_CONTRACT_SPEC.md:179 附近。

根因： 拆图记录默认 selectedMediaId 为第一张，单图投影却调用固定取 results.at(-1) 的“最新结果”函数。

触发与证据： 2×2 拆分的网关替身返回四个媒体引用。实际记录选中 grid-1，out-image 却指向 grid-4；out-images 列表包含全部四项，所以仅测列表长度不会发现。

修复： 为拆图定义按 selectedMediaId 选择的投影；明确无效 ID 的回退行为。不要无差别改其他操作节点的“最新结果”语义。

回归验收： 默认选择、切换选择、无效 ID、空集合断言完整媒体引用。test/projectNodeOutputs.test.ts 已有多结果 fixture，但需补 mediaId 精确断言，不能只断言 kind。

F11 · P2 · 解密暂不可用时，普通编辑清除原密文

位置： src/main/gateway/providers.repo.ts:94–112；src/main/gateway/keycrypto.ts 的解密失败空串返回路径。

根因： 留空密钥本应保留原值，但 saveProvider 先通过 getProvider 解密旧密钥，然后重新加密保存。解密失败返回空串后，保存分支把 api_key_ref 变成 null。

触发： 已有 enc: 密文，系统密钥服务暂不可用或解密异常。用户只改供应商名称/模型，按界面约定密钥留空，原密文被清除；系统恢复后也无法再解密已丢失的数据。

证据： 假密文、模拟不可用 safeStorage 与实际保存实现的隔离验证中，仅改名称即可使密文字段变 null。没有读取用户真实密钥。

修复： 未提交新密钥时直接保留数据库中的原始密文字段，不解密重加密。分别表达未配置、不可解密、主动清除三种状态；同步清理文件顶部关于明文存储的过时注释。

回归验收： 正常、解密不可用、解密抛错三种条件下，留空编辑均应逐字节保留密文；明确新密钥才替换，明确清除动作才删除。

阶段 A：先保住数据与执行边界

8. 已有优点、限制与最终判断

已有基础值得保留

  • 工程已经分出 shared engine、应用服务、renderer/headless 适配层，适合进一步统一语义，而不是整体推倒重写。
  • 普通保存已有版本检查、排他写锁、备份、数据库与文件回滚思路，需补失败阶段正确性，而非重新引入另一套独立保存机制。
  • 供应商列表使用公开摘要，不回传解密 Key；问题 F11 是编辑时丢密文，不是列表已经泄露密钥。
  • 导入已有版本/条目数/声明解压体积检查、媒体文件名校验、引用递归重映射、暂存目录与事务；没有把已处理的路径问题重复列成漏洞。
  • 已有 950 项自动化用例及契约快照/版本门禁。下一步重点应是边界组合和真实环境验证，不是单纯增加测试数量。

未完成的验证

  • 18 项受 ABI 阻断的测试未通过；没有证明修复 ABI 后必然全部通过。
  • 未完成真实 Electron 的关窗、外部并发编辑、跨端保存重开端到端验证。
  • 未执行真实模型服务、收费调用、恶意媒体完整利用链、真实数据库故障、安装包升级/签名或长时间性能压力测试。
  • 未运行依赖漏洞数据库扫描，因此不提供“依赖无已知漏洞”的结论。
  • 未验证远端 CI 或运行中的部署；本轮只更新 GitHub 源码分支。
  • 本机 origin/main 跟踪缓存读取异常仍保留；服务器直接查询的提交与本地一致。

最终判断： 项目具备清晰的工程基础，但保存与无界面执行边界仍有高优先级风险。本轮交付是“已同步源码 + 有证据的审查与修复计划”，不是“问题已修复”。建议先完成阶段 A/B，再在匹配 ABI 的环境中复跑全部测试与桌面回归，之后才决定是否发布。
