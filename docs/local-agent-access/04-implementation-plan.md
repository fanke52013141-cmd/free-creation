# 本地外部 Agent 接入实施计划与验收

2026-10-24；评审草案。主入口：[方案目录](README.md)；权威边界：[主规范](../../AGENT_ACCESS_SPEC.md)。

用户已授权先落地A0+A1最小纵向包；实际实现、命令和验证见[交付台账](05-a0-a1-minimal-delivery.md)。本篇是完整分期目标，未列入实际支持的能力仍待实施，不作为恢复旧接入代码的依据。

## 1. 实施顺序与完成定义

顺序为 A0 → A1 → A2 → A3 → A4。A2/A3 可以在公共底座稳定后按互不重叠的节点模块并行适配，但同一文件/强耦合模块只能有一个实现负责人。每包须先列用户路径、修改范围、现有行为、日志影响和验收，再实施。

支持状态使用：planned（未开放）、implemented（指定入口已实现但未完成稳定验收）、verified（规定验收通过）、excluded（该动作明确不开放）。同时标出已验证的入口和客户端版本，不能将CLI通过等同MCP/HTTP通过。

每包交付包含：可运行能力、公共契约与兼容结论、覆盖清单、日志证据、自动测试结果、真实桌面/客户端路径、未支持与未验证边界。不得以测试数量或工具清单长度替代产品验收。

## 2. A0：定规范、建立公共契约与同步门禁

**用户路径**：开发者新增一个测试用能力或修改一个契约，缺少接入声明时门禁准确失败；补齐声明后生成一致的目录。尚不向外开放真实项目写入。

| 工作包              | 具体工作                                                                                              | 验收                                                                                              |
| ------------------- | ----------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------- |
| A0.1 规范生效       | 确认主规范、矩阵、阶段；将接入影响条款加入AGENTS及模板，保留历史下线说明                              | 规范入口可查；内部Flow与外部支持状态分开                                                          |
| A0.2 契约底座       | OperationSpec、NodeAccessSpec、envelope、错误、版本、限制、Registry；抽取可共享的节点描述             | 31类型均有声明；严格Schema；不存在万能invoke工具                                                  |
| A0.3 账本与身份适配 | 普通外部调用主体；实例/dataStore绑定；幂等键有效期与回执；graph/semantic revision映射；锁与宿主拥有者 | 外部主体到正式租约/占用的映射已实现并通过隔离测试，不伪造内部Agent任务；重复/冲突/过期/未知有测试 |
| A0.4 接入门禁       | 实现登记/暴露/生成/兼容/影响检查，接入现有verify和CI                                                  | 故意缺声明、增幽灵工具、过期生成物和不兼容变更均能阻断                                            |
| A0.5 日志设计       | 注册接入层允许字段与事件；明确入口和业务终态拥有者                                                    | 假密钥/正文不进入实际日志输出；logger失败不改变业务                                               |

建议新增模块（路径待实施时确认）：`src/shared/agent-access/` 放声明、Schema、映射与生成器输入；`src/main/agent-access/` 放访问边界、Dispatcher和业务协调；`src/local-agent/` 放CLI/MCP薄代理；相关测试单列 `test/local-agent-access/`。不照搬已经撤下的目录作为旧系统恢复。

需要先锁定的实现细节：

- 首版目标客户端及MCP协议兼容组合；应用与CLI的打包/安装方式。
- Windows本地连接与凭据保存方式；实例选择、数据目录和单实例/项目拥有者策略。
- idempotencyKey的有效期/过期拒绝方案、回执保留与崩溃窗口；删除回执不能随项目一起消失。
- 统一命令主体如何进入现有Flow占用、审核、租约及semantic revision检查。
- DTO与configSchema来源；不得以宽泛unknown对象代替需要类型化的字段。

这些是实现者需要落实的技术决策，不要求用户逐个批准库或文件名；有影响产品范围的新选择才重新说明。

## 3. A1：项目操作与首条 MCP / CLI 闭环

**用户路径**：Agent连接本机应用 → 识别版本/实例 → 列出项目 → 新建项目 → 修改名称/声明元数据 → 保存并查询 → 复制 → 导出 → 在桌面看见同一项目和导出结果 → 显式删除隔离测试副本。

操作顺序：能力发现 → `project.list/create/get/open/update/rename/save/clone/export` → `project.get`确认 → 删除预检/impact确认 → `project.delete`。其中update修改元数据、rename修改名称、save只负责提交；A2补齐项目画布内容的修改。

A1完成用户明确要求的项目操作接口；图内容修改在A2，通过graph/node操作实现。`project.update`不接受任意快照或项目包。

| 工作包              | 具体工作                                                                       | 验收                                                                                                       |
| ------------------- | ------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------- |
| A1.1 连接和启动     | CLI/MCP代理、本机连接、状态/版本发现、显式启动/等待就绪                        | 未运行/版本不兼容/多实例有稳定结果；协议stdout纯净                                                         |
| A1.2 公共项目服务   | list/get/create/open/update/rename/clone/save/delete复用仓库；UI与外部共用规则 | CRUD幂等；修订冲突；在线画布未保存改动不丢；删除拒绝活跃/unknown占用                                       |
| A1.3 导出服务       | 拆开UI对话框与导出业务；显式目标、源版本固定、完整性与凭据剥离                 | 可不用对话框导出；UI未保存修改时协调保存或冲突/等待，内容保留；缺失媒体默认拒绝；重名/磁盘故障不损坏原文件 |
| A1.4 查询和诊断     | 能力/模型去敏目录、run.get基础、资源库只读、诊断摘要/包；资源包导出可选扩展    | 返回真实状态；不泄露密钥；大结果分页/引用有界；资源包与项目包分开验收                                      |
| A1.5 安装包与客户端 | 打包CLI/MCP入口、生成实际可用配置、至少一个真实MCP客户端验收                   | 安装包外可调用；与应用版本匹配；开发源码环境通过不足以交付                                                 |

建议命令外观如下，仅为未来使用示意，本轮不可执行：

```text
canvas-studio status --json
canvas-studio project list --json
canvas-studio project create --input-file create-project.json --json
canvas-studio project export --input-file export-project.json --json
canvas-studio run get --task-id <taskId> --json
canvas-studio mcp serve --stdio
```

写入参数通过UTF-8文件/stdin输入，避免正文/凭据进入命令行历史、转义错误或shell替换。CLI默认JSON输出，不混入业务调试日志；`--wait`等待任务但超时不重放。退出码建议固定映射完成、输入/版本错误、占用、等待超时、业务失败和unknown；`accepted`返回任务ID，不误称执行完成。

每项项目变更必须返回提交版本；删除显式确认绑定ID、修订与影响清单，不以同名项目作为目标。第一阶段不建设回收站，不提供无约束批量删除。

## 4. A2：全部节点的结构化访问与确定性路径

**用户路径**：Agent枚举31类型与字段 → 创建文本/JSON/处理节点 → 更新正文和配置 → 按portId连线 → 预检 → 执行确定性节点 → 读取正式端口输出 → 保存、关闭、重开 → 桌面可继续编辑和运行。

| 工作包            | 具体工作                                                                   | 验收                                                             |
| ----------------- | -------------------------------------------------------------------------- | ---------------------------------------------------------------- |
| A2.1 类型和配置   | 31个NodeAccessSpec与配置Schema、默认值、字段白名单、版本兼容               | 每类均能读契约、建节点、改合法字段；不能写运行meta或伪造类型版本 |
| A2.2 图命令       | 节点创建/读写/复制/删除/摆放、数据边和控制/状态关系的分别校验、graph.patch | 无效端口/基数/循环/关系拒绝；原子patch无半提交；many顺序稳定     |
| A2.3 公共执行准入 | 普通外部节点命令复用租约、占用、修订、审核和桌面桥，不冒充Agent任务        | 手动与外部操作互斥正确；相同key跨transport不重复执行             |
| A2.4 确定性节点   | 文本/JSON/结构/分镜的编辑与投影、processor执行；裁剪/拆分等适用本地处理    | 输出类型/配置/独立资产/保存结果与桌面一致；依赖缺失不假成功      |
| A2.5 正式结果     | output.list/get/select/export，摘要与正文/媒体引用分开                     | 可连接和可复用；选择已有结果不隐式生成新内容                     |

媒体节点的结构化编辑可以引用已存在的受控素材，新增本地素材的公共登记在A3；不要求A2为了测试去读取用户私有目录。已有编辑范围不足的复杂节点，可分字段逐包补齐；未支持字段给出原因，不能以接受任意config对象替代校验。

A2必须建立旧接口失败的五类回归：配置错层、专用投影丢失、JSON正文清空、循环取消被当成功、多路输入覆盖。暂未开放循环执行时，相关拒绝行为与后续测试夹具也应明确，不能先走错误的替代路径。

## 5. A3：模型、媒体长任务与内部 Agent Flow

**用户路径**：Agent选择已验证模型 → 固定输入和版本 → 提交生成 → 获得taskId → 观察真实状态 → 成果入库并物化为独立节点 → 读取/继续连接 → 导出项目。中途断线可查询原任务，不产生第二次提交。

| 工作包              | 具体工作                                                                                                                 | 验收                                                               |
| ------------------- | ------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------ |
| A3.1 六类现有target | 先复用processor/image-gen/image-edit/video/speech/tts的现有准入与限制                                                    | 保留单张/单任务、固定输入、模型上限、版本及unknown约束；无隐式放宽 |
| A3.2 媒体与模型扩展 | voice-design、ai-process；抽帧/截取/声音调整；深度/白模本地推理；受控media接入                                           | 每类独立声明依赖、预算、取消、产物和恢复边界                       |
| A3.3 任务和事件     | node.execute提交；run.get/list/wait/cancel/reconcile及适用run.resume按taskId控制；Flow操作控制声明范围；游标、保留与节流 | 超时、重开、租约丢失与远端unknown不重放；保存失败不建议重生成      |
| A3.4 Agent与审核    | 外部启动/观察/停止内部Flow、专用Agent任务、固定资产审核/有界返工                                                         | 人工与AI动作分开；质量拒绝/技术失败/人工等待区分；不能编辑运行事实 |
| A3.5 跨入口持久化   | 项目、固定资产、输出、日志关联与导出保持同源                                                                             | 手动与MCP/CLI规范化快照一致，重开可见；运行权威不随导出复制        |

深度视频/白模视频是本地Python/CUDA与ffmpeg路径，需要查询实际环境状态、资源限制和取消清理，不能按供应商任务设计。项目资源库、素材注册与项目包导入是不同操作，禁止通过媒体接口注入项目数据库/归档。

真实计费供应商验证列为独立验收项，使用隔离样例和明确预算；单测/mock只能证明本地协议，不能证明供应商真实取消或幂等。未实际测试的供应商/模型/模式继续标未验证，不扩大为“所有模型可用”。

## 6. A4：复杂能力专项与可选 HTTP

| 能力       | 建议边界                                                            | 专项验收                                                                  |
| ---------- | ------------------------------------------------------------------- | ------------------------------------------------------------------------- |
| AI对话     | 增加会话、消息、附件、最后回复及取消协议；不直接覆盖聊天私有存储    | 多轮一致、附件归属、并发消息、保存重开；图片结果遵循已有输出契约          |
| 代码       | 先审核现有Worker/runCode隔离能力，再决定是否开放外部执行            | 超时/内存/返回体/日志有界；不得默认获得宿主文件、进程、网络或Electron API |
| 循环       | 声明子图、项身份、预算、暂停/停止/恢复与实际并发能力                | 取消项不被复用为成功；重开不重复提交已受理任务；many输入不丢              |
| 网址       | URL、重定向、私网/本机资源策略、体积和超时限制                      | 防止将公网抓取能力变任意本机/内网读取；明确动态网页支持边界               |
| 3D预演台   | 可读写已声明配置、准备镜头/输入、查看最近正式发布结果；人工发布保留 | 不模拟点击绕过manual-publish；若未来自动发布必须单独改业务契约并验收      |
| 状态机     | 读取/编辑定义和查询可信运行状态；独立executor当前不开放             | 不把模型文字当事件事实；独立自动执行需另包实现，接入计划不替它宣称完成    |
| 资源包导入 | 非必要延期项，与项目导入明确分开                                    | 只有确认纳入时才实现重映射、临时落盘和事务；不阻塞本轮必要范围            |
| HTTP API   | 仅真实调用方需要时加REST薄适配；MCP Streamable HTTP另列协议与兼容表 | loopback、凭据、Origin/Host、限额、断线与跨入口幂等；不复制业务实现       |

上述能力可以只开放部分动作；如导演台“可准备、需人工发布”，状态机“可编辑、独立执行未支持”。这是显式动作级边界，不是把整个节点从覆盖清单中消失。A4可选HTTP、资源包导入和新增状态机业务不作为核心项目/节点接入交付的隐含前置条件。

## 7. 测试层次与具体场景

| 层次           | 验证内容                                                         | 证据                                             |
| -------------- | ---------------------------------------------------------------- | ------------------------------------------------ |
| 契约/静态      | Registry、Active、Schema、生成目录、版本与暴露一致               | 快速门禁报告与兼容diff                           |
| 公共服务       | CRUD、原子图patch、冲突、幂等、导出与故障                        | 隔离仓库/文件夹、真实提交与回读                  |
| 跨入口一致性   | 同一fixture分别通过UI公共业务入口、CLI、MCP执行                  | 规范化语义图、输出包、独立资产及保存版本对比     |
| 真桌面         | 外部修改实时可见，保存重开，手动与外部任务竞争                   | 有标识窗口、截图/结果文件、隔离数据真值          |
| 恢复/故障注入  | 受理前后断线、媒体完成后保存失败、renderer丢失、磁盘满、日志拒写 | 原任务核对、无重复副作用、明确unknown/未保存状态 |
| 打包/客户端    | 已打包应用、CLI/MCP入口、至少一个真实客户端                      | 精确版本、安装/启动配置和端到端回执              |
| 供应商真实验证 | 最小真实生成、取消/核对、下载入库                                | 模型/模式/预算与费用、通过/未验证逐项记录        |

最低必测情形：

1. CLI发出创建/生成，响应丢失后MCP以同幂等键查询/重试，只能返回原身份与结果。
2. UI有未保存修改，外部按旧版本写入，冲突明确且用户内容保留。
3. 应用/renderer退出时有pending命令，重开为unknown并阻止重复执行；核对不调用新模型。
4. 媒体已生成但保存失败，结果仍可核对，恢复只补提交，不再次生成。
5. many输入顺序、字幕/音色JSON、结果选择、固定媒体与独立资产保存重开一致。
6. 删除拒绝活跃/unknown占用；确认token过期或修订变化拒绝；重试删除原副本不影响同名新项目。
7. 项目导出不含密钥；路径穿越/联接点逃逸/重名/缺失媒体/临时提交失败均有确定结果。
8. 日志/诊断包中无假密钥、中文提示词、回复、代码正文、签名URL；日志失败与业务账本失败语义不同。
9. 枚举31节点均有状态和理由；旧类型不可新建；state-machine独立执行、导演台人工发布不可被万能工具绕过。
10. 项目包导入不在任何工具/CLI/HTTP目录中，直接构造operation也被拒绝。

现有基线可复用 `npm run test:contract`、`npm run verify:logging`、相关Agent Flow专项及完整 `npm run verify`。新增门禁实现后纳入原 `verify:checks` 和CI。测试统一使用 `CANVAS_DATA_DIR` 等隔离目录；可见窗口标识并退出清理，不操作真实用户项目。

## 8. 首包建议与排期方法

建议下一次实施从 A0 与 A1 的最小纵向包开始：公共项目服务 + 本机连接 + project.list/create/rename/get/export + CLI/MCP + 实际桌面回读。随后同属A1补齐update/open/save/clone/delete、资源库/诊断基础。这样首先验证接入架构是否真的共用桌面事实，再扩大31节点范围。

不在缺少原型验证时承诺固定工期。A0结束后按“公共服务抽取、接入宿主、节点配置Schema缺口、真实客户端与打包验证”拆估；A1闭环后再锁A2/A3节点批次。每包结束更新开发台账和覆盖数，禁止把阶段编号当作完成证据。

## 9. 本轮交付边界

已交付：规范草案、功能和31节点清单、同步门禁设计、分阶段任务、变更模板。未实现：外部传输、公共操作Registry、NodeAccessSpec、自动同步门禁、跨入口运行适配和新增测试。

日志覆盖：本轮不涉及运行变更；后续每包按现有日志规范补齐实际路径并更新覆盖清单。验证证据仅限源码调查和文档一致性检查；没有运行模型或项目修改，也没有重跑全量verify。
