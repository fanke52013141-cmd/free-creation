## 结论

当前共有 23 个可创建节点，均已具备 Active 类型、稳定的 `contractVersion`、明确输入输出、已注册 executor 和 `projectOutputs`。静态注册校验与连线矩阵不依赖上游节点标题或类型猜测，数据流统一以 `source.outputs[sourcePortId] -> target.inputs[targetPortId]` 表示。

## 一、输入输出与组合关系

完整端口清单见 [NODE_COMPLIANCE_MATRIX.md](./NODE_COMPLIANCE_MATRIX.md)。以下按真正的数据依赖给出可组合链路；箭头仅在端口类型和 JSON Schema 兼容时成立。

| 领域           | 标准链路                                                                                                                                                      | 约束                                                                                       |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| 文本与提示词   | `text.out-text` → `image-gen.in-text` / `video.in-text` / `speech.in-text` / `chat.in-text` / `ai-process.in-text`                                            | 文本可多输入，消费者自行合并已声明的文本上下文。                                           |
| 图像生成与编辑 | `image.out-image` / `image-gen.out-image` → `image-crop.in-image` / `image-split.in-image` / `image-edit.in-image` / `video.in-image`                         | 变换节点只接收真实 image；裁剪、拆分、编辑均产生新的 image 资产。                          |
| 图片集合       | `image-split.out-images` → `iterate.in-list`                                                                                                                  | JSON Schema 必须匹配 `list.items@1`；逐项出口仅限循环体。                                  |
| 视频链路       | `video.out-video` → `video-frame.in-video` / `video-clip.in-video` / `video-audio.in-video`                                                                   | 三个下游均要求单个真实 video；不允许把图片/音频误连为视频。                                |
| 音频链路       | `video-audio.out-audio` / `audio.out-audio` → `vocal-separate.in-audio` / `tts.in-audio`                                                                      | 人声分离输出人声及可选伴奏；TTS 的音频入口是明确的声音参考。                               |
| 结构创作       | `json.out-json` / `structured.out-json` → `storyboard.in-json` → `director.in-storyboard`                                                                     | JSON 必须同时通过端口类型和 Schema 校验；通用 `json.any@1` 不能冒充 `storyboard.shots@1`。 |
| 导演台发布     | `director.out-frame` → 图像/视频输入；`director.out-preview-video` → `video.in-reference-video`；`director.out-camera` / `out-project` → 对应预演 JSON 消费者 | 仅用户手动发布后的帧/视频才进入下游；不能因打开导演台隐式生成输出。                        |
| 通用逻辑       | `processor` 显式透传 `any`；`code`、`structured` 用 `resolvePorts` 生成实例端口                                                                               | 动态端口仍受统一 schema、命名、基数与投影校验。                                            |

## 三、用户关注能力核验

### 图片生成

- 已有：模型选择、尺寸选择、种子、文本提示词、提示词包、单图及多图参考输入；生图输出是可连接的 `out-image`。
- 已优化：`aspectRatio` 已作为稳定配置，界面按能力表提供比例优先选择；当前安全尺寸映射为默认、`1:1`、`3:2`、`2:3`，模型切换与旧 size-only 配置会自动归一。
- 限制：尚未确认图片服务的统一独立比例请求参数，因此不会把 `16:9` / `9:16` 伪装成通用能力；确认供应商后只允许在共享能力表中增加精确模型条目。
- 结论：节点协议和可见配置均合规，详情见 [P0_P3_NODE_CAPABILITY_OPTIMIZATION_2026_08_31.md](./P0_P3_NODE_CAPABILITY_OPTIMIZATION_2026_08_31.md)。

### 视频生成（Seedance / MiniMax H3）

- 已有模型选择。`Seedance` 和精确模型 ID 为 `minimax-h3` 的 `MiniMax H3` 均有显式能力表，UI 与主进程提交前均做约束检查。
- MiniMax H3：`21:9`、`16:9`、`4:3`、`1:1`、`3:4`、`9:16`；4–15 秒；`768P`/`2K`；最多 9 图、3 视频、3 音频参考；支持首尾帧硬约束，不支持“生成同步音频”开关。
- Seedance：自适应及上述六种画幅；4–15 秒；`480p`/`720p`/`1080p`；最多 9 图、3 视频、3 音频参考；参考素材模式，不宣称首尾帧硬约束；支持“生成同步音频”开关。
- 结论：用户要求的 `16:9`、`9:16`、秒数设置及 Seedance/MiniMax H3 模型选择，当前已实现且契约化。真实供应商响应、限额与实际成片质量仍属于下一阶段桌面端验证，不应仅凭静态代码宣称完成验收。

## 五、导演台安排

导演台不作为当前发布的前置开发项，进入**冻结、验收、再决策**状态：

1. 冻结现有 `director` v2 的输入/输出：分镜、参考图、机位输入；帧、预演视频、机位和工程摘要输出。
2. 仅接受协议错误、数据丢失、发布失败或影响主流程的缺陷修复；不在验证前加入图片直接建模、云端 3D 生成或新引擎。
3. 后续验收必须覆盖：项目重开、手动发布 PNG/WebM、`out-preview-video -> video.in-reference-video`、未发布不产生输出、导入导出后导演台引用重映射。
4. 图片直接建模若恢复评估，必须先提供可替换 Provider、离线/失败 fallback、成本与隐私说明，并保持现有端口和手动发布语义不变。
