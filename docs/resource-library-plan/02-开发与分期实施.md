# 开发与分期实施方案

## 1. 实施原则

本轮独立交付项目效率、资源积累与视频处理能力。沿用本地单用户 Electron、SQLite、现有媒体仓库和强类型节点协议。

新增的库数据属于本机数据工作区，不存到安装目录、不要求云端账号。本文是目标方案；分期实现与当前边界见[当前实现说明](04-当前实现与边界.md)。

## 3. 数据模型

### 3.1 项目节点配置

```ts
interface WorkspaceProfile {
  schemaVersion: 1
  visibleNodeTypeIds: string[]
  presetRef?: { id: string; version: number }
}
// ProjectFile 增加可选 workspaceProfile；旧文件缺省保持兼容。
```

可见集合引用稳定 nodeTypeId，不依赖中文名称。保存前校验，遇到未来未知类型保留原始配置引用并显示缺失提示，不能一次打开就抹掉。

由一个 selector 负责所有创建入口；分类显示名与顺序仍由现有偏好负责。库资源插入所需类型隐藏时，先显示预览和选择；最终是否展示由项目配置决定。

### 3.2 资源核心对象

```ts
interface Resource {
  id: string
  kind: 'single' | 'composite'
  formPreset: 'image' | 'prompt' | 'character' | 'scene' | 'style' | 'custom'
  latestRevisionId: string
  archivedAt?: number
}

interface ResourceRevision {
  id: string
  resourceId: string
  revisionNumber: number
  baseRevisionId?: string
  title: string
  description: string
  componentIds: string[]
  changeNote?: string
  createdAt: number
}

interface ResourceComponent {
  id: string
  revisionId: string
  role: string // reference-image / description / prompt / voice-sample / example 等
  valueType: 'text' | 'markdown' | 'image' | 'audio' | 'video' | 'file' | 'json'
  blobRef?: string
  text?: string
  schemaRef?: string
  referencedRevision?: { resourceId: string; revisionId: string; componentId: string }
  order: number
}

interface ResourceUsage {
  projectId: string
  resourceId: string
  revisionId: string
  componentIds: string[]
  materializedNodeIds: string[]
  projectMediaIds: string[]
  localOverride: boolean
}
```

类型草案在实现时应改为 discriminated union，约束 text/blobRef/reference 三种内容来源互斥，防止空组件。role 使用预设注册表并允许受控扩展，valueType 仍是强类型。

预设通过表单 Schema 定义槽位和说明。第一版界面先开放图片与提示词，但存储模型提前允许音频等类型；第二版复用同一结构开放完整组合。

### 3.3 建议表

| 表 | 内容与约束 |
|---|---|
| `library_resources` | 稳定身份、类型、最新修订、归档标记 |
| `library_revisions` | 版本标题/描述/封面/变更说明，版本号唯一，发布不可变 |
| `library_components` | 类型化内容、用途、顺序与可选固定版本引用 |
| `library_blobs` | 内容哈希、相对路径、mime、大小；不可变文件 |
| `library_tags` / `library_resource_tags` | 标签及多对多关系 |
| `library_collections` / `library_collection_items` | 收藏集及多对多关系 |
| `library_boards` / `library_board_items` | 展板布局、说明、固定版本引用 |
| `library_recipes` | prompt 组件、变量、参考组件、模型/参数和来源 |
| `library_recipe_examples` | 某次配方运行与样例文件的对应关系 |
| `library_usages` | 项目中的引用、来源与局部改动状态 |
| `library_operations` | 收藏/导入/发布的暂存、提交、失败恢复记录 |

组合的子引用固定 revisionId；拒绝循环依赖，限制递归深度，并在发布时校验完整依赖闭包。

标签、收藏关系、使用次数可独立更新；引用会影响生产的正文、图、声音和配方必须形成内容版本。

## 4. 存储与资源生命周期

### 4.1 推荐策略

全局库把文件复制到独立 `library/blobs/`，记录 hash；使用资源时把选中文件物化到项目 `media/`，生成新的 MediaAsset 并保留来源。

该方案会占用额外磁盘，但无需一开始就重构所有项目素材删除语义。后续可在不变更资源协议的前提下优化共享 blob；第一版不使用符号链接指向原项目。

### 4.2 收藏过程

固定所选节点的已提交内容 → 创建操作 ID → 复制临时文件并校验 → 写不可变 blob → DB 事务创建资源修订/组件/来源 → 完成后可见。

崩溃后根据 operation 状态恢复；允许清理无主暂存文件，不能清理仍被项目/资源版本引用的正式数据。内容 hash 去重只解决文件重复，不自动合并两份用户认为不同的资源。

### 4.3 使用过程

选择 revision 与组件 → 校验目标端口 → 导入项目文件 → 创建现有素材节点/文本节点和必要连线 → 持久化图与 usage → 作为一个可撤销操作完成。

跨 DB/图文件的操作先记日志，失败补偿。撤销图操作不立即物理删除复用文件；垃圾回收另行处理。

删除源项目不删除库副本。归档资源不破坏项目物化内容。资源物理清理前检查修订、展板、嵌套资源引用；有引用时禁止直接清除或先明确解除依赖。

## 5. 资源如何映射为节点

首版复用现有文本/图片/音频/视频/文件素材节点，不新增一个可随意输出一切的“万能资产节点”。

组合资源插入后表现为可折叠分组；每个组件有稳定的节点与端口，连线真实可见。插入到目标节点时，只展开所选择的兼容组件。

人物的多个形象可以由多个图片节点表达，连接到支持 many 的输入；单图输入先选一张。提示词和描述同为 text 时，由用户选择正文组合方式并预览，不能按节点名称隐式拼接。

如果后续需要原生“资源引用节点”，必须另行设计稳定端口和版本契约。它不作为第一期资源库的必要条件。

配方应用只修改所声明的配置字段。显示将替换的 prompt、模型或参数，保留用户未选择覆盖的字段。应用配方不会自动运行模型。

## 6. 搜索、预览与性能

- 首版：名称/描述/标签/提示词正文搜索，支持收藏集、类型、时间和最近使用筛选。
- SQLite 搜索先实现可预测的中文子串或分词策略，再根据当前 bundled SQLite 能力决定是否启用 FTS；不能默认英文 tokenizer 能满足中文。
- 列表分页/游标加载，缩略图独立生成、缓存并设置上限；禁止一次读取全部原图或全部音频。
- 文件内容、版本和来源按详情面板懒加载。
- 搜索 UI 对旧请求去重/取消，避免晚返回结果覆盖最新搜索。
- 建议用 5,000 条资源的样本库记录搜索延迟和内存，目标为常规文本搜索 P95 小于 500ms；这是待实测目标，不是当前指标。

## 8. 项目复制的开发细节

1. 抽取已有导入器中的重映射和校验函数，形成内存 manifest。无需先导出 ZIP 再导入来复制大项目。
2. 当前编辑项目先 flush 保存，拿到确定 graphVersion；运行中新增结果不混进同一份复制快照。
3. 定义 ID 的作用域：项目级图 ID 可统一映射，媒体/项目全局 ID 必须新建，资源版本引用保留；任何映射都需同时覆盖 graph 和 tldrawSnapshot。
4. 遍历声明的媒体引用与项目媒体清单，包括 config、nodeResult、导演台、封面和项目内资源来源；不通过字符串片段替换正文。
5. 默认完整复制持有全部项目素材，避免漏掉用户未放上画布但已导入的素材；丢失文件先报告，不能假装完整。
6. 在暂存目录复制，检查空间与文件完成情况，记录 operation；DB 事务和目录提交成功后项目才 visible。
7. 仅结构模式复用清理原则，同时显示被移除内容概览；不能复制执行中任务和供应商 jobId 作为活动作业。
8. UI 显示真实阶段进度，取消只清理本次经路径校验的暂存目录。

- 从节点输入搜索只允许兼容内容；单值输入不会接入多项。
- 失败的复制/收藏不留下可打开的半成品。

### 总体顺序

核心三期合计 **64–101 人日**，应在一期存储设计和视频 PoC 后重新估算。优先交付项目复制和节点配置，同时建立库协议；随后贯通图片/提示词收藏与使用，再扩展组合和展板。

视频 R3-01 可以提前独立开展。其后端选择与实际 GPU 环境确定前，不承诺完整视频功能日历日期。

## 10. 发布、迁移与长期维护

- 旧项目不自动把所有生成历史灌入资源库；用户显式收藏，保留库的可用性。
- DB 迁移前备份；新表和可选项目字段优先向前兼容。
- 更新项目导出器，使固定版本来源与本地素材自包含；全库导出另设包格式。
- 导入时校验 manifest 版本、路径、文件大小和引用完整性；禁止携带 API Key。
- 资源使用统计不参与内容版本；本机更换后若无法恢复历史使用记录，不能影响内容可用性。
- 新增节点需完成仓库要求的契约、多输出、失败/取消、持久化和全量 verify 验收；本文仅列计划，本次未运行。
- 每期记录构建版本/源码提交，核对实际安装目录和桌面快捷方式，确保用户启动的是本次发布。

## 11. 需要优先防止的设计问题

| 问题 | 处理 |
|---|---|
| 人物、场景、风格各建独立一套数据表 | 用通用组件模型和表单预设 |
| 库文件仍指向源项目 | 收藏时取得独立文件所有权 |
| 提示词更新自动替换所有旧项目 | 使用固定 revisionId，显式升级 |
| 收藏一堆节点后仍要求用户手工拼接 | 保存自然表单，插入时解析兼容组件 |
| 有效 prompt 与效果图失去对应 | 配方、样例、版本分别记录关联 |
| 全局搜索只能按文件名 | 索引名称、说明、标签与正文 |
| “任意节点使用”变成无类型乱接线 | 统一搜索，按目标契约筛选并预览 |
| 一个视频节点随模式改变输出 | 深度估计与白模渲染分别定义稳定契约 |
| 把模型仓库可下载当作生产可分发 | 固定代码/权重/依赖版本并核对条款 |

建议先将 R1-01 至 R1-03 作为启动迭代：完成项目效率功能与资源协议，为后续积累建立稳定基础。
