# 视频转深度、视频转白模：独立节点最终实施方案

版本：v2.0 · 2026-09-26 · 状态：首版已实现，并完成 RTX 5080 本机视频实测

本方案替代《资源库与工作台优化方案 v1.0》中视频转换的接入建议。项目复制、节点选择和资源库的方案保持独立。

> 项目当前换机依赖、实测平台与白模画质边界见[本地视频转换说明](./VIDEO_CONVERSION_SETUP.md)。本文件中部分体验、运行包与验收表描述的是目标方案，不代表首版都已实现。

## 1. 最终产品决定

实现两个独立节点：

1. **视频转深度**：原视频输入，输出深度视频，可附带高精度深度数据。
2. **视频转白模**：原视频输入，输出白色无纹理模型质感的视频。

两个节点都可以单独使用。白模节点不要求用户先放置深度节点，不要求用户寻找或连接法线图。内部可以共用解码、估计模型、缓存和编码器。

运行方式：Electron 应用管理独立的本地 Python 推理运行包与模型。日常操作不依赖 ComfyUI，不配置 ComfyUI 工作流，不启动 ComfyUI 服务。

这两个功能属于确定性的媒体处理入口，不需要 Agent、主 Agent 或 Agent Flow。

### 1.1 能力结论

- 深度视频：存在可独立运行的现成开源模型，主要工作是工程接入和视频数据处理。
- 白模视频：本次检索未确认一个同时满足任意视频、稳定时序、直接输出成品、明确生产适用条件的一站式开源项目。可用的开源基础是视频深度或视频法线估计；我们需补白色材质着色、时序处理和输出。
- 上述白模路线可以提供固定原视角的白模效果，不承诺得到完整三维模型，也不支持凭空补出不可见背面或自由换机位。

“白膜”在产品界面统一写作“白模”。本方案定义的目标是去除原视频颜色与表面纹理，尽量保持构图、形体轮廓和动作。

## 2. 已确认的开源候选与选择

### 2.1 默认深度引擎：Video Depth Anything Small

该项目面向视频深度，提供独立推理脚本、灰度输出及 NPZ/EXR。官方将 Small 权重列为 Apache-2.0，Base/Large 列为 CC-BY-NC-4.0；首版选择 Small，固定代码提交和权重哈希。官方 A100 的 FP16 Small 示例为 6.8GB 显存（1×32×518×518），该条件不等于本机实测。离线模式作为首版基础，实验性流式模式不默认启用。[官方仓库](https://github.com/DepthAnything/Video-Depth-Anything)

工程选择理由：目标与视频转换直接匹配，能够拿到深度数组，便于控制视频编码、缓存和白模渲染；不必先建设通用工作流后端。

### 2.2 白模增强候选：NormalCrafter

该模型生成视频法线序列。官方实现具有独立推理路径；仓库代码为 MIT，模型卡标注 Apache-2.0，但推理还加载 Stable Video Diffusion 的基础组件，分发前必须核对这些组件的实际版本和条款。官方参考显存为 512×256 约 6GB、1024×576 约 20GB。[官方仓库](https://github.com/Binyr/NormalCrafter)、[权重模型卡](https://huggingface.co/Yanrui95/NormalCrafter)、[推理代码](https://github.com/Binyr/NormalCrafter/blob/main/run.py)

它输出的是表面方向，不直接输出白模成片。我们的白模渲染器使用这些方向进行固定白色材质着色。该链路作为增强引擎，需通过效果、兼容性、完整依赖条款三项门槛后启用。

### 2.3 候选比较

| 方案 | 适合本需求的部分 | 最终决策 |
|---|---|---|
| Video Depth Anything Small | 视频深度与基础白模结构估计 | 首版默认模型 |
| NormalCrafter | 直接估计视频表面方向，供白模着色 | 增强候选，完成验证后加入 |
| Depth Anything 3 | 深度和相机/多视角估计方向 | 后续替换候选，本轮不引入重建功能 |
| DepthCrafter | 视频深度研究对照 | 不作为默认生产模型 |
| 单张图片深度模型逐帧运行 | 简单实验 | 不作为默认视频方案，需另解时序稳定 |
| 视频生成模型按“白模风格”重绘 | 风格化视觉效果 | 不作为本轮结构保持型转换方案 |

Depth Anything 3 的官方模型表列出不同规模及不同许可，不能笼统认为所有权重都同一授权；升级时需对照视频样片，不因版本名称较新直接更换默认引擎。[官方模型表](https://github.com/ByteDance-Seed/Depth-Anything-3#model-cards)

DepthCrafter 的公开许可限制商业或生产用途，因此不进入默认打包清单。[项目许可证](https://raw.githubusercontent.com/Tencent/DepthCrafter/main/LICENSE)

### 2.4 选型门槛

生产默认只保留一个已验证深度引擎。NormalCrafter 未过门槛时，不自动替换成“看似一样”的其他模式；用户看见的引擎和实际运行记录必须一致。

不存在“装了开源模型就等于已经完成视频产品”的前提。我们承担解码、时间轴、缓存、资源限制、错误恢复和正式结果登记。

### 2.5 首版实现与实测记录

2026-09-26 已在 Windows + NVIDIA GeForce RTX 5080 上运行 Small 权重，并处理一段 854×480、24 fps 的视频片段。前 10 秒共 240 帧，模型推理约 12 秒；深度结果和白模结果由一次深度推理共同生成，MP4 均保留原音轨并通过时长、帧数和分辨率检查。

当前实现默认最长边 512 px，可在节点设置中选择 768 或 1024 px。该实测将最长边设为 1024 px，因此保留输入的 854×480 分辨率。RTX 5080 的实测结果不能代替其他显卡和长视频的性能测试。

本次验证脚本让两个结果共用一次深度推理；目前画布中的两个独立节点分别运行时会各自推理，跨节点推理缓存尚未实现。

## 3. 两个节点的用户体验

### 3.1 视频转深度

节点默认显示：原视频缩略图、处理范围、输出尺寸、近远方向、开始/取消、结果预览。

默认值建议：

- 范围：完整输入视频；可选开始/结束时间，单位毫秒。
- 尺寸：保持宽高比，初始最长边 768；不自动放大低分辨率输入。
- 时长：保持选定片段时长。
- 帧率：优先保留可表达的源时序，必要时显式转换恒定帧率。
- 深度显示：近白远黑；可切换，但不改变保存的原始数据语义。
- 音轨：默认不保留，可选择复制或转码原音轨。
- 高精度数据：可选保留；用于后续处理和导出，不影响普通视频使用。

高级选项：推理尺寸、FP16/FP32、灰度映射范围、处理缓存与高精度格式。模型内部时序窗口不暴露为随意调节参数。

“先看效果”按钮对用户选定的 3–5 秒片段运行，产生标记为预览的结果；点击“转换完整片段”才生成正式结果。

### 3.2 视频转白模

默认只接原视频。界面显示：处理范围、输出尺寸、效果档位、形体强度、光照方向、环境亮度、开始/取消、原图与结果对比。

效果档位：

- **基础白模**：共用深度模型，推导近似表面方向后着色。
- **增强白模**：使用视频法线模型，完成验证与依赖准备后才可选；未安装时显示可用条件。

两个档位输入和输出契约一致，区别为同一转换能力的实现参数。用户无需手工串联模型。

默认处理整个画面。自动抠出人物、把背景换成纯色需要分割或遮罩能力，不把它隐藏在首版承诺里。已有背景也会转换成相应白模表面。

预览与正式渲染共用着色参数，固定尺度映射；预览可能因上下文较短而与完整视频估计有小幅差异，不能保证逐像素相同。

### 3.3 共同交互

状态显示排队、读取视频、估计结构、渲染、编码、保存与失败原因。只有可计算分母的阶段显示百分比；不把模型加载时间伪装成帧进度。

结果是独立视频素材，源视频不改动。可以继续连线、导出和收藏到资源库。调整参数后再次运行会创建新结果，不覆盖旧文件。

## 4. 深度视频的处理链路

```text
in-video
  → 校验/ffprobe（时长、尺寸、旋转、时间戳）
  → 固定处理片段与时间映射
  → 解码、方向修正、宽高比保持
  → 按镜头组织时序输入
  → 视频深度估计
  → 存储深度与帧时间信息
  → 镜头级灰度映射
  → 编码、可选音轨处理
  → 校验结果并登记项目素材
```

### 4.1 深度值的解释

相对深度、逆深度和度量深度分别标记。默认相对模型不标注“米”。编码前由模型适配器声明输出语义和近远方向，不能靠颜色猜测。

每个镜头用固定统计范围映射灰度，例如分位点裁剪；不得每帧独立自动拉伸，让静止物体忽亮忽暗。镜头切换允许重新估计映射，并记录分段边界。

底层浮点输出与显示映射分别保存；切换近白/近黑只改显示。深度 MP4 供观看与兼容控制，精确数值读取高精度包。

### 4.2 长视频与分段

官方深度实现含固定窗口、重叠帧及尺度对齐逻辑，不能把每段当作无关视频处理后直接拼接。[核心推理实现](https://github.com/DepthAnything/Video-Depth-Anything/blob/main/video_depth_anything/video_depth.py)

首版适配器保留原时序逻辑，镜头内状态连续，切镜后重置。为了限制内存，把可提交的结果逐段落盘；重构缓存时需与固定响应/样片基线比较。

若初期无法保证长视频的有界内存，就在运行前明确显示支持的最大时长与分辨率。禁止静默只处理前几百帧。

## 5. 白模视频的处理链路

### 5.1 基础白模：首版必须实现的路线

```text
原视频 → 共享视频深度估计
       → 镜头内固定尺度的伪表面
       → 深度边缘处理及近似法线
       → 固定白色材质、简化方向光与环境光
       → 输出白模视频
```

深度为相对值时，使用明确标记的屏幕空间近似表面，不伪造真实相机标定。形体强度控制深度变化在着色中的作用。

一种可实现的着色形式：

```text
N = normalize(-s × ∂h/∂x, -s × ∂h/∂y, 1)
brightness = ambient + diffuse × max(dot(N, L), 0)
pixel = encode_sRGB(clamp(white_material × brightness))
```

其中 h 为按镜头固定尺度处理的表面值，导数按画面归一化坐标计算，s 为形体强度，L 为视图空间固定光照方向。这是我们的近似算法，不是对模型原始输出的物理测量解释。

需要处理近远极性、法线朝向、深度不连续边缘和无效值。原视频颜色不参与材质，避免原纹理重新出现在白模上。滤波不能简单跨帧平均，否则会造成动作拖影。

该路线的优点是共用已选模型，新增运行依赖较少。局限是精细表面容易显得平、边界可能呈浮雕状；必须通过目标样片确定是否达到用户所说的白模效果。

### 5.2 增强白模：法线模型路线

```text
原视频 → 视频法线估计 → 坐标系校准/单位化/边界处理
       → 同一白色材质渲染器 → 白模视频
```

读取浮点法线，不从有损 RGB 法线预览视频反解。适配器明确 xyz 轴向、法线符号和相机/视图空间，使用已知形状样例校验光照左右与凸凹。

NormalCrafter 的可视化辅助函数把法线值映射为颜色；这些彩色预览并不是白模输出。适配器需要直接获取模型数组，再送给我们的着色器。[官方辅助实现](https://github.com/Binyr/NormalCrafter/blob/main/normalcrafter/utils.py)

法线估计提供了另一种形体信息来源，不能在未做对比时宣称必然比深度推导更好。增强档位的名字只在样片显示有价值后发布。

### 5.3 不应承诺的效果

不承诺真实投影阴影、完整环境遮蔽、正确透明/反射材质、不可见背面或换视角。首版使用简单光照，不在 UI 提供尚未实现的真实三维材质参数。

如果用户的目标是“像三维软件真正渲染出的高质量全场景白模”，而两条路线均未达到标准，则该目标转为重建/重绘专项；不能用深度视频冒充完成。

## 6. 独立本地引擎架构

```text
React 节点卡片
  ↓ 现有节点 executor + gateway 契约
Electron main：VideoConversionService
  ├─ 输入校验、模型管理、GPU 队列、作业数据库
  ├─ 既有 FFmpeg/FFprobe 能力封装
  └─ 受管 Python Worker（管道通信，无需浏览器服务）
       ├─ VideoDepthAnythingAdapter
       ├─ NormalCrafterAdapter（可选）
       ├─ WhiteClayRenderer
       └─ 数组缓存/时间映射
  ↓
项目媒体仓库 + 执行记录 + 独立结果节点
```

首版使用一个受管 worker，一次处理一个 GPU 作业；两节点共用队列，避免同时加载大模型。按需切换模型，内存不足时卸载另一模型，不能靠启动多个进程争抢显存。

业务入口分别为 `convertVideoToDepth` 和 `convertVideoToClay`。共享底层算法不改变节点的独立身份。

### 6.1 进程与通信

- 用固定可执行文件路径与参数数组启动进程，Windows 窗口隐藏。
- stdin/stdout 使用版本化 JSON Lines；日志写 stderr，避免日志污染协议。
- 请求含 protocolVersion、jobId、输入文件引用、配置、输出暂存目录。
- 事件含 jobId、seq、stage、completedFrames、totalFrames、warning/error。
- 不把视频帧用大段 base64 在 Electron 和 Python 之间来回传；通过受管文件/数组目录交换。
- 预览和正式任务都记录 jobId。重复命令返回原任务，不重复提交。

### 6.2 运行环境

**当前实现：**应用提供“安装本地推理环境”入口，但首次启动前仍需系统可发现的 Python 3.12；程序随后在应用数据目录创建隔离虚拟环境，在线安装固定依赖并下载校验 Small 权重。离线包导入尚未实现。视频编解码继续调用本机 FFmpeg/FFprobe；需要 NVIDIA CUDA 显卡和兼容驱动。无需配置 ComfyUI。

后续发行目标仍是由应用管理可校验、可更新的运行包和离线导入路径，避免用户准备全局 Python；运行中不隐式下载新模型。

新模型或新运行包安装到新版本目录，通过健康检查后切换，失败保留旧版。不得修改用户系统 Python 或全局 CUDA 环境。

GPU 驱动由系统提供，不假设打包了 CUDA runtime 就兼容所有显卡。当前仅 Windows RTX 5080 样片完成实测；Linux NVIDIA 路径存在但未完成验收，macOS、CPU 和 AMD 不支持。

## 7. 当前电脑与资源预算

已验证机器：NVIDIA GeForce RTX 5080，驱动 591.86。已安装隔离推理环境并校验 116,440,756 字节的 Small 权重；同一输入前 10 秒视频成功输出深度与白模 MP4。实际依赖准备、占用和换机步骤见[本地视频转换说明](./VIDEO_CONVERSION_SETUP.md)。

建议把该机器作为首个验证目标：

| 能力 | 初始验证档位 | 备注 |
|---|---|---|
| 深度 | Small、FP16、最长边 768、5–10 秒 | 记录实际峰值，不直接套用 A100 数据 |
| 基础白模 | 复用深度数组，渲染同尺寸 | 重点看轮廓、浮雕感和闪烁 |
| 法线增强 | 最长边 512 或 768，按需 CPU offload | 不默认开启官方约 20GB 的高分辨率档位 |

验证 PyTorch 的设备识别、架构支持和实际 kernel 执行；不能以 `cuda.is_available()` 一项作为全部通过条件。注意可选加速依赖与该显卡的兼容性，首版不强制依赖 xformers。

同时核对系统 RAM 和磁盘预算。视频模型能处理长序列不代表其演示脚本内存恒定；解码帧和浮点数组可能占用数 GB。队列应根据配置预估，并在开跑前显示临时空间需求。

OOM 时允许用户切换低分辨率预设；不能自动改变已提交任务的质量设置并把它当成原配置完成。新设置创建一次明确重试。

## 8. 视频时间、色彩与编码

### 8.1 时序

由 FFprobe 读取真实时间基与帧时间戳，处理旋转、非方形像素和可变帧率。需要转 CFR 时记录目标有理数帧率及源到输出时间映射，保证时长不因简单采样发生变化。

低帧率预览可以重采样；正式转换不默默丢帧。若采用抽帧模式，界面明确告知，并记录为不同配置。

样片验证 23.976/29.97、竖屏旋转、可变帧率和带音轨素材。不能仅比较文件头的 FPS。

### 8.2 色彩

输入 HDR 先做明确的模型输入色调映射并记录；不把 HDR 数值直接按 SDR 解读。深度/法线数组为非颜色数据，不做视觉 gamma 变换；只在渲染预览时编码为显示颜色。

### 8.3 音轨与输出

默认不携带音轨，节点选项可保留。片段裁切必须使音轨同步；编码器不兼容时转码并记录。不存在音轨时正常完成。

默认交付易预览的 MP4，具体编码器沿用经过核对的应用发行配置；FFmpeg 编译选项及所带编码器作为发行依赖核对。高精度数组单独保存，MP4 不用于恢复精确深度。

## 9. 节点协议

### 9.1 视频转深度：`video-depth`

| 方向 | ID | 类型 | 要求 |
|---|---|---|---|
| 输入 | `in-video` | video，one | 必需，原始视频 |
| 输出 | `out-video` | video，one | 深度控制视频，运行成功必有 |
| 输出 | `out-json` | json，`video.depth@1` | 帧映射、模型、参数、语义和来源 |
| 输出 | `out-file` | file，one | 可选高精度包；只有选择保留时产生 |

### 9.2 视频转白模：`video-clay`

| 方向 | ID | 类型 | 要求 |
|---|---|---|---|
| 输入 | `in-video` | video，one | 必需，原始视频，不是深度图 |
| 输出 | `out-video` | video，one | 白模效果视频，运行成功必有 |
| 输出 | `out-json` | json，`video.clay@1` | 实际引擎、着色、帧映射和来源 |
| 输出 | `out-file` | file，one | 可选诊断包，含本次使用的深度/法线及说明 |

可选输出在契约中明确 optional；下游若要求必需文件而本次未产生，应阻止运行并提示打开保留选项。模式不改变端口 ID 或类型。

配置写 `props.config`，执行通过共享 executor 与主进程 gateway，正式结果写 `meta.nodeResult`，JSON 附加输出沿用现有元数据白名单机制并做适配。不得在 React 直接运行模型。

两个节点建立 NodeTypeSpec、ActiveNodeTypeId、稳定 contractVersion、JSON Schema 和 projectOutputs。输出视频物化为独立素材节点；多个运行结果分别保留。

给视频增加语义标记：rgb、depth-control、clay-render。普通播放器可以播放，但下游生成模型是否接受 depth-control 必须由能力配置确定。

## 10. 作业、缓存与恢复

### 10.1 状态

```text
queued → probing → decoding → inferring → rendering → encoding → committing → succeeded
                          ↘ failed / cancelling → cancelled
进程重启后未完成任务 → interrupted → 用户选择重试或从可靠分段恢复
```

不是每个中间阶段都能精确续跑。首版承诺恢复任务记录、复用已完成且校验通过的缓存；未保存模型状态的时序段从安全边界重新执行。

### 10.2 缓存键

输入文件 hash、片段范围、帧时间映射、模型/权重 hash、推理配置、引擎版本共同构成估计缓存键。着色光照参数不进入估计缓存键，进入渲染缓存键。

因此先跑深度再跑基础白模时，在输入与估计配置相同时可以复用；只改光照无需重跑模型。不同尺寸、采样、模型、归一化依赖变化必须失效，不能只按文件路径复用。

缓存为可清理加速数据。用户选择保留的高精度包则是正式项目资产，不能随缓存清理被删除。

### 10.3 取消与结果提交

取消先发协作信号，超时终止本任务 worker；重建 worker 后再处理后续队列。编码器也需随任务停止。晚到输出不会覆盖新任务。

结果先在 job 暂存目录生成，校验可解码、时长、帧数和元数据一致，再登记媒体并原子提交。失败不返回成功状态，不覆盖源文件。

磁盘不足、模型缺失、显存不足、格式错误、进程崩溃分别使用稳定错误码，给出具体可操作建议。日志不记录用户密钥。

## 13. 开发任务与顺序

| 步骤 | 工作 | 交付/出口 | 估算人日 |
|---|---|---|---|
| V1 | 独立推理验证 | 当前 5080 上跑通 Small；得到深度及基础白模样片；核对 Windows 依赖 | 3–5 |
| V2 | 管理运行环境 | 下载/离线导入、哈希检查、GPU 健康检查、版本回退 | 3–5 |
| V3 | 转换作业底座 | 队列、进程协议、取消、状态持久化、时间轴、缓存 | 4–6 |
| V4 | 深度节点 | 配置 UI、契约、灰度输出、高精度包、媒体登记 | 3–5 |
| V5 | 基础白模节点 | 原视频直接输入、深度法线近似、着色、预览与正式输出 | 4–6 |
| V6 | 集成和发行 | 时序/错误/旧功能回归、节点契约、安装包和说明 | 3–5 |

首版双节点预计 **20–32 人日**，为熟悉当前工程的开发者估算，含对应验证；不承诺尚未测量的速度和视觉质量。

增强法线路线另计 **5–9 人日**：完整依赖核对、适配与低显存策略、法线坐标校准、样片对比。若依赖或质量不满足，保留研究结果，不放进正式默认安装。

V1 样片必须先评审白模是否达到目标。通过后建设 V2–V6；没通过则选择增强路线继续验证并重估，不用堆 UI 掩盖算法不足。首版可以先发布已通过的深度节点，白模必须单独达到验收。

## 14. 验收矩阵

本表为完整验收矩阵。当前只完成上文记录的单机 10 秒样片和项目类型检查，其他输入、显卡、平台与长视频矩阵仍未完成。

| 类别 | 样例/操作 | 通过条件 |
|---|---|---|
| 深度基础 | 室内、人物、室外移动镜头 | 主要前后关系可辨；近远方向正确 |
| 白模基础 | 人物衣物、物体、背景 | 原图颜色/纹理不直接混入；有可读的形体明暗 |
| 运动保持 | 行走、转身、快速动作 | 无生成式改动作；轮廓与时间大致对齐，估计异常明确记录 |
| 时序 | 静态镜头、移动镜头、多镜头硬切 | 不逐帧全图跳亮；跨镜头不错误传播状态 |
| 难例 | 发丝、透明、反光、多人遮挡 | 记录边缘和形体错误，给出适用边界 |
| 视频格式 | 竖屏旋转、VFR、23.976/29.97 FPS | 不错转、不改变播放速度；CFR 映射可追溯 |
| 音轨 | 有声/无声、片段裁切 | 保留模式同步，关闭模式无音轨 |
| 单节点使用 | 原视频分别连两个节点 | 均可直接执行，不需要另一个节点或 ComfyUI |
| 缓存 | 先深度后基础白模、只调光照 | 条件相同复用推理；配置改变正确失效 |
| 恢复 | 运行中退出、重新打开 | 状态可解释，成功缓存可复用，不伪称继续丢失的模型状态 |
| 取消 | 推理/编码阶段停止 | 子进程和临时写入停止，源素材无变化 |
| 错误 | OOM、磁盘满、模型缺失、坏视频 | 明确错误、不产生假成功，不静默降低质量 |
| 数据输出 | NPZ/manifest 与视频 | dtype、shape、时间、语义和引用一致 |
| 项目迁移 | 导出再导入含转换结果的项目 | 视频和保留的数据包完整，媒体引用重映射 |
| 发行 | 干净机器安装组件后启动 | 无系统 Python/ComfyUI 配置要求，版本可查 |

每类选 5–10 秒短片，另加一个至少 60 秒视频验证内存和分段。固定模型、配置、输入 hash；记录总耗时、峰值显存、RAM 和临时磁盘空间。默认档位与最大支持时长依据这些结果确定。

白模视觉验收由用户选择的目标样片主导；评价形体、轮廓、纹理去除和稳定性，不以“能输出一个白色视频文件”作为完成。

## 15. 发布决策与最终建议

确定采用：**两个独立视频输入节点 + 应用管理的本地推理运行包 + 共享深度/法线与媒体处理底座。**

默认深度选 Video Depth Anything Small。基础白模先实现深度驱动的白色材质着色，独立评估 NormalCrafter 增强路径。无 ComfyUI 集成工作，不让用户配置内部处理链路。

后续仍需验证目标样片的白模视觉质量、其他显卡/长视频的显存与吞吐、Linux 发行版兼容性以及增强法线路线的完整依赖条款。这些验证不会改变两个节点可以单独接收原视频的产品接口。
