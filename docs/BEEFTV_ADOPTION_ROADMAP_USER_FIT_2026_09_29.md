# Canvas Studio：按实际创作需求修订的 BeefTV 借鉴方案

日期：2026-09-29。此版取代《BEEFTV_ADOPTION_ROADMAP_2026_09_29.md》的功能优先级和工期；旧文保留为参考功能调研与源码索引。模型目录的首批优化已开始实施，其余阶段仍为方案。

## 模型分类补充决策

“识图”按**输入能力**配置，不作为与文本模型平级的新模型类别。模型目录仍选择“文本模型”，其下增加“支持图片输入”开关或输入能力项；验证通过后显示“文本输出 · 可接收图片”标识。该模型继续执行 `text.generate`，可输出文本、Markdown 或 JSON；选择图片模型仍代表 `image.generate` / `image.edit` 等图片产出能力。

底层可复用 `Capability.acceptedAssetKinds`，在文本生成能力中标记 `image`，并保留文字输入。现有 `ModelValidationSnapshot` 按 operation 记录验证；仅用纯文本请求通过 `text.generate` 验证，不能证明识图能力。实现时应增加独立的图片输入验证状态或按“操作＋输入能力”记录验证结果，并用真实测试图片提问验证。模型保存时的勾选是用户声明，运行时只允许已通过图片验证的模型处理图片。已经验证纯文本能力的旧模型默认只显示文本输入能力，不自动升级为识图。

AI 处理节点检测是否连有图片：无图时所有已验证文本模型可选；有图时只显示已验证支持图片输入的文本模型。图片以项目媒体引用交给主进程解析，再组装供应商请求；输出端口和现有 JSON Schema 验证流程保持一致。对话节点若后续需要看图，复用同一模型能力和传输路径。此决定替代旧文“新增 vision 模型类别”的表述。

### 已开始的模型目录改动与后续顺序

第一批代码改动：文本模型可声明图片输入；识图验证发送内置测试图并检查颜色回答；修改能力、连接地址、协议或密钥会使旧验证和绑定失效；模型目录展示能力与验证状态。识图验证当前只开放实际文本调用链已匹配的 OpenAI 兼容协议。此批是**模型配置与验证**，尚未把用户图片接入聊天或 AI 处理请求。

后续模型侧按以下顺序推进，均不要求新增业务节点：

1. **统一模型目录与旧供应商设置的行为。** 当前仍有两套配置入口和目录回填，逐步把可调用模型、验证与绑定收敛为同一事实来源；保留旧配置的安全迁移。
2. **接通项目图片的模型请求。** 先做主进程受控媒体读取与多模态消息组装，按供应商协议分派；避免把本机路径或密钥传到渲染器。再选择面向用户的应用入口。
3. **补齐协议适配。** 目录提供 Google、Anthropic 等连接类型，但当前正式文本调用主要用 OpenAI 兼容驱动；原生协议要在正式调用和验证都可用后才展示“可识图”。
4. **改善选择模型的过程。** 在模型管理页明确“可用、待验证、失败、需要重新绑定”；按输入/输出能力筛选；显示验证耗时及最近错误。模型绑定应有可见入口，避免只靠功能键字符串。
5. **真实质量验收。** 识图除内置颜色图外，还需用户常见素材样本；测试清晰度、文字识别、复杂场景、结构化 JSON 成功率、耗时和成本。单张红图验证只证明基础传输和视觉识别，不能证明创作质量。

## 1. 用户取舍与结论

| BeefTV 能力 | 决定 | 在我们项目里的处理 |
| --- | --- | --- |
| 调色、草图、多角度、打光、人物质感 | 不立项 | 没有当前创作需求，不新增节点、模板或快捷入口 |
| 普通图片尺寸调整 | 不立项 | 以生成尺寸为主；未来如遇平台像素硬要求再考虑导出时处理 |
| A/B 对比 | 暂不立项 | 有明确的 AI 超分及原图对照需求后，再做同一预览器中的对比；不单设节点 |
| 提示词优化 | 复用 AI 处理节点 | 保存一份节点库模板或示例配置，不新增节点类型 |
| 图片评审 | 复用 AI 处理节点 | 先接通多模态图片输入与结构化报告；只有报告需要特殊交互时才扩展查看器 |
| BeefTV 批量创作表 | 不复制独立表格 | 先研究现有分镜板与循环的逐镜头执行；确有编辑或恢复缺口时增强分镜板 |
| 剧本角色/场景/道具提取 | 复用 AI 处理、结构化、节点库和资源库 | 处理节点负责提取；节点库负责复用流程；资源库负责保存经人工确认的素材 |

## 2. 现有概念与真正的空缺

- **AI 处理节点**已接受多路文本和 JSON 上下文，可输出文本、Markdown 或经所选 Schema 验证的 JSON。纯文本提示词优化、剧本提取不需要新节点。当前端口没有图片输入；多模态评审的核心增量是可信的 `image` 输入、模型能力校验和结果展示。
- **分镜板**已经是可编辑镜头表格，镜头有稳定 ID，可增删、上下移动、逐字段编辑，输出 `storyboard.shots@1` 和摘要。BeefTV 批量表侧重每行提示词、参考素材、执行参数和生成结果。我们若要补，重点是镜头与生成任务、结果之间的关系，而非再画一张表。
- **循环节点**已有 `list.items@1` 输入、逐项运行、结果汇总和失败项/续跑模式。分镜板输出的 `storyboard.shots@1` 与循环输入并非同一 Schema；需要显式转换或契约化映射，再验证逐项任务身份与恢复语义。
- **节点库**保存可复用的节点组合与连线。**资源库**保存素材、提示词、角色、场景、风格等可复用内容及版本。**提取**是把剧本文本转成候选结构数据的计算步骤；用户确认后才成为资源库内容。三者属于不同层次，已有节点足够承担第一版提取。
- **AI 超分**是用户提出的唯一可能改变图片节点优先级的能力。当前生成目标尺寸不能解决低清旧图、局部裁剪、较小模型输出以及固定尺寸素材的放大质量问题。先验证云端模型质量、成本和输出契约，再决定是否立项；普通插值缩放不能充当超分。

## 3. 新的阶段计划

工期为一名熟悉项目的工程师的粗估工程日；在 P0 调查后重估。每一阶段有独立的退出条件，不按时间自动放行。

| 阶段 | 目标 | 具体工作 | 退出条件 | 粗估 |
| --- | --- | --- | --- | --- |
| P0：真实链路核对 | 确认缺口 | 用一份剧本、20 个镜头和 3 个可复用角色跑通现有 AI 处理→分镜板→循环→生成；记录 Schema、引用、结果、恢复的断点；核查已配置的供应商 | 形成可复现的问题清单和最小实施范围 | 2–3 天 |
| P1：运行可靠性 | 减少重复生成和成果丢失 | 区分提交、查询、下载、落盘失败；继续查询原任务或重下结果；快照恢复前备份、媒体引用检查；增强现有诊断 | 重启后已受理任务不被盲目重交；失败恢复不损坏项目 | 8–12 天 |
| P2：多模态 AI 处理 | 用一个节点处理看图与评审 | 扩展 AI 处理的图片端口、主进程请求和供应商能力验证；结构化报告可查看；节点库提供“图片评审”“参考图分析”“提示词优化”配方 | 真实图片进入已验证视觉模型；报告与图片来源关联；纯文本模式保持兼容 | 8–14 天 |
| P3：分镜生产闭环 | 让分镜直接驱动生成 | 通过显式转换/映射把 `storyboard.shots@1` 接入逐项任务；每镜头绑定固定资源版本、提示词、参考图、任务和选用结果；按镜头重做和续跑 | 20 镜头中改 3、失败 2 后，只处理受影响镜头，资源与结果不串行 | 10–16 天 |
| P4：素材沉淀与复用 | 剧本候选进入资源库 | 用 AI 处理输出角色、场景、道具候选 JSON；人工核对与去重；选中后保存为资源库版本；节点库保存提取和分镜工作流 | 重跑剧本不自动覆盖已确认资产；旧分镜引用仍可追溯 | 5–9 天 |
| P5：按需验证 AI 超分 | 判断是否值得新增图像能力 | 优先查 ToAPIS，其次火山的真实云端超分能力；用低清图、裁剪图、人物图评估质量、耗时、价格、尺寸和失败率 | 形成是否立项的结论；通过后再设计独立节点与原图对照预览 | 2–4 天调研；实现另估 |
| P6：规模与迁移 | 保障较大项目可用 | 基于真实分镜场景测画布、图片解码和结果查看；资源包换机导入；手动升级的数据保护 | 100 镜头项目可打开、滚动、续跑、导入导出；性能与数据指标满足 P0 约定 | 6–10 天 |

P0–P4 约 **33–54 工程日**，P6 约再加 **6–10 天**；P5 的云端超分调研独立进行，是否开发由实际效果决定。估算不含供应商开通及外部服务等待。

## 4. 实施边界

1. 新模型能力复用已有供应商配置。视觉模型先用真实图片验证，不根据名称猜测支持情况；不新增本地生成模型。
2. 对 AI 处理节点的端口或契约调整，先读 `NODE_CONTRACT_SPEC.md`，补 `contractVersion`、输入/输出 Schema、执行器、输出投影、持久化与失败测试，通过 `test/node-compliance.test.ts` 和全量 `npm run verify`。
3. 镜头任务按稳定镜头 ID 和输入版本记录；分镜编辑、项目重开和导入导出保持关系。批量并发只在逐项状态隔离后考虑，串行先交付。
4. 角色、场景、道具候选进入资源库需用户显式选择；模型输出不直接修改已确认资源。节点库只保存可复用流程，项目媒体依旧走资源/项目资产引用。
5. 不增加登录、团队、云项目、Agent/CLI/MCP/headless、画布内成片剪辑、自动更新或字幕转写。视频任务的“取消”继续按本地停止观察表达。

## 5. 先做的三个小交付

1. **AI 处理配方**：用现有节点保存提示词整理、剧本候选提取配置，确认结构化输出的实际可用性。这一步几乎不需要新节点代码。
2. **分镜到生成的单镜头路径**：先让一个镜头连上资源库引用、生成任务和选用结果，再扩到 20 镜头的串行处理与失败续跑。
3. **视觉输入试点**：选一个已配置供应商的视觉模型，完成图片输入、评审 JSON、真实调用、重开与导入导出回归。
