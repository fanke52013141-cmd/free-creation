# 通用 Agent Flow：架构与开发方案

版本：v1.0 · 2026-09-26 · 本文所有新增接口为设计草案

## 1. 现有基础与差距

| 已核对的位置 | 当前能力 | 本次演进方式 |
|---|---|---|
| `src/shared/types/index.ts` | 项目、节点、端口等基础类型 | 增加可选配置引用与协议版本，兼容旧项目 |

| `src/main/store/projects.repo.ts` | SQLite 索引与 project.json 图数据 | 图定义继续保存；运行账本写 SQLite |

`AGENTS.md` 明确旧 Agent/CLI/MCP/headless 实现已移除。新增非渲染进程执行路径前，应补桌面与新运行宿主输出一致性验证。共享接口内历史注释不代表现有 headless 可直接启用。

## 2. 架构决策

### 2.1 分层

```text
Renderer：画布 / 任务面板 / 协作会话 / 产物 / 配置中心
        ↓ 类型化 IPC 命令                         ↑ 持久化事件投影
Main：Flow 应用服务（校验命令、事务、查询与导入导出）
        ↓
FlowRuntimeAdapter：唯一负责流程调度和恢复的运行后端
        ├─ Agent 调用适配器 → 现有模型网关
        ├─ NodeExecutorAdapter → 共享基础执行器
        ├─ HumanTaskService → 待办、决策与恢复信号
        └─ ContextBuilder / ArtifactService
        ↓
SQLite：定义修订 / 运行 / 事件 / 会话 / 产物引用 / 检查点
文件目录：既有媒体、不可变文本快照、模板资源
```

运行宿主由 Electron main 管理；耗时计算放入合适的 Worker 或子进程，避免阻塞 UI 和 IPC。代码节点保留现有离线 Worker 能力边界，不因 Agent 接入获得 Node.js 或任意网络能力。

不直接恢复历史 CLI/MCP。新服务首先供本地桌面使用；第三期若需要外部入口，再独立评估。

### 2.2 运行框架选择

建议第一期最先做 LangGraph JS 的窄范围适配验证。它支持混合确定性步骤与 Agent 步骤、持久化和人工中断；LangChain 提供模型、工具和 Agent 抽象。[官方概览](https://docs.langchain.com/oss/javascript/langgraph/overview)

验证范围：两个任务、一次工具调用、一次人工中断、进程重启恢复、重复命令去重、现有节点多端口输出一致性。还需核对目标 Electron/Node 版本、本地持久化实现、包体积和取消语义。

满足门槛后通过 `FlowRuntimeAdapter` 使用 LangGraph，不能再在外层实现一个竞争调度器。业务事件与表是审计/查询投影，运行状态变化由同一套命令和适配器推进。

若验证发现本地持久化或执行适配无法满足条件，则形成 ADR，选用本地有限状态运行器实现同一接口。此为替代决策，不同时维护两套生产后端；一期工作量应据此重新估算。

### 2.3 节点层与流程层

- 基础节点：声明输入输出，执行明确的能力。
- 任务阶段：声明参与者、完成条件和对应节点子图。
- 流程：组织任务依赖、分支、批处理及修订。

阶段折叠为 UI 分组；内部真实节点和端口保持可查看。若增加 Agent 执行节点或产物提交节点，必须遵守 `ActiveNodeTypeId`、`NodeTypeSpec`、Schema、executor、projectOutputs 和版本规范。

动态产物契约采用配置时实例化、保存后稳定的端口规格。契约变化要求新修订和重新校验，不能把所有业务端口标为 `any`。

现有业务边仅表达 `nodeId + portId` 数据依赖。Agent 委派、人工确认、条件调度保存在独立的流程定义内；不把装饰线混入边表，也不让主 Agent 按节点标题推断数据。

## 3. 核心类型草案

```ts
type Participation = 'human' | 'collaborative' | 'ai'
type ExecutionMode = 'manual' | 'single-call' | 'conversation' | 'tool' | 'subflow'
type ConfirmationPolicy = 'human' | 'validated-auto'

interface VersionRef { id: string; version: number }
interface ArtifactVersionRef { artifactId: string; versionId: string }

interface TaskDefinition {
  id: string
  title: string
  objective: string
  participation: Participation
  executionMode: ExecutionMode
  agentProfile?: VersionRef
  inputBindings: InputBinding[]
  outputContracts: PortContract[]
  contextPolicy: ContextPolicy
  confirmation: ConfirmationPolicy
  implementation: NodeBinding | SubflowBinding | ManualBinding
  limits: { maxAttempts: number; maxToolCalls: number; timeoutMs?: number }
}

interface AgentProfile {
  id: string
  version: number
  systemContent: string
  modelRef: string
  skillRefs: VersionRef[]
  allowedTools: ToolContractRef[]
  contextPolicy: ContextPolicy
}

interface FlowRun {
  id: string
  projectId: string
  definitionSnapshotId: string
  status: FlowRunStatus
  stateRevision: number
  runtimeCheckpointRef?: string
  createdAt: number
}

interface TaskRun {
  id: string
  flowRunId: string
  taskDefinitionId: string
  itemKey?: string
  status: TaskRunStatus
  currentAttemptId?: string
  inputVersions: ArtifactVersionRef[]
  effectiveConfigSnapshotId: string
  outputVersions: ArtifactVersionRef[]
  sessionId?: string
  staleAgainstCurrentSelection: boolean
}

interface ArtifactVersion {
  id: string
  artifactId: string
  revision: number
  kind: 'text' | 'markdown' | 'json' | 'image' | 'audio' | 'video' | 'file'
  contentRef: string
  contentHash: string
  schemaRef?: VersionRef
  source: { taskRunId?: string; attemptId?: string; actor: 'human' | 'ai' | 'tool' }
  inputVersions: ArtifactVersionRef[]
  createdAt: number
}
```

辅助类型在开发时结合现有 PortSpec 定义，避免复制两套 Schema。`modelRef` 只引用本地供应商配置，不存 API Key。

Agent 配置、TaskDefinition、FlowDefinition 都采用不可变修订加可编辑草稿；FlowRun 固定快照。运行中修改 Agent 指令创建新任务修订/尝试，并记录差异，不悄悄改写正在调用的输入。

## 4. 存储设计

### 4.1 建议新增表

| 表 | 关键内容 | 约束 |
|---|---|---|
| `flow_definitions` / `flow_definition_versions` | 可编辑草稿与发布快照 | 同一逻辑 ID 的版本唯一 |
| `agent_profile_versions` / `skill_versions` | 指令、工具引用与版本 | 发布后不可变 |
| `flow_runs` / `task_runs` | 状态、修订号、快照、输入版本 | 更新必须校验 expectedRevision |
| `task_attempts` | 每次执行的开始/结束、错误和配置 | 不覆盖历史尝试 |
| `flow_events` | runId、seq、eventType、payload | `(run_id, seq)` 唯一 |
| `command_receipts` | commandId、结果、目标状态版本 | commandId 唯一，重复返回原结果 |
| `sessions` / `session_messages` | 按任务保存对话、工具结果及摘要引用 | 不使用一个全局共享消息数组 |
| `artifacts` / `artifact_versions` | 业务身份、版本、内容引用与来源 | `(artifact_id, revision)` 唯一 |
| `artifact_decisions` | 版本、接受/退回、意见、依据 | 决策引用具体版本 |
| `artifact_dependencies` | 输出版本依赖哪些输入版本 | 支持反向影响查询 |
| `human_tasks` | 编辑/讨论/选择/上传/确认请求及状态 | 同一待办只完成一次 |
| `tool_calls` | 幂等键、provider jobId、结果引用、未知状态 | 可查询既有调用结果 |
| `context_snapshots` | 来源、选用版本、摘要、估算 token | 不包含密钥 |
| `runtime_outbox` | 已提交但待通知运行后端的操作 | 消费可重入与可去重 |

运行后端的检查点按其适配方式保存，与业务事件通过稳定 runId、commandId 和操作记录关联。不能假设框架检查点与所有业务表天然具备跨库原子事务。

### 4.2 项目文件与数据库边界

- project.json 保存画布、工作台配置引用、流程定义引用与版本。
- SQLite 保存运行、消息、决策、产物索引和事件。
- 媒体继续使用现有 MediaAsset。文本/JSON 可按大小选择 DB 内容或文件引用，所有导出都能解析引用。
- 运行创建时把实际使用的图、配置和契约快照写入 SQLite，固定哈希；后续 project.json 改动不影响该运行。
- 涉及图和 DB 的变更使用可恢复的操作记录：记录意图、写文件临时件并原子替换、提交引用、标记完成；启动时对未完成操作补偿或回滚。

### 4.3 产物和画布的关系

Artifact 是领域对象，画布卡片是投影。删除某张展示卡片不自动删除历史成果和被其他运行引用的文件。

`emitArtifact` 当前主要面向媒体资产卡片。应增加适配层，把媒体结果登记为产物版本，再异步投影到画布，不能让“画布回调成功”成为正式结果持久化的唯一依据。

文本提炼、版本提交等新输出使用明确节点或流程步骤。查看、选择已有版本可以是附加操作，产生新内容则必须有生产步骤及来源。

## 5. 运行状态与完成语义

### 5.1 TaskRun 状态

```text
pending → ready → running → awaiting-human → ready / succeeded
                    ├──→ succeeded
                    ├──→ failed → ready（创建新 attempt）
                    ├──→ paused → ready
                    └──→ cancelling → cancelled
pending / ready → skipped（仅合法条件分支或显式策略）
running → recovery-required（重启后无法确定外部调用结果）
```

`awaiting-human` 另存原因：discussion、edit、upload、select、review。完成一次讨论消息不等于完成任务。

`succeeded` 的必要条件：声明的必需产物已登记、Schema 和引用有效、确认策略已满足、输出和完成事件已落库。可选输出缺失按契约处理；空输出不能被一律视为成功。

“产物过期”是相对当前选定上游版本的标记，不改写历史 TaskRun 的成功事实。

### 5.2 FlowRun 聚合状态

建议区分 created、running、waiting、paused、succeeded、failed、cancelled、recovery-required。优先规则：

1. 有实际运行或可执行的任务时显示 running，同时给出待人处理数量。
2. 没有可执行任务但存在人工待办时显示 waiting。
3. 全局暂停请求完成后显示 paused。
4. 所有必需任务及交付条件满足才 succeeded。
5. 不可恢复失败导致必需交付无法达到时 failed；允许继续其他独立分支的策略需显式配置。

汇总显示运行、待办、失败和完成数量，不用单一颜色隐藏局部状态。

## 6. 恢复、幂等与纠偏

### 6.1 人工确认事务

```text
收到 commandId + humanTaskId + versionId + expectedRevision
  → 检查命令是否已处理
  → 校验任务仍待处理、版本未变化、产物符合契约
  → 同一事务写决策、关闭待办、追加事件、写 outbox 与命令结果
  → outbox 消费者把恢复信号交给运行后端
  → 后端按稳定操作 ID 去重并推进
  → UI 读取新事件；断线后从最后 seq 补取
```

重复确认返回原结果；陈旧页面确认旧版本返回冲突并提示刷新，不能批准另一份内容。

### 6.2 外部调用

调用前保存意图与幂等键；提交后保存 provider jobId；成功后登记结果引用，再推进任务。支持查询 jobId 的供应商优先恢复查询。

网络断开或崩溃发生在“供应商已接受、jobId 尚未保存”的窗口时，不能承诺 exactly-once。标记结果未知，提供查询或明确重试操作；不自动再次付费调用。UI 必须说明不确定状态。

LangGraph 中断恢复会重新执行所在节点中断之前的代码。因此生成操作和人工审阅分开建步骤，恢复前先检查已有调用和产物记录。[官方中断说明](https://docs.langchain.com/oss/javascript/langgraph/interrupts)

### 6.3 暂停和退出

- 暂停：停止派发新任务；当前原子操作结束后落盘。不能声称远端任务立即停止。
- 取消：发取消信号，支持的供应商尝试取消；晚到结果隔离存档，不自动释放下游。
- 关闭窗口：沿用应用现有生命周期并明确提示；第一期不承诺隐藏后台持续执行。
- 完全退出或关机：保存可恢复点；再次启动先对账，再由用户继续。远端已提交任务可能继续执行，需要查询其状态。

### 6.4 局部重做

第一期仅支持串行流程：选择上游新版本后，显示后续受影响范围，创建修订运行，复用未受影响的确认产物。不能自动重跑已完成步骤。

第二期基于 `artifact_dependencies` 计算最小受影响闭包；批处理按 itemKey 和输入指纹隔离。相同下标不代表同一个对象，重排序不应丢失身份。

## 7. 上下文与工具执行

ContextBuilder 输入 TaskRun、配置快照及产物引用，输出：模型消息、工具列表、来源清单、预算估算与缺失项。

构建顺序为固定指令、项目硬约束、任务输入、相关成果、当前会话与反馈。资源内容作为资料处理，不能覆盖系统指令或增加工具权限。

工具参数必须使用已声明端口或 Schema；调用前校验，结果后校验。禁止 React 直接调用模型；禁止 Agent 绕过网关任意创建媒体或修改正式项目状态。

工具调用执行器复用现有输入解析、多值端口、输出投影和取消规范。运行宿主需要纯数据契约目录时，应从现有规格提取共享描述，避免手工维护第二份类型和端口表。

第一期先支持既有确定性能力和协作对话；第二期开放配置式受限工具循环；第三期才开放受限子任务委派。

## 8. IPC 与前端状态

建议新增命令及查询，不直接让 renderer 改运行表：

| 接口草案 | 输入要点 | 输出/行为 |
|---|---|---|
| `flow.validateDefinition` | 定义修订 | 契约、变量和依赖错误 |
| `flow.start` | projectId、definitionVersion、inputs、commandId | runId 和状态快照 |
| `flow.pause/resume/cancel` | runId、expectedRevision、commandId | 新修订或冲突 |
| `task.sendMessage` | taskRunId、sessionId、正文、commandId | 消息 ID 与增量事件 |
| `task.createDraft` | 消息范围、输出契约、commandId | 显式提炼步骤和产物引用 |
| `humanTask.resolve` | 待办、动作、版本、意见、revision、commandId | 决策及后续状态 |
| `task.retry` | taskRunId、输入/配置修订、commandId | 新 attemptId |
| `artifact.createRevision` | artifactId、baseVersionId、内容 | 新草稿版本 |
| `flow.getSnapshot/getEvents` | runId、afterSeq | 当前投影/增量事件 |
| `flow.planRevision` | 新定义或输入版本 | 受影响任务与重做建议 |

前端 Zustand 保存临时选中、面板和缓存投影；不成为正式运行状态的唯一存储。事件具有 seq 和 schemaVersion；断线补取后去重。大段模型流先临时显示，定期或消息结束时持久化，重启后明确标记未完成的消息。

## 9. 第二期编排语义

- 数据依赖默认 DAG；条件、并行、ForEach、Join 和人工修订作为显式流程控制。
- 条件用受限表达式访问声明输入，不执行任意 JavaScript。AI 判断输出需结构化校验，无法判断进入人工待办。
- 并行默认 Join all；必需分支失败则阻止该 Join。可选分支必须声明缺失输出处理方式。
- ForEach 固定输入清单快照、稳定 itemKey、最大并发和单项重试策略。默认全部必需项成功后交付；部分成功交付需配置并标记缺项。
- 修订/重试使用新的尝试或运行修订，限定次数；不要靠画布任意回边制造无限循环。
- 子流程声明入口/出口，内部节点不泄漏未声明端口，展开可追踪对应 TaskRun。
- 嵌套深度、并发数、工具调用数和运行预算均有上限，超限进入可解释状态。

## 10. 第三期主 Agent 动作边界

主 Agent 读取目标、运行摘要、产物摘要和显式相关内容；不默认注入全部子任务聊天。

对流程的动作使用结构化提案：添加任务、选择模板、修改配置、建议输入绑定、请求重试、请求用户决策。所有提案经过契约校验和影响预览。

生成流程步骤：需求澄清 → 选模板/能力 → 生成定义草稿 → 静态校验 → 展示依赖及人工介入位置 → 用户保存并运行。

在本次用户设定的自主范围内，可执行已有流程中的允许动作；改变交付目标、改动已确认成果、超出预算或扩大工具范围时创建待办。动态新增子任务也必须有完整输入输出契约，不能直接进入不可见的后台队列。

## 12. 迁移与发布

1. 特性开关默认关闭开发中功能；老项目保持当前运行路径。
2. 新建表采用向前兼容迁移，迁移前保留数据库与项目备份，失败不得展示半完成项目。
3. 旧项目的 workspaceProfile 缺省解释为兼容现有显示，不删除历史节点。
4. 老对话不自动转换成“已确认产物”；用户选择需要提炼的内容。
5. 老运行记录保留；导入到新视图时标记为历史记录，缺少信息不伪造。
6. 新旧运行路径对同一节点设置执行所有权，避免同时运行；新流程内节点由 FlowRuntime 控制。
7. 导入导出加入 manifest 与版本迁移。模板包不带密钥/媒体/会话；项目包可选择带产物和历史，必须重映射所有引用，包括 tldraw、nodeResult、导演台及新产物依赖。
8. 导入检查路径穿越、资源大小、缺失文件和不支持版本；经过临时目录与事务成功后再展示。
9. 旧版本应用对含新格式项目应拒绝不安全写入；回滚使用备份或明确的兼容导出，不能承诺旧程序无损读取新格式。
10. 发布产物记录源码提交、构建时间、应用版本和协议版本，关于页可见。同步检查桌面快捷方式与实际安装目录，避免重现启动旧 UI 的问题。

## 13. 验证策略与技术风险

这里只规划后续验证，本次未执行测试。

- 单元：状态转换、重复命令、输入绑定、版本依赖、上下文预算与合法配置组合。
- 集成：数据库迁移、人工确认事务、outbox 重放、事件补取、导入重映射。
- 执行一致性：桌面与新宿主的同一契约输入、所有输出端口、错误、取消、多输入顺序和媒体来源。
- 恢复：生成前/后、等待人工、确认后恢复前、事件发送前等故障窗口。
- UI：会话归属可见、不串话、修改旧版本冲突提示、隐藏节点不破坏旧项目。
- 回归：按仓库规范进行节点契约检查及完整 verify；真实付费模型另设小额度样本和清晰预算。

最大风险是重复执行副作用、两套调度状态冲突、运行中修改配置、上下文串用与数据库/文件不一致。优先解决这些问题，再增加主 Agent 自主性。
