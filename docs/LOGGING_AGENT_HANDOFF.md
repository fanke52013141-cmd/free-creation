# 日志系统开发 Agent 任务说明

本文件可直接作为开发任务交给另一个 Agent。日期：2026-10-04。

## 1. 你的开发目标

实现本项目已制定的日志规范与实施计划，使一次操作能从流程/节点，追踪到模型请求、远端任务、媒体落盘和项目保存。日志独立保存，失败后能够导出安全、可读的诊断包；新增功能有可执行的日志接入检查。

你有具体开发任务，不能只输出新的方案或增加零散console。按下列阶段实施，每阶段有可运行代码、测试、覆盖清单和交付记录。记录只完成了哪些阶段，不能把规范已写好等同于日志系统已实现。

## 4. 第一步交付：底座与两条完整链路（L01–L03）

### 任务A：统一事件与上下文（L01）

实现schema v1、事件声明、允许字段、安全序列化、错误归一化、诊断上下文。

要求：

- 保留旧runId、trace与nodeRun读写兼容；增加根trace、节点执行实例、请求、attempt和父子关联。
- 由公共调度/执行器负责开始与唯一终态。各功能仅补自己的实际阶段。
- 给现有trace/info/error/phase做明确适配；避免一口气修改所有节点契约。
- 类型化接口控制属性；任意原始错误/配置/响应不得直接序列化。
- logger失败不改变业务执行；最小mock没有诊断接口仍可测试，桌面路径注入则应有契约断言。

建议新增测试：schema、上下文、字段白名单/安全序列化、公共生命周期；文件名由最终模块结构决定。更新已有runRecord与执行器测试，验证旧记录仍可读。

完成标准：构造一次3节点运行能看到共同根trace和独立执行实例；非法字段被拒绝/安全丢弃；失败/取消无重复终态；敏感fixture不进入输出。

### 任务B：独立事件保存（L02）

实现main统一writer、异步有界队列、session分片JSONL、轮转/限额、日志健康状态与安全查询。

要求：

- 采用规范第9节默认值，不把提高nodeRun上限当作独立存储。
- 使用getDataDir下diagnostics目录、session隔离、CANVAS_DATA_DIR测试临时目录。
- 区分已接收、已入队与已落盘；不能把IPC回执当持久化保证。
- 慢盘、拒写、磁盘满、尾部残缺、队列溢出、正常退出flush超时均有明确定义。
- 清理只作用于诊断目录；不得读取/删除项目或媒体以释放日志空间。
- 继续保留electron-log应用摘要；按规范说明其目录与新事件目录不同。

建议测试：writer轮转、队列限制、拒写/恢复、坏行读取、多实例隔离、退出flush与容量清理。使用可注入时钟/文件写入接口获得确定性，避免依赖真实磁盘满。

完成标准：画布没有保存也能读到已落盘事件；日志故障不改变业务结果；队列有界；导出可指出丢失/截断；重启能安全读有效前缀。

### 任务C：对话和生图贯通（L03）

链路1：对话节点→能力解析→IPC→流式模型请求→首片/完成或失败→输出校验。

链路2：生图节点→提交→任务接受/状态→下载→媒体落盘→输出校验→关联项目保存。

要求：

- 沿shared契约、preload、renderer gateway、main gateway传递诊断上下文，main再次校验。
- 请求ID与远端任务ID区分；请求重试保持逻辑requestId并增加attempt；新的用户重跑开启新trace。
- 首片和结束可记录统计，token正文与reasoning不能记。
- 区分远端成功、下载成功、媒体入库成功与画布保存成功。
- 若自动保存合并多个节点变化，用关联字段连接它们，不能强行归给最后一个节点。
- 用确定性fixture验证401、429、超时、流中断、取消竞争、下载/落盘失败；真实模型验收记录与模拟分开。

完成标准：一次失败可以按ID找到真实失败阶段；“远端成功但本地下载失败”不会被日志误导为重新提交生成；对话/生图均可读到完整事件，不只是nodeRun摘要。

首个里程碑只在A/B/C都验收后标完成。若交付被中断，留下明确阶段和失败测试，不把部分能力命名为“完整日志系统”。

## 5. 第二步交付：全面覆盖、导出和防遗漏（L04–L06）

### 任务D：覆盖清单逐项迁移（L04）

按LOGGING_COVERAGE每个业务域推进：视频恢复、音频、图片编辑、本地处理、迭代、代码Worker、保存恢复、导入导出、素材库、模型验证、应用异常退出。

每迁移一项提交：实际阶段事件、关联/错误映射、成功和主要失败测试、清单验收记录。视频已有任务恢复要复用；日志不得触发重复提交。外部进程输出、用户代码和路径需要安全处理。

### 任务E：扩展已有运行中心和诊断包（L05）

在现有UI增加流程时间线及请求/任务/保存阶段；支持按范围读取独立事件，展示缺失、过期和截断。

导出manifest/events/summary/coverage，按规范25MiB上限、原子写入、二次脱敏；不默认打包数据库/项目/素材/main.log全文。旧单节点JSON导出兼容保留。

完成标准：开发Agent仅凭包可定位错误边界并知道证据缺口；包中没有正文、Key、签名URL或用户绝对路径；不能宣称包包含足够资料逐像素重放生成。

### 任务F：自动检查新增功能遗漏（L06）

完成事件schema、隐私、生命周期、IPC关联的测试门禁；对新业务裸console/直接logger旁路做增量检查。建立日志影响声明与变更匹配，纯样式文档可有依据地标no-impact，历史旁路需明确允许清单与迁移计划。

新脚本真实存在且通过后，再加入npm run verify和现有CI。不能只修改AGENTS/PR模板后说“自动门禁完成”；不能只扫描是否出现log字样判覆盖。

## 6. 必须遵守的边界

- 不记录API Key、原始请求/响应、提示词、聊天正文、reasoning、文档、媒体/base64、代码及完整签名URL。
- 不把日志用作业务事务成功凭证、任务恢复库或自动重试指令。
- 不在React组件绕过executor调用模型；不引入云端日志、账户或重新接Agent/CLI/MCP。
- 不破坏节点端口/输出协议；确需变更时完成契约版本、迁移与全量验证。
- 不吞业务异常，不用logger返回值代替模型/文件/事务结果。
- 不重新开发已有运行中心、视频恢复、失败重跑或另设一套模型解析。
- 不将别人的未提交代码、截图、测试产物混入本任务提交。

## 7. 验证与完成定义

每阶段先定向测试再运行适用门禁；节点/业务代码交付执行 `npm run verify`。桌面故障行为按计划A01–A18在隔离数据目录验收。

定向用例命令必须基于真正创建的测试文件，交付时写出实际命令/结果；本任务说明不提供假装已有的测试脚本。

每阶段交付回复至少包含：

1. 完成哪个阶段/哪些业务域，具体新增或复用了哪些入口。
2. 当前能追踪哪些ID和阶段，哪些路径仍未覆盖。
3. 成功、失败、取消、重试、恢复、拒写/脱敏的实际验证结果。
4. 如何在应用中查看或导出；样例采用假数据且标明路径。
5. 是否通过全量门禁，有哪些桌面/真实模型边界尚未验证。
6. 覆盖清单已更新；提交以可验收阶段拆分，提交备注准确说明现状。

完整任务完成必须同时满足：L01–L06交付；关键业务域清单有证据；A01–A18适用项通过；日志故障不改变业务；诊断包清洗完整；自动门禁能发现一个新增网络路径缺日志的示例。尚未实施部分继续保留待办，不能从文档中删除来伪装完成。
