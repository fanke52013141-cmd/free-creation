# 节点流（Workflow）规范与执行方案

2026-11-11 · 实施设计。现有实现与待开发范围见[交付备注](WORKFLOW_DELIVERY_NOTES.md)。

## 1. 产品目标与对象

用户把一段画布打磨成一个可重复调用的小能力。节点流发布后，可以像普通节点一样接在其他节点或节点流前后。调用方根据公开端口接线、根据版本选择实现、根据运行结果判断成功。内部实现可以独立演进。

| 对象 | 归属与生命周期 |
| --- | --- |
| 节点流 | 稳定 ID、名称、说明，聚合编辑稿和历史发布。重命名保留 ID。用户界面称「节点流」，先沿用已有 `composite` 节点类型、存储与操作标识。 |
| 编辑稿 | 独立可编辑的内部画布、公开端口与映射。保存后可恢复。保留基准版本和草稿修订号，以便检测并发覆盖。 |
| 发布版本 | 不可修改的画布与调用契约，固定所引用的节点流版本、节点契约版本和必要资产引用。沿用 `1.0 / 2.0` 的用户呈现。 |
| 画布实例 | 按节点流 ID 和固定版本引用发布内容，通过公开端口与外层画布交换数据。新插入默认用最新发布，已插入实例主动升级。 |
| 运行记录 | 一次固定版本调用，关联父子运行、步骤、实际结果、产物引用及失败阶段。 |

流程模板继续作为可复制、展开的画布内容。节点流的 API 指可组合的本地调用契约，GUI、CLI、MCP 复用本地执行宿主和业务规则。

## 2. 公开端口与执行规则

### 2.1 首次生成接口建议

1. 用所选子图的有效数据边识别起点和终点。没有内部上游数据边的是起点，没有内部下游数据边的是终点。坐标、创建顺序、名称和模型推测均不参与。单个孤立节点同时是起点和终点，多条分支按各自边界处理。
2. 起点的可接入输入端口和终点的业务结果端口形成候选。类型、Schema、必填性、基数从保存配置下的节点契约读取。一个 `many` 端口在界面显示一项，可接收多份有序数据。无输入端口的节点提供内部固定内容或资源。
3. 用户确认候选，可隐藏具备可运行前提的可选端口，也可显式公开某个中间端口。UI 标出来源节点与端口。每个公开端口具备稳定 ID 和明确映射。第一批采用一个公开输入绑定一个内部输入、一个公开输出绑定一个内部输出。同一内部输出可继续由普通数据边分发。
4. 全图检查必填输入是否有可用的内部来源、已公开映射或节点契约认可的固定输入。发现缺口时定位到节点和端口，允许补线、补固定输入或显式公开。按节点执行前置条件和运行数据再检查动态约束。

### 2.2 编辑与发布

- 保留已确认的接口。新增起点、修改布局和更换内部实现不会自动重写公开端口。删除内部目标或改变端口类型时，保留失效映射的提示，发布前要求重新绑定或明确移除。
- 端口 ID 与显示名称分离。重新绑定到同类型、同含义的内部端口，可以保留公开 ID。兼容预检比较 ID、类型、Schema、必填性、基数及实际连线，输出受影响的节点和边。样例回归检查结果含义与默认值等行为变化。
- `文本 → AI 处理 → 生图` 中，外部文本进入文本节点的 `in-text`，然后按原契约与节点正文合并并经 `out-text` 传递。正文属于内部画布快照。把外部值直接写成正文、只取第一份输入、由标题猜测目标均无法满足该规则。

### 2.3 调用与嵌套

- 运行先解析固定版本、有效依赖和输入。把真实类型的输入包交给内部映射端口，复用现有节点执行、Schema 校验和投影逻辑。每次调用拥有独立运行上下文，临时数据与运行结果不会改写编辑稿或发布快照。
- 内部步骤完成后，从明确映射的输出收集结果。缺少约定的必需输出时返回失败，禁止用上一轮输出冒充本轮结果。图片等媒体输出使用宿主可访问的正式产物引用。
- 节点流内可以包含普通节点和固定版本的节点流。发布与运行都检查直接或间接递归、嵌套深度和展开预算。依赖找不到时明确报错，不能自动改用最新版。
- 记录父子调用、内部失败节点、耗时和产物关联。对付费请求沿用现有确认、占用和重试语义。结果未知时先核对原请求，等待与恢复有实证后再开放相应能力。

## 3. 保存、发布与存量兼容

| 动作 | 规则 |
| --- | --- |
| 首次封装 | 从选区复制节点、内部边、布局、正文、配置、媒体引用和可适用的背景板，原画布继续独立编辑。首次发布 `1.0` 需要显式确认。 |
| 保存草稿 | 原子保存草稿及修订号。允许未接完的图，并显示问题。关闭重开恢复同一草稿。版本列表和正在运行的固定版本不随草稿更新。 |
| 发布新版本 | 基于明确的草稿修订校验接口、图、依赖和资源。在同一事务里分配版本并写入发布快照、更新最新发布指针。冲突返回明确结果，失败时保留草稿。发布成功后重复提交不得误增一版。 |
| 基于历史编辑 | 从选定快照创建工作副本。已有未保存改动时先确认。下一次发布使用新版本号。 |
| 升级实例 | 提供新旧接口差异及连线预检。用户确认后迁移兼容连线。取消或预检失败保留原实例与原图。 |
| 归档与删除 | 归档后隐藏默认发现入口，已绑定实例可按固定版本使用。物理删除前检查项目实例和发布版本的嵌套引用。 |

现有仓库允许同版本覆盖，且旧组合可能依赖原有输入处理。实施时先保存存量版本和实例实际绑定的内容，兼容读取旧 `1.0.0`，查清同主版本别名冲突后再迁移。历史发布的接口、ID 与旧运行语义保留。新发布按新规则校验。旧数据迁移、固定资产重映射和失败回滚使用隔离数据验证，导入导出排除 API Key。

## 4. 页面和交互

1. **首次封装**。主画布「保存节点 → 节点流」显示名称和接口建议，保存方式使用平面单选项。需要修改映射时展开输入输出详情。提交后可直接打开节点流。
2. **节点库与详情**。列表保留一个「编辑」入口。详情集中展示「信息」「输入输出」「历史版本」。主操作「编辑画布」，历史可查看并基于指定版本继续编辑。
3. **全屏编辑**。复用主画布编辑内核、节点库、节点设置、正文编辑、端口连线、拖动、背景板、复制粘贴、撤销重做和试跑。当前独立画布仅是起点，按主画布实际支持能力逐项验收。右上有「保存」「发布新版本」和关闭。关闭时有未保存内容，提供保存并关闭、放弃、继续编辑。
4. **发布预览**。展示基准版本、接口差异、引用版本和阻断问题。主操作复用主画布「运行」按钮的颜色、尺寸与状态。背景板工具顺序为横向、纵向、自动整理、圆形当前色。

视觉设计用同一个 Stitch 项目覆盖首次封装、节点流详情与全屏画布。以真实控件、长名称、窄屏和出错状态验收，布局设计沿用节点 UI 规范和公共组件。

## 5. 实施顺序与验收

| 批次 | 实施内容 | 退出条件 |
| --- | --- | --- |
| W1 文本调用闭环 | 从 `src/shared/composite`、`src/main/store/composite.repo.ts` 和现有组合执行器起步。明确协议版本、草稿和不可变发布。接通明确映射的文本传值、固定版本和嵌套引用。提供最小可操作的 GUI 路径及同包 CLI/MCP。 | 普通节点调用文本节点流并消费真实输出。外层节点流固定引用内层 `1.0`，内层编辑保存重开并发布 `2.0` 后，外层仍按 `1.0` 运行。验证没有公开接口自动重写、发布失败可回编辑和不兼容升级受阻。 |
| W2 完整画布与统一入口 | 共用主画布能力，统一封装、详情和全屏编辑，完成 Stitch 布局及交互。 | 在真实 Electron 中打开旧组合、增删节点、拖端口连线、修改原设置、撤销重做，保存关窗后恢复，发布新版本可在历史查看。核对主画布独立性。 |
| W3 多类型和版本生命周期 | 逐类验证图片、JSON、多值、多输出和媒体资产。实现实例升级、引用保护、嵌套限制及存量迁移。 | 类型和基数错误有确定结果，媒体产物可被下游节点消费，递归与超限明确拒绝，旧实例未升级前继续运行。 |
| W4 回归样例和运行可靠性 | 保存样例，比较版本行为。接通真实模型、失败定位、人工补交、受控重试与重启恢复。 | 有真实模型端到端证据。已完成步骤不会因恢复重复执行，未知付费请求可核对。 |

### W1 的首条验收路径

1. 创建可确定性运行的「文案整理 `1.0`」，声明文本输入与文本输出。验证有正文、无正文、未传可选输入及多值顺序，按节点契约断言结果。
2. 用普通节点输入调用它，把输出接给另一个普通节点，确认下游读到本次真实输出。再把它嵌入「标题整理 `1.0`」，通过外层端口运行。
3. 修改内层图并保存。关闭重开恢复草稿，验证旧发布仍可调用。发布 `2.0` 后再运行外层，确认它仍固定 `1.0`。同版本覆盖请求要被拒绝。
4. 构造一个删除公开输出或新增必填输入的版本。升级预检应列出受影响端口和现有连线，失败或取消后原实例仍可运行。W1 可先验证公共预检，完整 UI 放 W3。
5. 用 GUI、CLI、MCP 验证同一批数据的正式输出和错误。浏览器 mock 用于交互回归，真实桌面及外部进程用于验收调用。

每批遵循[节点契约](../../NODE_CONTRACT_SPEC.md)、[日志规范](../../LOGGING_SPEC.md)和[三入口一致性](../../AGENT_PARITY_SPEC.md)。交付时登记操作、契约兼容结论、日志覆盖、脱敏证据及剩余边界。后续 Agent 先做 W1，见[执行指令](WORKFLOW_AGENT_INSTRUCTIONS.md)。
