## 1. 基线复现（改动前）

| 现状 | 复现位置 | 实际行为 | 三入口已验证范围 |
| --- | --- | --- | --- |
| 文本如何送达 `in-text` | `src/renderer/src/composite/run-composite.ts` | 文本包只取 `packets[0]`；目标是文本节点 `in-text` 时直接 `updateShape({text})` **替换**正文，未走普通文本节点合并；非文本包被忽略，多值顺序未保留 | GUI 仅单元/组件级；CLI/MCP 无执行入口，只能发布/读取 |
| 草稿与发布是否分开 | `composite_drafts` / `composite_versions` | 表已分开，`saveCompositeDraft` 有 revision；但 GUI「保存并发布」一次完成，节点库「编辑」总是读已发布最新版本，不恢复草稿 | 仓储单测覆盖 revision；CLI/MCP 有 draft.get/save，未做 GUI 端到端 |
| 同版本发布是否覆盖 | `publishCompositeVersion` | 同版本不同摘要 **直接 UPDATE 覆盖**（2026-11-10 裁决），而 Agent 操作描述写的是“拒绝覆盖”，文档与行为不一致 | 仓储单测覆盖覆盖行为；CLI/MCP 契约描述与实现不一致 |
| 嵌套是否解析到固定版本 | `buildCompositeManifestFromGraph` / `run-composite.ts` | 运行使用组合节点 config 内嵌的 manifest 快照，天然固定；但构建 manifest 时未登记 `capability` 依赖，发布预检无法检查嵌套存在性/环/预算，也没有“内层发 2.0 后外层仍 1.0”的测试 | 无 |

结论：W1 必须先修正文本送达与发布不可变，补齐草稿恢复/固定嵌套依赖，并用同一业务实现覆盖 GUI/CLI/MCP。

## 2. 本批完成项

### 2.1 公开端口与映射

- 新增可选的 `runtimeVersion`：缺省=1（历史语义），新封装写 2。`schemaVersion` 仍为 1，避免破坏旧客户端。
- 公开端口继续保存稳定 `id`、方向、类型、Schema 引用、必填性、基数和 `targets/source` 精确映射。
- `buildCompositeManifestFromEditor` 替代“保存时重新推导 + 按数组下标重排内部 ID”：
  - 内部节点 ID 来自创建时写入 `meta.compositeNodeId` 的稳定值，新节点用随机稳定 ID；
  - 已确认的公开输入/输出原样保留，不因增删节点自动重写；
  - 映射失效保留原节点/端口并给出可定位提示，发布校验阻断；
  - 依赖按当前内部图重建，嵌套节点流登记固定 `capabilityId@version`。
- `validateCompositeManifest` 继续做全图必填缺口、类型、基数、DAG、依赖与预算校验；发布前执行。

### 2.2 文本进入 `in-text`

- 运行语义 2：外部文本包作为**虚拟上游文本节点**接入契约声明的目标端口，保留 `many` 的调用顺序（`connectOrder`），由普通 `textExecutor` 执行合并（`外部文本 + $$$ + 内部正文`）与 `out-text` 投影。不再直接改写正文。
- 可选输入缺失不注入、不报错；必需输入缺失返回 `INPUT_REQUIRED` 并带公开端口 ID。
- 未验证类型（图片/视频/音频/文件）给出明确 `INPUT_TYPE_UNSUPPORTED`；可接入的文本/JSON/媒体按统一规则创建虚拟源。
- 公开输出按本次运行的显式映射收集：文本/JSON 写入 `meta.nodeExtra`，媒体写 `meta.nodeResult`；缺少必需输出返回 `REQUIRED_OUTPUT_MISSING`，定位到公开端口、内部节点和端口。
- `projectCompositeOutputs` 只在 `nodeRun=success` 时暴露本次结果；失败运行不暴露旧值。`output.get` 已登记 `composite` 投影。

### 2.3 草稿、发布与固定嵌套

- 草稿保存保留 revision 乐观并发：冲突返回 `DRAFT_REVISION_CONFLICT`，不覆盖原草稿。
- 发布不可变：
  - 同版本同摘要幂等；
  - 同版本异摘要 `VERSION_IMMUTABLE`；
  - 新版本必须大于最新发布 `VERSION_NOT_NEWER`；
  - 可选 `expectedRevision` 校验发布基于的草稿修订，失败保留草稿。
- 全屏编辑拆成「保存草稿」与「发布新版本」；编辑时优先恢复草稿，关闭重开仍可继续；发布默认下一个主版本。
- 嵌套节点流在构建 manifest 时登记 `{kind:'capability', id, version}`，发布校验检查存在性、环、深度与展开预算；运行继续使用 config 内的固定快照，不会自动改用最新版。
- 升级公共预检 `planCompositeUpgrade` 比较端口 ID、类型、Schema、必填性、基数，并结合项目实际连线输出受影响节点/边；新增必填输入也阻断。CLI/MCP 暴露 `composite.upgrade.preview`，完整升级 UI 留 W3。

### 2.4 兼容与迁移

- `composite_versions` 旧行不改写；缺省 `runtimeVersion` 的旧发布按语义 1 运行：文本仍直接替换正文、输出仍取首个媒体结果。
- 旧模板、旧组合实例、旧草稿保持可读；所有新字段为加性，Agent 输入 Schema 仅新增可选字段和一个新操作。
- 数据库 M28 为 `composite_runs` 加 `parent_run_id` / `failure_phase` / `output_summary`，只存 ID、阶段和端口种类，不存正文。
- 同版本覆盖从“允许”改为“拒绝”是**有意的行为修订**：此前覆盖会让已绑定实例的固定版本内容漂移；旧数据不迁移，只约束后续发布。兼容结论：旧版本可读可运行，新发布遵循不可变规则。

### 3.2 GUI / CLI / MCP 路径

- GUI：节点库「编辑」恢复草稿 → 全屏画布「保存草稿」/「发布新版本」；节点库「新版本」从最新发布创建下一个版本；主画布插入的实例保存固定 manifest 快照。
- CLI/MCP：
  1. `composite.draft.save` / `composite.publish`（可带 `expectedRevision`）；
  2. `composite.validate`；
  3. `composite.upgrade.preview`（项目内实例的实际连线）；
  4. 执行复用 `graph.patch` 插入固定版本实例、`node.execute` + `run.wait` / `output.get`（`composite` 已登记确定性投影）。
- 真实桌面证据（2026-11-11，隔离数据目录，退出后清理）：启动 Electron（`--local-agent-access`）后由 CLI 完成
  `project.create` → `project.open` → `composite.publish 1.0` → 同版本覆盖返回 `VERSION_IMMUTABLE` →
  `graph.patch` 插入 composite 实例 → `node.execute` single → `run.wait` completed → `output.get` 得到
  `out-polished.text = "内部说明"`；另跑一个可选输入未传、正文为空的「标题整理 1.0」，
  `run.wait` failed，`composite.run.list` 返回 `errorCode=REQUIRED_OUTPUT_MISSING`、
  `failurePhase=output`、`parentRunId` 与 `instanceNodeId` 可定位。MCP stdio 工具目录包含
  `composite_upgrade_preview`，`composite_validate` / `composite_get` 返回与 CLI 相同的契约结果。
  证据脚本为临时隔离验收脚本（`qa/w1-desktop-acceptance.cjs`，qa 目录不入库），输出留档 `qa/w1-desktop-acceptance.log`；窗口标题带 `[TEST]` 标识，关闭后删除临时目录。
- GUI 本身尚未用真实鼠标点击走完「保存节点 → 节点流」和「草稿恢复 → 发布 2.0」；该边界在回报中单列，不把 CLI/API 调用当作 GUI 点击验收。
