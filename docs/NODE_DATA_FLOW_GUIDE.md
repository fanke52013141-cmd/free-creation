# 节点数据流与代码节点用法

本文用用户视角说明常见节点各自负责什么，以及端口传值的形态。完整的机器契约仍以
[`NODE_CONTRACT_SPEC.md`](../NODE_CONTRACT_SPEC.md) 为准。

## 常见节点怎么选

| 节点     | 主要用途                                                 | 什么时候选它                         |
| -------- | -------------------------------------------------------- | ------------------------------------ |
| 数据处理 | 透传一个值、从 JSON 取字段、把值套进文本模板             | 只需要简单转换，想用表单操作         |
| JSON     | 解析或格式化通用 JSON，方便查看和手工编辑                | 数据结构还没有专用 Schema            |
| 结构数据 | 编辑 JSON 模板、替换连线占位符，并按 Schema 校验         | 下游要求稳定字段和数据格式           |
| 分镜板   | 编辑 `shots` 列表，并输出完整分镜 JSON 与摘要            | 内容是一组镜头，需要逐行管理         |
| 代码     | 用 JavaScript 完成自定义转换，或把多项处理合在一个函数中 | 表单节点表达不了，且用户愿意维护代码 |

数据处理和 JSON 节点能做的转换，大多也能用代码实现。例如 `JSON.parse(args.text)` 可以解析文本，
`return args.json[0].title` 可以取字段。不过专用节点保留了可视化编辑、错误提示和 Schema 校验，
一般操作优先用专用节点；遇到复杂逻辑时再用代码。代码节点不会让一个普通 JSON 节点自动变成
“按任意业务结构编辑”的界面。

JSON 节点的取值顺序是：有上游 JSON 时优先用 JSON；没有 JSON 时才解析 `in-text`；两类都没有时
使用节点内已编辑的 JSON 正文。JSON 与文本同时连接时，文本不会参与本次运行。

## 用一个小创作例子理解 JSON、数据处理和结构数据

先记住三个角色：

- **JSON 节点**像一个通用数据盒子：把合法 JSON 放进去、解析出来、查看或格式化。它不规定数据必须有哪些业务字段。
- **结构数据节点**像一张带规则的表单：正文仍然是 JSON，但选择 Schema 后会检查必填字段和字段类型，并把这套规则作为连线契约告诉下游。
- **数据处理节点**像一个小工具：对一个输入值做原样传递、取一个字段，或把整个值填入一段文本模板。

可以把 Schema 理解成“这类数据的填写规则”，把 JSON 理解成“本次填写的具体内容”。Schema 本身不会被塞进 JSON 正文；节点输出仍是 JSON 值，只是端口声明了这份 JSON 应符合哪套规则。

### 先看三个节点的区别

| 节点 | 你在里面做什么 | 输出是什么 | 适合的情况 |
| --- | --- | --- | --- |
| JSON | 粘贴/编辑 JSON，或把上游 JSON/JSON 文本解析并格式化 | 原来的 JSON 值；多个 JSON 输入时变成一个数组 | 临时数据、调试、还没有专用字段规则的数据 |
| 数据处理 | 选“原样传递 / 提取字段 / 字符串模板”之一 | 原样模式保留输入值；提取模式输出字段值；模板模式输出文本 | 只需做一次很小的转换 |
| 结构数据 | 选 Schema，编辑 JSON 正文，可引用上游字段 | 通过该 Schema 校验的 JSON | 希望角色、场景、提示词、镜头等下游都认识同一套字段 |

### 数据处理节点：3 种操作、6 种固定值类型

数据处理节点只有一个输入端口 `in-value` 和一个输出端口 `out-value`。它一次处理**一个值**；端口本身不会因为类型下拉框而变成六种不同端口。界面里的固定值类型有 6 种：

| 类型 | 例子 | 实际值 |
| --- | --- | --- |
| 任意 `any` | `林岚`、`42`、`true`、`{"name":"林岚"}`、`[1,2]` | 能解析成 JSON 的内容按 JSON 解析；否则作为文本 |
| 文本 `string` | `林岚` | 文本 `林岚`，不会当作 JSON 数字或布尔值 |
| 数字 `number` | `42` | 输入内容 `42` 被 JSON 解析成数字 42 |
| 布尔 `boolean` | `true` | 输入内容 `true` 被 JSON 解析成布尔值 true |
| 对象 `object` | `{"name":"林岚"}` | JSON 对象 |
| 数组 `array` | `["雨巷","夜晚"]` | JSON 数组 |

**一个容易误会的细节：**类型下拉框只用于没有可用连线值时解释节点里的“固定值”，不会验证或转换已经连进来的值；当前执行器对 `number`、`boolean`、`object`、`array` 也只是尝试解析 JSON，没有再检查解析结果是否真的是所选类型。因此，选了“数字”却填 `hello`，仍可能退回成文本，不等于强制类型检查。需要可靠字段规则时，应使用结构数据节点。

数据处理的 3 种操作如下：

1. **原样传递**：输入是什么，输出就是什么，类型也不变。例如连入 JSON 对象 `{ "name": "林岚" }`，`out-value` 仍是这个 JSON 对象；连入文本，输出仍是文本。它不会自动把对象拆成字段。
2. **提取字段**：只接受 JSON 输入，在“字段路径”填字段名，例如 `name`；若输入为 `{ "name": "林岚", "appearance": "短发" }`，输出 `林岚`，并成为文本。若提取到数字、布尔、对象或数组，则作为 JSON 输出。路径可以用点号逐层进入对象，例如 `profile.name`；当前不支持数组下标路径。路径不存在会运行失败。
3. **字符串模板**：模板里的每个 `{{value}}` 都替换成**整个输入值**，结果永远是文本。例如输入 `林岚`，模板 `主角：{{value}}，正在寻找失踪的朋友。` 输出 `主角：林岚，正在寻找失踪的朋友。`。若输入是对象或数组，会先把整个对象/数组序列化成 JSON 文本；它不会像结构数据节点那样逐字段替换。

例如，把下面的角色对象连到数据处理节点：

```json
{
  "id": "character-linlan",
  "name": "林岚",
  "description": "雨夜里坚持追寻真相的人",
  "appearance": "深色风衣，短发"
}
```

- 选“原样传递”：`out-value` 是完整角色对象。
- 选“提取字段”，路径填 `name`：`out-value` 是文本 `林岚`。
- 选“字符串模板”，填 `人物简介：{{value}}`：输出是包含整段 JSON 的文本，不只是名字。若只想要名字，先用“提取字段”，再接一个模板节点。

### JSON 节点什么时候用？

JSON 节点不要求“角色必须有 name”或“场景必须有 location”，只负责通用 JSON 的解析、编辑和查看。它可以装 JSON 的任意合法根值，包括文本、数字、布尔、对象、数组和 `null`。

- 接一条 JSON 连线：原值保持原样；接多条 JSON 连线：按连线顺序收成数组。
- 只接文本：尝试把文本解析成 JSON；比如文本 `{"name":"林岚"}` 会变成对象，普通文字 `林岚` 不是合法 JSON，会失败。
- 两种输入都没有：使用节点正文里的 JSON。
- JSON 节点不替你检查业务字段。 `{ "name": "林岚" }` 和 `{ "anything": 7 }` 都可以是有效通用 JSON。

### 结构数据节点和内置结构

结构数据节点选择一套 Schema，然后用自己的 JSON 正文创建一个值。连接到 `in-context` 的 JSON 可通过 `{{input[0].字段名}}` 明确引用；下标来自该输入端口的连线顺序。`{{input[0]}}` 如果单独占满一个 JSON 字符串值，会把整个对象/数组原样放进去。连接到 `in-text` 的文本用 `{{text}}` 引用。节点只看这些明确声明的输入，不会在画布上自动寻找某个叫“角色”的节点。

下面用“林岚在霓虹雨巷追查线索”串成一条完整例子。依次放置并选择对应结构：

**1. 角色设定 — `character.profile@1`**

必填字段是 `id`、`name`、`description`；`appearance`、`persona`、`voice`、`tags`、`referenceImageIds` 可选。

```json
{
  "id": "character-linlan",
  "name": "林岚",
  "description": "雨夜里坚持追寻真相的人",
  "appearance": "深色风衣，短发",
  "persona": "冷静、敏锐，不轻易相信别人",
  "tags": ["主角", "记者"]
}
```

`id` 是稳定识别这名角色的键；`description` 是下游写提示词时最常用的人物描述。`referenceImageIds` 存的是项目媒体资产 ID 列表，不是图片内容本身。

**2. 场景设定 — `scene.definition@1`**

必填字段是 `id`、`name`、`description`；`location`、`timeOfDay`、`mood`、`tags`、`referenceImageIds` 可选。把角色的 `out-json` 接到场景的 `in-context` 后，可以这样编辑场景正文：

```json
{
  "id": "scene-neon-alley",
  "name": "霓虹雨巷",
  "description": "{{input[0].name}} 穿过雨夜的霓虹街巷，寻找失踪的朋友",
  "location": "老城区窄巷",
  "timeOfDay": "午夜",
  "mood": "潮湿、紧张",
  "tags": ["雨夜", "霓虹"]
}
```

运行后，`description` 会变成“林岚 穿过雨夜的霓虹街巷，寻找失踪的朋友”。模板正文会保留占位符不被覆盖，所以修改角色名字后再次运行，场景会重新引用新名字。

**3. 镜头定义 — `shot.definition@1`**

必填字段是 `id`、`scene`；`dialogue`、`sound`、`camera`、`duration` 可选。把场景输出接到镜头的 `in-context`：

```json
{
  "id": "shot-01",
  "scene": "{{input[0].description}}",
  "dialogue": "林岚：那份记录一定还在这里。",
  "sound": "雨声、远处车流",
  "camera": "中近景跟拍，人物停在巷口",
  "duration": "5s"
}
```

这个 Schema 描述**一条镜头**，不是整张分镜表。

**4. 分镜列表 — `storyboard.shots@1`**

把单镜头装进 `shots` 数组，再接到分镜板。一个简单形式是：

```json
{
  "shots": [
    "{{input[0]}}"
  ]
}
```

这里 `{{input[0]}}` 整项引用上一步的镜头对象，运行后会成为真实对象。多个镜头就把多个镜头对象放进 `shots` 数组；分镜板会把它们呈现为可编辑的多行镜头。该 Schema 要求根值是对象且 `shots` 是数组；镜头对象中的 `id`、`scene`、`dialogue`、`duration`（如果提供）要是字符串。

### 你说的“分析列表”是哪一种？

当前内置 Schema 没有叫“分析列表”的选项。若你指的是界面里的**分镜列表**，它是上面的 `{ "shots": [...] }`，专门交给分镜板编辑；若你指的是**对象列表**，它是 `list.items@1`，根值本身就是对象数组，例如：

```json
[
  { "id": "shot-01", "scene": "雨巷里的人物回头" },
  { "id": "shot-02", "scene": "人物走入巷口" }
]
```

对象列表要求每一项都是对象，适合接到循环节点的 `in-list`，让后续子流程逐项处理。若你的意思确实是“分析结果列表”，目前可以先用对象列表并自定义每项字段，例如 `{ "id": "finding-1", "claim": "...", "evidence": "..." }`；这不会自动产生分析内容，只是规定和传递分析结果的形状。

### 提示词包 — `prompt.bundle@1`

提示词包把“要生成什么”以及“希望如何生成”放在一个可校验对象里。必填字段只有 `prompt`；`negativePrompt`、`style`、`aspectRatio`、`seed`、`referenceImageIds` 可选：

```json
{
  "prompt": "林岚在霓虹雨巷中寻找线索，回头望向远处车灯",
  "negativePrompt": "模糊，文字水印，重复人物",
  "style": "35mm 胶片，浅景深，低饱和青橙色调",
  "aspectRatio": "16:9",
  "seed": 42,
  "referenceImageIds": []
}
```

把它连到生图/视频节点的“提示词包”端口。当前图像/视频执行会读取 `prompt` 和 `style`；其余字段会保留在结构数据里，但当前执行器未必会把它们作为生成参数发送给模型。图片等媒体仍通过媒体端口传资产引用；`referenceImageIds` 只是 ID 列表，不会把图片二进制塞进 JSON。

**选择口诀：**只想存/看一坨通用 JSON，用 JSON；只想对单个值做小转换，用数据处理；希望明确字段并让系统替你校验，用结构数据；如果数据要一行一项地编辑，用分镜板；如果数据要逐项跑流程，用对象列表加循环。

## “多值”与“数组”是两回事

- 一条 JSON 连线可以传对象，也可以传数组。比如 `[1, 2]` 是**一个** JSON 值。
- 输入端口设为 `many`，表示可以接多条连线；运行器按保存的连线顺序保留输入数据包。JSON 和媒体输入按序组成数组，单个 JSON 数组仍保持为其中一项；多值文本输入则按 `\n$$$\n` 合并成一个字符串。
- 图片、视频、音频和文件端口传的是资产引用（类型、资产 ID、路径和 MIME），不是像素或二进制。
- 多张图片连到生图节点的 `in-images` 后，执行器得到的是有序图片引用数组；这时不必先把图片伪装成 JSON。图片拆分的 `out-images` 是一条 JSON 列表，每个条目都带有 `kind: "image"` 和图片资产引用，可连接到循环的 `in-list`；再把循环的 `out-item` 接到图片端口，就会在每轮传入当前那张图片。普通列表条目仍作为 JSON 传递。
- 一个输出端口可以连到多个下游。输入端口的 `many` 不控制输出能连几条线。

## 代码节点的输入和输出

代码在本地 Web Worker 运行。Coze 风格入口如下：

```js
async function main(args) {
  return { caption: args.shot.scene, length: args.shot.duration }
}
```

输入侧固定的便捷字段：

- `args.text`：`in-text` 收到的文本合并成一个字符串。
- `args.json`：`in-json` 收到的 JSON 值列表。若其中一项本身是 JSON 数组，列表里该项仍是一个数组。
- `args.images`、`args.videos`、`args.audios`、`args.files`：所有媒体输入的资产引用列表；每项是 `{ kind, mediaId, mediaPath, mime }`，不是媒体二进制。
- 在输入参数表中声明的字段：例如 `shot: object / one` 生成 `args.shot`；`references: image / many` 生成
  `args.references` 图片引用数组。`many` 每个值一项，即使某项 JSON 本身又是数组，也不会自动压平。
- `camera / one` 参数传入的是符合 `previs.camera@1` 的机位对象；多值机位参数会成为机位对象数组。

输出侧：

- 单输出兼容模式把 `return` 的值写到一个命名端口，并按配置类型检查。
- 多输出模式中，配置表的每一行对应一个独立端口。代码返回对象的同名字段会映射到该端口；
  例如声明 `caption: string` 和 `length: number`，就返回 `{ caption: "...", length: 3 }`。
- 同类型字段可以有多个端口，因为它们是不同的函数字段；其它节点仍使用 `many` 输入口承接多条同类连线。
- `camera` 输出字段必须返回符合 `previs.camera@1` 的对象，之后可连到 3D 预演台的机位输入。
- 图片等媒体输出必须引用本节点实际收到的资产。代码节点不能读取图片像素或凭空创建文件；
  要编辑媒体时请使用对应媒体节点。

代码 Worker 不提供 Node/Electron API、动态模块或网络访问。代码只处理传入数据，工具库 `_` 和 `dayjs`
是离线轻量实现。

这个输入输出模型和 Coze 开源工作流的“命名字段映射”思路接近：Coze 节点以字段名接收输入 map、再返回字段名对应的输出 map；这里把代码节点参数和返回对象字段直接映射到有类型的画布端口。运行方式不同：Canvas Studio 代码使用本地 JavaScript Worker；Coze Studio 仓库提到其代码节点使用 Python 执行环境。可以沿用 Coze 的“先声明字段、再连线、代码按字段名取值”的操作习惯，但不能直接照搬语言、依赖库或执行环境。[Coze 工作流节点开发说明](https://github.com/coze-dev/coze-studio/wiki/11.-Add-new-workflow-node-types-%28backend%29) · [Coze Studio 仓库](https://github.com/coze-dev/coze-studio)

## 分镜板表格

分镜板按所有镜头对象中出现过的字段动态生成列。每行仍对应一个镜头；原始 JSON 的额外字段（例如
`camera` 或 `sound`）会保留并能编辑。`id` 是稳定内部键，显示但不可直接改。JSON 编辑入口仍可用于
一次性编辑整份数据。

## 循环与批处理

当前节点叫“循环”：把列表逐项送进循环体，等待当前项完成后再运行下一项；支持单项失败、重试和断点恢复。
这与 Coze 的“批处理”是不同运行模式：Coze 批处理按并发数分批运行整个处理体，循环则表达逐项控制流。
因此这里把顺序执行的节点称为“循环”；要加入并行批处理，应单独呈现并设置并发数、失败策略、取消行为和结果排序。
可参照 [Coze 批处理节点说明](https://docs.coze.cn/guides_batch_node) 和 [Coze Studio 复合节点实现说明](https://github.com/coze-dev/coze-studio/wiki/11.-Add-new-workflow-node-types-%28backend%29)。
