# 方案三：代码冗余与冲突审查方案

目标：识别没有价值的旧代码、重复实现、矛盾规则和无效测试，同时保留仍承担旧项目兼容的必要逻辑。本方案首先产出有证据的清单；扫描命中不等于可删除，也不等于已确认缺陷。

基线和范围见 [执行总览](./00-执行总览.md)。以方案一基线测试保证行为，以方案二验证清理后用户任务没有倒退。

**一、先划定源码、产物与历史资料**

| 对象 | 审查方式 | 判定原则 |
|---|---|---|
| `source/src`、`source/packages` | 主代码审查范围 | 根据真实入口、依赖、执行路径判断使用状态 |
| `source/test`、`source/scripts`、配置/锁文件 | 测试和构建链审查 | 核对package脚本、CI、测试收集范围、运行路径 |
| `source/resources` | 运行资源、Python推理、许可、模板 | 不因TS静态引用缺失判为无用；检查打包和运行时路径 |
| `source/docs`、根规范 | 文档一致性审查 | 区分强制规范、当前说明、讨论稿、历史归档 |
| 根目录 `current/resources/app`、`resources/app`、`voice-design-node-build`、`build-video-no-playhead`、`previous-build-*` | 构建/历史副本盘点 | 先确认启动、回退、打包依赖；重复文件不等于重复执行代码 |
| `source/out`、`dist`、`artifacts`、`outputs` | 构建和证据 | 排除业务重复率；旧审计证据不擅自删除 |
| `node_modules` 与上游vendor | 依赖边界 | 不纳入自研代码重复率，另做打包/来源清单核对 |

第一步记录工作树未提交/未跟踪内容与实际运行进程路径。只读扫描不需要清空工作区。整理历史安装副本是单独维护任务，不在此次审查中自动删除目录。

**二、建立实际调用链与规则归属**

逐个核心节点画出可追踪链：

```text
创建入口/NodeTypeSpec/resolvePorts
  → Body/Settings 与统一运行入口
  → 输入收集/契约校验/运行器
  → shared executor（必要时经 renderer 转导出）
  → GatewayClient/renderer adapter/IPC
  → main model-host/model-runtime 或本地媒体服务
  → 结果写回/emitArtifact/SQLite/文件
  → projectOutputs/下游消费/保存恢复
```

每条链记录文件与符号，不只记录目录。确认真正的执行入口后，才能决定是否合并适配器或删除兼容分支。

| 规则 | 应核对的一致性来源 | 高风险冲突 |
|---|---|---|
| 端口身份与schema | Spec + resolvePorts + shared schema +迁移 | 静态快照和运行时端口不同，旧边仍指不存在端口 |
| 默认值和限制 | shared config parser + UI控件 +主进程校验 | 前端允许64×64，底层只允许64格；秒/毫秒、百分比含义不同 |
| 输入优先级 | inputs helper + executor + UI说明 | 文档说合并，执行器覆盖；上传和连线取值不同 |
| 模型选择 | 功能绑定/能力解析 +实际请求+UI | 新featureKey路径和旧modelKey路径各选不同模型 |
| 运行状态 | engine/store/runRecord +节点就绪态+回调 | done/success/skipped/cancelled映射漂移，迟到响应改写取消 |
| 输出有效性 | executor结果+projectOutputs+读取运行记录 | 失败仍投影旧值；配置结果双写导致重开显示旧数据 |
| 媒体物化 | emitArtifact+media repo+project store | 一个回调生成多份资产；临时文件被当正式结果 |
| UI基础组件 | NodeCardView、共享控件/样式、节点Body | 各节点各写一套运行按钮、下拉、Tooltip、拖动/滚动规则 |
| 数据存储 | props.config/text 与 meta.nodeRun/nodeResult | config残留result兜底覆盖新meta，迁移重复执行 |

**六、冲突审查的四步法**

对每项疑似矛盾，按下列顺序形成可复核结果：

1. **列两端事实**：文件A/符号/规则与文件B/符号/不同规则，例如UI上限与parser上限，附行号或片段。
2. **建立最小反例**：同一输入在两条入口分别执行；确定性case比较值/调用次数/输出类型，模型case用同一个stub响应排除随机性。
3. **确定权威规则**：强制契约与产品任务优先；若文档本身过时则登记待决策，不能因为一处实现更方便就更改协议。
4. **提出修复和回归**：明确保留哪个实现、删除哪些分支、迁移哪些调用方、旧数据如何读取；附一个失败前成功后的回归用例。

示例：语音合成换backend后端口集、设置面板和执行器不同步。分别生成两套实例端口→保存含旧边项目→切backend→检查就绪态和实际请求字段→重开复查。修复对象是端口解析/失效边策略，不应只隐藏UI报错。

**七、候选分类与删除门槛**

| 分类 | 条件 | 处理 |
|---|---|---|
| 保留 | 有当前消费者或明确旧项目兼容责任 | 补责任说明和行为测试；必要时改名使兼容范围可见 |
| 合并 | 两实现语义相同，差异无业务理由 | 选择现有权威实现，迁移调用方，差异测试证明无回退 |
| 修正文档/注释 | 代码行为与当前产品一致，旧说明误导 | 修订当前说明，历史文档标记日期/替代计划 |
| 可删除候选 | 静态/动态/配置/资源/兼容均无使用证据 | 形成具体文件/符号列表，核对删除范围后在独立变更中处理 |
| 暂缓 | 动态调用、旧项目覆盖或外部消费者未明确 | 保留并注明阻塞证据，禁止为了“减少行数”直接删除 |

达到删除门槛必须同时满足：①无可达业务路径；②不是迁移/旧快照读取必要逻辑；③不被资源路径/IPC字符串/脚本动态引用；④打包后真桌面启动与对应用户任务通过；⑤有可恢复变更记录。公共导出只被测试引用时，应确认测试是否在保护有效协议，而非直接认定生产不用即可删。

采用的审查技能 `C:/Users/Administrator/.codex/skills/code-review-and-quality/SKILL.md` 对重构后孤立代码写明：**“Ask before deleting”**。因此本方案默认先交付具体候选；未来若任务已明确授权这些具体清理，可在该授权范围内执行，否则到实际删除前展示清单确认。本次仅编制方案，不存在待批准的删除动作。

**八、整改顺序与每批验证**

| 批次 | 变更范围 | 验证 |
|---|---|---|
| A | 修正文档、过时注释、测试范围说明 | 文档链接、契约文档测试、快照对照；不能顺手改行为 |
| B | 删除已确认孤立符号/纯转导出层迁移 | 全引用复查、lint/typecheck、受影响单测、构建；入口/动态路径完整 |
| C | 合并配置解析、投影、请求/错误适配重复逻辑 | 同输入差异测试+所有消费者回归+旧快照读取 |
| D | 修复模型选择、状态、取消/重试或媒体入库双路径 | 请求计数/事件乱序/故障注入；桌面闭环及必要真实模型复测 |
| E | 清理共享UI样式/交互冲突 | 方案二五大类代表节点；DPI/缩放/焦点/滚动截图对比 |

每批只改一个逻辑主题，避免“统一重构+新功能+依赖升级”打包。纯行为保持重构不需要为行数写测试；涉及协议、数据或执行路径时必须有能抓回归的测试。批次完成后记录复杂度是否下降，而不是只看代码搬到了另一个文件。

**九、最终交付格式和验收**

每条审查发现填表：

```text
编号/分类/严重度/置信度：
问题：一句话说明具体重复或矛盾
位置：文件、符号、行号；与哪一处冲突
引用证据：静态调用、动态加载、配置/迁移、构建资源
可复现输入与行为差异：
用户或维护成本影响：
建议：保留谁、迁移谁、删哪些分支、为什么
验证：方案一/二caseId，旧项目样本，构建和打包
状态：待确认 / 已复现 / 已修复 / 复测通过 / 暂缓（原因）
```
