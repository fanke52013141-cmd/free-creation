# 方案一：全面代码测试方案

目标：逐节点验证“声明的契约 → 收到的值 → 实际执行 → 正式输出 → 下游消费 → 保存恢复”一致。范围、素材和结果格式见 [执行总览](./00-执行总览.md)。以下为待执行用例；现有测试名称只代表可复用入口，不代表已经完整覆盖或本轮通过。

**一、分层执行与证据要求**

| 层 | 方法 | 需要证明 | 不能据此声称 |
|---|---|---|---|
| L1 静态/契约 | TypeScript、注册校验、schema、快照 | 接口定义、类型、基数、版本、动态端口一致 | API 或桌面已可用 |
| L2 执行器 | Vitest，受控 gateway mock | 正常、错误、取消、输出投影和副作用 | 真媒体质量或上游服务可用 |
| L3 本地集成 | 真文件、图像引擎、FFmpeg、SQLite、GPU | 转换结果和落盘可核验 | 所有 UI 手势已通过 |
| L4 桌面 E2E | 真 Electron、真实连线、运行器、IPC | 点击到产物及保存重开闭环 | 未实际调用的供应商可用 |
| L5 真实模型 | 当前安全存储和模型网关，最小真实请求 | 模型、请求、下载、入库、下游可消费 | 所有参数组合和故障均已覆盖 |

先执行 L1/L2，修复阻断后进入 L3/L4，最后跑收费的 L5。错误响应、超时和重试上限尽量用本地 stub 注入，真实模型只承担真实适配验证。图片/声音按语义、可解码性、格式和引用验收，不要求生成文件哈希恒定。

**二、每个节点必须填写的契约卡**

从 Spec、`resolvePorts(shape)`、schema 和执行器共同提取，不仅复制静态 `ports`。

| 字段 | 必须记录 |
|---|---|
| 身份 | type、label、contractVersion、creatable/legacy、executionMode |
| 输入 | portId、type、schema/version、required、one/many、最大项数、稳定顺序 |
| 输入来源 | 静态值/正文/连线/上传的优先级或合并方式，无输入时行为 |
| 输出 | portId、type、schema/version、必填性、数量、模式互斥条件 |
| 执行 | executor 所有输入读取、网关能力、输出写回、取消、失败语义 |
| 状态 | props.config、props.text、meta.nodeRun、meta.nodeResult、额外结果与资产归属 |
| 持久化 | 输出重投影、来源 nodeId/portId/runId、迁移和导入重映射 |
| 测试 | 正常/边界/非法/失败/取消/重跑/依赖/保存的用例 ID 和证据 |

通用契约测试集，每个适用节点执行：

| ID | 操作 | 预期 |
|---|---|---|
| CON-01 | 遍历所有可创建节点，核对类型、注册、默认配置、executor、projectOutputs | 无缺失注册；有输出则有投影；版本与快照一致 |
| CON-02 | 遍历全部输入/输出，制造重复 ID、错误方向、缺失 schema | 注册/校验明确拒绝；不进入可用节点集 |
| CON-03 | 同类型、text↔markdown、json→text、text→json、媒体错类型、any、iteration 分别连线 | 只按契约允许；any 不免除运行时真实值校验；不隐式强转 |
| CON-04 | one 端口连两源；many 连 0/1/2/上限/超上限；多选批量连线包含一个非法项 | one 拒绝第二源；many 保持顺序；批量连接全部成功或整体拒绝 |
| CON-05 | 同 schema、不同业务 schema、不同版本、json.any 中合法/非法对象 | 连线兼容和运行时结构校验分别断言；通用 JSON 不绕过业务字段验证 |
| CON-06 | 分别使用固定值、连线值、两者共存，再断线；多源插入/删线/重连 | 值来源和合并顺序与说明一致；断线无幽灵输入；无未声明上传来源 |
| CON-07 | 切换 speech backend、structured schema、code 字段；AI 输出模式换三次 | UI、运行校验、输出投影同步；失效边明确提示/处理，不静默换端口 |
| CON-08 | 改标题、移动节点、改变创建顺序后重复运行 | 值仍按 nodeId+portId 寻址，与标题/空间位置无关 |
| CON-09 | 故意产生缺必填输出、错误类型、错误 schema、仅半套输出 | 不标成功，不向下游发布不合法结果；可选输出缺失是合法分支 |
| CON-10 | 成功→修改配置→运行失败/取消→尝试消费旧结果 | 旧资产可留作历史，但不能作为本次成功输出；界面与运行记录区分旧值 |
| CON-11 | 同一操作节点运行两次；删除生产节点或某一产物 | 操作身份、配置、标题不变；新产物独立；删除不隐式级联删除另一方 |
| CON-12 | 给生产关系虚线和真实数据边各建一组，运行选定图 | 只有真实数据边参与依赖、拓扑和输入 |
| CON-13 | 构造无输出上游、已失败上游、过期媒体引用、错项目 mediaId | 错误定位来源与端口；无跨项目误读、无静默空值成功 |
| CON-14 | 保存、关闭进程、重开、项目导出再导入 | 配置/结果/端口版本保留；媒体 ID 与路径全量重映射；无 Key 导出 |

提示：DAT-03的“合法JSON字符串”、DAT-06的“缺失占位字段”、DAT-11的“体配置改变后续跑”是重点探测项，尚未断言已存在缺陷。

**七、性能与恢复补验**

- 图规模：10/100/500节点，本地确定性链与分叉图各一组，重复3次记录建图、运行、保存、重开耗时和峰值内存；500不支持时记录设计边界。
- 循环：0/1/20/100项仅跑本地变换，核对线性增长、取消响应、结果体积、保存速度；不以100项付费模型做压力测试。
- 媒体：小/中/大尺寸一次一档；GPU记录显存、临时磁盘、处理帧率；模型时延与应用开销分开。
- 建议初始体验目标：点击到反馈≤300ms、取消到界面反馈≤1秒；取消请求后底层释放时间单独记录。无正式性能基线时这些是待校准目标，不是“已满足”承诺。
- 覆盖率可用 `pnpm run test:coverage -- --maxWorkers=1 --minWorkers=1`，但当前coverage include仅选取部分文件，还含renderer转导出。先校正到真实业务文件，再报告覆盖率；不能把局部数字叫全项目覆盖率。

**八、完成标准与交付**

1. 每个核心节点有契约卡、单节点正常结果、至少一个异常、依赖链和重开证据；模式/供应商动态分支全部枚举。
2. 每个关键失败证明“未请求/已请求/任务仍在服务端/已落盘”的真实阶段；状态、记录、资产一致。
3. 分别交付L1–L5结果，skip/BLOCKED清晰；只有真实调用才标“真实模型通过”。
4. P0/P1关闭，关键阻塞解除后才能整体验收；优化项单列：输入预校验、错误定位、去重请求、取消/恢复、独立媒体校验、缺失自动化覆盖。
5. 修复先跑受影响定向用例，再补最终统一门禁和关键链回归；输出缺陷前后对照，不通过修改快照或期望值掩盖行为回退。
