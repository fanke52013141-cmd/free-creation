# Canvas Studio 节点审查与测试计划

编制日期：2026-09-28。源码基线：`source`，提交 `d821bbb`。性质：待执行计划，不是测试通过报告。

本次只读取源码、现有测试、规范和启动说明；没有运行模型、调用 API、修改业务代码或删除旧代码。现有变更日志中的通过数量是历史记录，不作为本轮结果。

三个方案可分别执行，建议顺序为：代码测试基线 → 用户交互验收 → 冗余与冲突整改 → 受影响回归。

**共同范围**

- 核心节点：网址、文件、AI 对话、AI 处理；裁剪、拆分、生图、P 图；视频素材、抽帧、视频截取、深度视频、白模视频；声音调整、语音合成、语音克隆、音色设计；数据处理、JSON、结构数据、分镜板、循环。
- 基础依赖：文本、图片资产、音频资产，连接器、运行器、数据存储、模型网关、媒体处理服务。
- 关联回归：代码节点、节点库/工作流、项目导入导出、历史节点读取。3D 预演台仅做公共机制受影响回归，不把它和白模视频混为一个功能。
- 排除：远程视频生成真实请求、视频生成计费任务及以其为必要步骤的闭环。视频生成的静态契约、离线 mock 可以随全量测试运行。深度视频、白模视频是本地转换，必须测试，不因名称含“视频”而排除。
- 当前是本地单用户 Electron 产品，不新增登录、团队或云端项目测试。

**开始前必须对齐的现状**

| 项目 | 当前源码事实 | 对测试设计的影响 |

**执行环境与样本**

固定 Windows 主验收环境，记录系统、CPU/GPU、内存、显示分辨率/DPI、Electron/Node/pnpm、FFmpeg/FFprobe、Python/CUDA 环境、供应商与模型 ID。API Key 只通过现有安全配置读取，报告不包含密钥、鉴权头或带签名的下载链接。

离线/破坏性故障测试使用独立 `CANVAS_DATA_DIR` 和专用项目。真实模型测试使用当前安全配置下新建的 QA 项目；不要把正式数据库复制到测试目录或把密钥导出。已有数据先按现有备份方式保留，故障注入不针对正式项目。

标准数据样例：

```json
{"name":"测试链接","url":"https://example.com/"}
```

```json
{"shots":[{"id":"s1","scene":"蓝色立方体","dialogue":"甲组-731","duration":"2"},{"id":"s2","scene":"红色球体","dialogue":"乙组-942","duration":"3"}]}
```

```json
[{"id":"a","prompt":"蓝色立方体"},{"id":"b","prompt":"红色球体"},{"id":"c","prompt":"绿色圆柱"}]
```

分镜样例采用当前 schema 的字符串 `duration`；循环列表根值是对象数组，不是 `{items:[...]}`。运行记录可以内部保存 `{items,progress}`，但输出投影必须遵守端口协议。

**统一记录和门禁**

每个表格行内的分号分支拆成独立执行记录，例如 `IMG-02.a`、`IMG-02.b`，不能只选一个正常分支就给整行通过。

```text
caseId / plan / nodeType / contractVersion / priority / owner
commit / buildPath / environment / projectId / fixtureHash
configSnapshot / sourceNodeId:portId -> targetNodeId:portId
steps / expected / actual / status / startedAt / duration
runId / provider:model / requestCount / actualCostIfAvailable
outputPort:type:schema / mediaId / mediaHash / evidencePaths
defectId / blockerReason / retestCommit / retestResult
```

状态统一为 PASS、FAIL、BLOCKED、NOT-RUN、N/A。缺 GPU/模型不可用记 BLOCKED；被跳过的测试不得算 PASS；N/A 要解释与范围的关系。每次报告分别给出已执行通过率 `PASS/(PASS+FAIL)` 和计划完成率 `(PASS+FAIL)/适用用例数`，防止大量未测时得到虚假的高通过率。

严重度：P0=数据丢失、密钥泄漏或失控重复付费；P1=核心节点/链路不可用、错误结果、取消或恢复失效；P2=可绕过的交互/边界问题；P3=非阻断改进。已知异常也要有缺陷号，不能通过扩大异常过滤器消失。

发布验收建议：范围内核心正常路径全部 PASS，P0/P1 为零，所有失败与 BLOCKED 有明确结论；核心真实 API 与本地 GPU 闭环不能用 mock 结果替代。完整 PASS 才能声称“所列功能已验证可用”；仍有阻塞则注明条件与未测项。
