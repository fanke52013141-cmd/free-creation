追加范围：依据用户提出的“AI 审核循环”，首版新增类型增至 Agent、状态机、AI 审核三种。审核是单次质量判断，控制循环通过标准结果与显式关系实现，详见 [AI 审核节点方案](07-ai-review-node.md)。C1 登记契约/UI，C2 接资产和 gate，C3 验证三类执行主体返工，C4 验证恢复；本文其余工单保持。

## 1. 要交付的产品行为

用户在画布创建人工材料节点、人机协作 Agent、纯 AI Agent 和单次处理节点；向 Agent 添加 Skill、工具与明确的输入输出。Agent 多步处理材料，产出可查看、编辑、连接和保存的资产；人机协作节点可等待人讨论、补充和选择；纯 AI 节点自行检查和重试。主 Agent 协调节点间交接，状态机校验流程阶段。上帝 Agent 根据需求创建同一张画布图。

第一条贯穿验收路径：人工提交材料 → 纯 AI 分析 Agent → 分析资产 → 人机协作整理 Agent → 人修改并提交 JSON 资产版本 → 单次处理节点校验/转换 → 最终资产。前两个 Agent 分别绑定分析与整理 Skill，调用真实能力节点。再把这条路径交给上帝 Agent 构建、主 Agent 协调。

### 1.1 参与方式与职责分开

| 参与方式       | 行为                                 | 人的参与                                         | 首版实现方式                                                     |
| -------------- | ------------------------------------ | ------------------------------------------------ | ---------------------------------------------------------------- |
| 人机协作 Agent | 多步处理、工具调用、检查、讨论与等待 | 可在本节点补材料、修订任务、审阅资产、提交继续   | 新增 `agent` 类型，`interactionMode=collaborative`               |
| 纯 AI Agent    | 多步处理、自检、有限重试和交付       | 正常任务没有必经人工步骤；用户仍可主动停止或接管 | 同一 `agent` 类型，`interactionMode=autonomous`                  |
| 纯人工节点     | 上传、填写、编辑和明确提交资产       | 人负责内容，不调用 AI                            | 复用文本、JSON、图片、音频、视频、文件等内容节点；按需补提交状态 |
| 单次处理节点   | 明确输入的一次转换                   | 配置、运行和查看，无自主任务循环                 | 保留 AI 处理、代码和媒体处理等现有节点                           |
| AI 对话节点    | 简单多轮交流、内容讨论               | 人驱动每轮对话                                   | 保留现有类型，不自动升级为任务 Agent                             |

`role=coordinator/specialist` 表达主 Agent/专业 Agent 职责；`interactionMode` 表达人是否参与，两项互不替代。人工节点是内容节点的工作方式，不立即新增通用“人工黑盒”类型。人工上传和生成的可交付内容均称“资产”；任务、会话、运行记录、等待和错误不是资产。

纯 AI Agent 缺输入或无法满足要求时，返回可定位的 `blocked/failed`，由主 Agent 决定补输入、换任务或终止；不会偷偷转为等待人回答的协作任务。只有用户显式接管或修改模式后才进入人工协作，修改有新修订和历史。人机协作也不逐步强制确认：只有声明的交接点或实际缺口才等待。

### 1.2 首版范围

新增 Agent、声明式状态机和 AI 审核类型；保留现有全部可创建节点。首批自动调度适配文本、JSON、AI 处理和受限代码处理，文件仅承诺已支持格式的明确读取。AI 审核先覆盖文本/JSON 和有界返工。图片/视频/音频节点继续手动可用，逐类通过适配验收后才开放自动调度。多专业 Agent 是首版核心；先顺序交接，独立任务并行在恢复门禁通过后再开放。

运行保持本地单用户 Electron；模型复用本机配置和验证入口。延续首版本地模型优先、不自动下载模型的约束；远端模型如需开放，通过同一模型适配契约进入并明确数据发送边界，不以云服务作为产品前提。首版不接 MCP/CLI、不建立第二套工作台，不给 Skill 默认 shell 或任意文件系统能力。

## 2. 框架选择与依据

建议采用 **LangGraph JS/TS 作为 Agent 任务运行底座，LangChain 作为消息、模型适配和工具组件层**。画布图仍是唯一可编辑业务流程。LangGraph 的内部状态图只描述一个 Agent 如何决定、调用、检查、等待和退出，不让用户维护第二张业务图。

官方资料核对于 2026-10-12：

| 来源                                                                               | 已核对事实                                                                      | 本项目设计判断                                     |
| ---------------------------------------------------------------------------------- | ------------------------------------------------------------------------------- | -------------------------------------------------- |
| [LangGraph overview](https://docs.langchain.com/oss/javascript/langgraph/overview) | 提供低层有状态编排、持久执行和人工参与；可独立使用                              | 用于可控制的 Agent 内部任务循环                    |
| [LangChain overview](https://docs.langchain.com/oss/javascript/langchain/overview) | 提供 Agent、模型和工具抽象；其 Agent 建于 LangGraph 上                          | 复用组件，不为每个角色再启动一套独立调度器         |
| [Interrupts](https://docs.langchain.com/oss/javascript/langgraph/interrupts)       | 持久人工等待需要 checkpointer 和稳定 thread ID；恢复会重入包含 interrupt 的步骤 | 人工等待映射到节点；恢复前后的副作用必须有命令回执 |
| [Tools](https://docs.langchain.com/oss/javascript/langchain/tools)                 | 工具可声明名称、描述与参数 Schema                                               | 框架工具只是包装，实际允许范围由本产品校验         |
| [Skills](https://docs.langchain.com/oss/javascript/langchain/multi-agent/skills)   | 支持按需加载专门指令和知识的模式                                                | 建立本地 Skill 目录、版本和按需读取机制            |
| [Agent Skills 格式](https://agentskills.io/specification)                          | 使用含元数据与正文的 SKILL.md，可带 references/assets/scripts                   | 首版支持指令和参考资源；脚本执行需要单独工具适配   |

上述框架事实不等于本项目已完成恢复、权限或节点调度。框架不保证外部供应商副作用“恰好一次”，不能用 checkpoint 代替业务事务和回执。

### 2.2 依赖与框架验证

C0 将真正使用的 `@langchain/langgraph`、`@langchain/core` 显式声明并锁定经过验证的兼容版本，不依赖传递包偶然可访问。默认先验证当前锁文件组合，不自动升级全部依赖。官方 interrupt responseSchema 功能注明需 1.4.16 或以上；当前 1.4.14 不直接引用这一 API，首版可在产品命令边界用已有 Zod 验证，升级则另留兼容证据。

先实现自定义 StateGraph 的一个有限循环；LangChain `createAgent` 仅在证明能复用同一工具校验、预算与 checkpoint 后才可作为内部替换，不能叠两套决策循环。暂不引入 Deep Agents 默认文件系统/子 Agent 执行环境，避免与现有节点和主 Agent 调度重复。不上 Python 服务、不改画布引擎、不把现有业务模型调用迁移为第二套请求路径。

## 3. Agent 节点配置和交互

### 3.1 节点配置草案

| 配置       | 内容与约束                                                              |
| ---------- | ----------------------------------------------------------------------- |
| 身份与职责 | 节点 ID、契约版本、角色、职责说明；显示名可改，不参与寻址               |
| 参与方式   | collaborative / autonomous，模式变化生成新修订，不修改正在执行的快照    |
| 模型       | 本机模型绑定引用、支持能力和验证结果；节点不保存密钥                    |
| Skill      | 固定 `skillId + version + contentHash`；显式选择、启用/停用、缺依赖原因 |
| 工具       | 工具 ID、版本、参数约束、允许节点范围、本机依赖和可用性                 |
| 输入输出   | 静态类型端口、JSON Schema、基数、必填性和完成条件                       |
| 人工策略   | 允许哪些补充/编辑/选择/继续事件；哪些阶段必须等待                       |
| 预算       | 最大模型轮数、工具次数、总时长、输入大小和可用时的 token 预算           |
| 失败策略   | 有限重试次数、可重试分类、预算耗尽和缺输入的处理                        |

普通节点同类端口遵守统一规范，首版 Agent 也不默认开放任意具名动态端口。任务配置改变输出结构时须经过契约版本、连线重验和确认，不由模型在运行中悄悄增删端口。配置固定在 `props.config`；用户目标/正文按现行 `props.text` 保存；任务实例与会话是依附该节点的运行数据。

### 3.2 用户交互

卡片显示模式、职责、当前任务、真实阶段、待人工事项、已提交资产引用与开始/停止/继续。长讨论使用本节点展开视图；工具和 Skill 选择进入节点设置，不把所有配置塞入卡片。

人机协作节点：讨论消息可随时保存；“采用为新要求”“提交材料”“选择版本”“继续任务”分别是明确事件。聊天发送本身不等于改任务或触发昂贵下游。用户可在本节点直接协作，不要求绕经主 Agent。

纯 AI 节点：默认显示目标、进度摘要、工具步骤和资产；正常路径不显示必经确认。过程监督由完成条件、Schema、确定性验证或明确检查步骤完成；模型自检是辅助，不把自称完成当成成功证据。不要求记录或展示模型内部隐含推理。

人工节点：草稿可编辑；进入 Agent Flow 的资产由“提交”产生固定版本。后续修改草稿不会覆盖正在运行的输入；现有手动画布保持原行为，不强制所有旧节点改成提交制。纯人工审核步骤以后确有需求时可独立扩展，不用上传节点冒充所有人工工作。

## 4. Skill 机制

Skill 提供方法、领域知识、模板和验收清单；工具提供实际动作。两者可以关联，但加载 Skill 不自动取得新工具权限，也不会新建一个隐藏 Agent。

### 4.1 包结构与管理

支持本地 `SKILL.md` 包，首版读取 name/description、正文、references 和 assets。产品内部另存 manifest：skillId、版本、内容哈希、来源、兼容条件、所需工具、适用输入输出和启用状态；这些不是擅自追加的官方必填字段。

本机设置提供“导入 Skill / 查看 / 编辑为新版本 / 停用”；节点设置提供“为这个 Agent 添加 Skill”，可看到实际依赖缺口。编辑后的新版本不影响旧任务；删除被引用版本前阻止操作或保留可恢复快照。模板保存绑定，导入时可携带明确选择的纯内容 Skill 包，不能带密钥和机器绝对路径。

### 4.2 加载流程

1. 创建任务时固定绑定版本；基础上下文只放已启用 Skill 的名称、描述和用途。
2. 由显式指定或模型调用 `skill.load` 加载需要的正文；参考资料用 `skill.readResource` 按片段读取。
3. 记录实际加载版本、资源引用和大小，控制每次读取及总上下文预算；不记录正文到诊断日志。
4. 工具白名单仍由节点和任务授权决定；Skill 的所需工具缺失时明确禁用或返回缺口。
5. 多 Skill 指令冲突时，产品约束和当前用户任务优先，不能通过 Skill 正文扩大执行范围。

首批内置示范包：材料分析、JSON 整理、结果检查。每包提供成功/失败样例与输出结构，使用相同材料比较“单次处理”“无 Skill 的 Agent”“有 Skill 的 Agent”的实际结果、有效重试和工具次数。Skill 包不是只把一段更长提示词塞进节点。

脚本文件首版可识别并显示“执行未支持”；要执行必须绑定注册过的受限工具，明确环境、输入输出和取消语义。包导入校验相对路径、文件类型与大小，不直接执行导入代码。

## 5. 工具机制与能力释放

### 5.1 三类工具

| 类型            | 示例草案                                                      | 实际执行位置                                  |
| --------------- | ------------------------------------------------------------- | --------------------------------------------- |
| 流程工具        | canvas.read/apply、task.assign/read、state.dispatch、run.stop | 公共图命令和任务服务；范围与角色校验          |
| 内容/Skill 读取 | asset.read、skill.load/readResource                           | main 受控读取；按引用、片段和预算返回         |
| 业务工具        | node.execute、asset.publish                                   | 真实能力节点和资产提交服务；返回运行/资产引用 |

工具描述从公共契约和已验收适配器生成；首版在设置中添加内置工具，不承诺直接导入任意 npm/MCP 工具。新增外部能力遵循同一适配接口，未来扩展不改 Agent 核心领域分支。

业务工具调用必须关联真实能力节点。节点不存在时，上帝 Agent/用户先补结构；专业 Agent 只有预先授权的局部创建范围才可创建能力节点。对读取或状态查询不逐轮造新节点，对业务加工保留节点、输入、尝试、结果与来源。

### 5.2 每个工具的契约

`toolId/version`、名称/描述、输入与输出 Schema、角色/节点范围、本机依赖、只读/可逆/外部副作用标记、超时、取消语义、幂等策略、诊断阶段。工具可用性按当前项目和任务计算，不在各角色里手写第二套名单。

框架发出的工具调用先经过：参数校验 → 身份/范围 → 版本 → 预算 → 占用与幂等 → 执行 → 输出校验 → 回执。模型返回的任意 nodeId、toolId 和“我是用户”都不直接可信。用户已授权范围内常规动作连续执行；声明需要人工确认的动作持久等待一次，重开不重复询问已完成的同一决策。

专业 Agent 默认读取本任务输入和自己的资产，不能全图扫描。主 Agent 管理授权控制范围的任务；上帝 Agent 有建图权限。读文件也要落在输入或 Skill 资源引用内，不默认获得机器全盘读取。

首版预算默认建议：每任务最多 12 次模型决策、20 次工具调用、10 分钟，单工具失败最多 2 次自动重试；这些是待 C0/C3 实测调整的产品初值，不覆盖长视频的独立任务时限。预算耗尽保留资产与回执，返回明确状态，不继续自动循环。主/专业 Agent 预算分别统计；主 Agent 委派有累计次数和总量限制。

## 6. 资产、结果和输入输出的保存

### 6.1 数据所有权

| 对象                         | 权威保存位置（拟）                                 | 节点内保存/显示什么                                |
| ---------------------------- | -------------------------------------------------- | -------------------------------------------------- |
| 图定义、节点配置、端口与关系 | 当前项目图/project.json，继续现有保存协调器        | 可编辑配置、正文或引用                             |
| Skill 包与版本               | 本机 Skill 库，元数据进现有数据库迁移体系          | 固定绑定与启用状态                                 |
| 文本/JSON 资产版本           | 资产版本仓库；小内容可存本地 SQLite                | assetId/versionId 引用和可见正文，避免两份独立正文 |
| 媒体/文件资产                | 复用现有 MediaAsset 和项目文件；版本层引用 mediaId | 预览及引用，端口不传二进制                         |
| Agent 任务、会话、等待、回执 | 依附项目/nodeId/taskId 的本地运行仓库              | 任务/会话引用和状态投影                            |
| Agent checkpoint             | 独立受控运行存储，由 main 单写入                   | threadId/checkpoint 引用，不充当用户流程定义       |
| Flow 业务状态                | 状态机持久实例与事件                               | 节点引用实例，不再维护可编辑 currentState 副本     |

表名和路径属于拟议实现，在 C0 审阅实际迁移版本和现存表后确定；不复用撤回实现的闲置表冒充交付，不删库或降版本。资产版本内容是业务数据，可以保存正文；诊断日志和导出诊断包禁止正文。导出项目是独立用户操作，不与诊断导出混淆。

### 6.2 资产版本协议草案

AssetVersion：assetId、versionId、kind、Schema 引用、内容或文件引用、createdAt、来源节点/taskId/runId/attemptId、父版本、输入版本引用、校验结果。人工上传与编辑记录人工来源，生成记录真实运行来源；候选、已选和已提交分别记录，选择一个版本不改变正文。

用户编辑采用资产生成新版本，不修改旧版本。节点标题、拖动、折叠不形成业务版本。历史节点保持原读取方式，新 Agent Flow 通过兼容适配按需创建资产版本，不一次迁移全部旧项目。媒体结果当前最多 12 项的候选集合不等于不可变资产版本仓库，也不作为新仓库的全量保留策略。

删除节点保留被引用资产；资产删除检查图、输入快照和历史引用。首版不自动清理被运行引用的资产或 checkpoint，后续按保留策略设计清理；防止“删一个节点把整个链路资料删掉”。

### 6.3 端口与连线

端口定义保持现有 PortDecl；实际运行值保持 NodeValue 类型。资产引用通过内部数据包携带 `assetId/versionId + 来源端口 + 契约版本`，业务 executor 接收兼容的已解析 NodeValue，不要求一次重写所有 executor。

数据边仍表达 `sourceNode.outPort → targetNode.inPort`。首版默认连接当前已提交/已选输出；提供固定资产版本的引用选择。执行启动时把所有实际输入固定为 InputManifest；执行中切换上游候选或人工修改不改变本次快照，后续任务使用新版本。

InputManifest 至少记录来源节点/端口、资产/版本、字段或片段范围、用途、大小与解析版本。主 Agent 的最小输入只能从已连线/明确参考的资产中选择；需要扩展参考必须受控提交，不能靠读全图绕过连接。

模型实际上下文组成：系统约束与角色 → 任务目标/完成条件 → 已加载 Skill → 选定输入内容 → 工具回执与必要会话摘要。任务配置和控制事件不是混在普通数据输入里的隐式 prompt。输出投影仅暴露已声明、通过校验且已提交的资产；讨论消息不会自动成为正式输出。

数据关系、控制关系、状态关系在同一画布显式保存。旧边缺类型仍为数据边；控制反馈不进入数据 DAG。连线不自动运行，调度才执行；类型/JSON Schema/基数不兼容、上游无正式输出时明确阻断，不猜测或默默转换。

### 6.4 原子性与导入导出

资产提交采用稳定 outputKey（task/attempt/output 字段），先完成文件暂存、校验和结果登记，再通过待物化记录投影到画布；失败可补同一个节点。文件、SQLite 和 project.json 不假装共享一个事务，使用回执、待处理队列和补偿。业务完成与“待画布呈现”分别显示。

项目导出包含图、已选择的资产版本和实际所需媒体、声明的 Skill 版本；默认不携带活动任务/checkpoint、密钥或机器路径。导入完整重映射节点、资产、版本、媒体以及结构化引用；无法带入的资源明确缺失并阻断相关运行。原导出路径及旧项目兼容保持，事务成功后才显示新项目。

## 7. 执行架构与框架接入

```text
画布节点 UI
  → 可信命令入口（项目/节点/版本/范围）
  → main Agent Runtime（LangGraph 内部循环）
      → 模型单步适配 → 现有模型验证/网关/密钥边界
      → 工具适配 → 统一工具校验 → 公共图命令或节点执行桥
  → 资产提交 / 持久等待 / 回执 / checkpoint
  → 事件投影回 Agent、状态机、资产节点
```

### 7.1 内部循环

读取任务输入 → 按需加载 Skill → 模型提出有限动作 → 校验命令 → 调用工具 → 观察回执 → 检查完成条件 → 下一轮 / 等待 / 提交 / 失败。任务完成需要输出 Schema、必需工具回执与声明的完成条件同时满足，模型“我完成了”不能直接写成功。

主 Agent 使用相同底座但只开放协调工具；专业 Agent 的独立任务有独立 thread 与预算，不以框架自动 subagent 生成隐藏任务。上帝 Agent 建图步骤先给预览，再按已授权范围事务提交图变更；不把“拟创建”显示为正在运行。建议上帝 Agent 首版也以画布内 builder 入口承载，具体选择新增角色还是现有节点展开模式在 C1 原型确认。

### 7.2 main 与 renderer 的桥接

先从现有 renderer 注册表抽出宿主无关的描述/契约，React Body 留 renderer；shared 不导入 Editor。main 持有 LangGraph 任务与工具校验；现有业务节点仍由唯一执行入口执行，main 经可信命令桥请求活跃画布执行并接收持久回执，不另写同业务 executor。

renderer 断开、项目切换或执行桥超时，main 停止新派发并标记等待宿主/需核对。不能因 IPC 超时重复发起外部调用。首版运行需要打开对应画布；后台持久等待可保存，关闭后的业务执行是否继续由现有任务服务真实能力决定，未验收不承诺。后续迁移执行宿主必须比较相同输入/输出/失败/取消，不属于恢复旧 headless。

### 7.3 模型适配

新增 AgentModelPort：messages、工具 Schema、响应/工具调用、usage、取消、流事件；由 main 的适配器桥接现有请求底座。现有聊天网关尚不是该接口，须补单步结构化 tool-call 能力，不能拿聊天字符串假装工具调用，也不能复用带自己工具循环的 startChat 再嵌套决策。

LangChain 模型适配仅把消息和工具 Schema 映射到现有 AI SDK 请求层，凭据继续在 main 使用。登记并实测 tool calling、结构化输出、流式、取消与本地无密钥连接等可用性；现有“text.generate 验证通过”不自动代表 Agent 模式可用。真实模型不支持时明确禁止启动相关任务，合成模型仅用于协议与故障测试。

### 7.4 持久化与恢复

稳定 threadId 由 project/node/task 和尝试身份映射，固定 runtimeVersion、graphRevision、输入版本、Skill/工具版本。checkpointer 的实现先验证与现有 SQLite/ Electron ABI 的兼容；优先通过现有数据库宿主适配接口，现成 SQLite saver 只有不引入冲突驱动且通过打包验证后才采用。

运行仓库是命令、任务、等待和资产提交的权威事实；checkpoint 只保存内部循环位置/上下文。回执写入与 checkpoint 存在间隙时，恢复先查询稳定 commandId 的业务回执再决定下一步，不盲信旧 checkpoint 重跑。内部 task/call 次序必须稳定；外部无法证明是否完成的动作显示需核对。

`interrupt` 恢复可能重新执行步骤开头，因此人工等待前不放未保护的副作用。人工响应绑定 waitId、taskId、revision 和候选版本；重复响应去重，迟到/过期选择拒绝，不覆盖用户新修改。每个 Agent 独立状态；Flow 暂停只停止新派发，不抹掉其他节点的真实状态。

## 12. 首包开工建议与待细化项

唯一推荐下一步：执行 C0，交付 Electron 中的最小持久 Agent 任务实验和明确的兼容结论；随后定 C1 协同契约及画布原型。C0 不使用真实个人项目、不自动执行付费媒体、不恢复已撤回接口。

建议默认选择：上帝 Agent 用画布内 builder 入口；人工协作在专业 Agent 本节点进行；资产正文在对应资产节点编辑；首批内置 Skill 为材料分析/JSON 整理/结果检查；模型先验证当前本机可用的本地配置。以上是产品建议，可在 C1 原型审阅调整，无需先把所有选项固定才开始 C0。

C0 必须解决的工程问题：选定版本能否打包、工具调用模型是否可用、单步模型接口如何与网关共用、checkpoint 如何沿现有数据库宿主持久化、main-renderer 回执桥能否避免超时重复业务。失败时先缩小底座实现或修适配，不撤回“画布唯一流程、人机/纯 AI 分开、资产真实落图”的产品要求。
