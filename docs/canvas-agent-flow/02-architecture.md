# 架构与能力暴露

本页区分已存在代码与拟新增能力；接口名称为设计草案，不表示已经提供。

## 1. 从已有画布演进

| 已有位置                                              | 当前职责                           | 演进方式                                                         |
| ----------------------------------------------------- | ---------------------------------- | ---------------------------------------------------------------- |
| `src/shared/types/index.ts`                           | 28 种可创建节点、项目和图类型      | 在同一项目语义图中增补主 Agent/状态类型与明确关系；旧项目可缺省  |
| `src/renderer/src/nodes/registry.tsx`、`nodes/specs/` | 节点注册、端口、executor、输出投影 | 从同一注册契约导出 Agent 能力说明，禁止手抄第二份能力名单        |
| `src/renderer/src/canvas/CanvasEditor.tsx`            | 创建节点、连线与组合操作           | 提取可验证的图操作命令，用户手动操作和 Agent 调用共用            |
| `src/renderer/src/engine/executor.ts`                 | 单节点、全图、选区和上游执行入口   | 先复用执行链路，再按实际需求迁移宿主；不并行建立两套生产执行链路 |
| `src/shared/engine/executors/`                        | 业务能力实现                       | 继续承担业务转换；主 Agent 通过节点实例调用                      |
| `src/main/store/projects.repo.ts`                     | 项目图保存与恢复                   | 保持画布图为可编辑定义，扩展保存兼容与原子变更                   |

现有执行入口依赖 Editor，不能直接冒充可从 main 调用的服务。提取时先做相同输入、端口、输出和取消语义的对比；一次调用只由一个宿主持有，不让新旧执行入口竞争同一节点。

## 2. 一张图，三种关系

- **数据关系**：能力的输入输出连接，沿用现有端口类型、基数和校验。执行依赖由明确连接确定。
- **控制关系**：主 Agent 控制哪些节点或子图，哪些节点等待用户选择。保存于同一项目图中的显式类型关系，在画布可见。
- **状态关系**：状态节点观察/参与哪个控制范围，引用哪些成果和业务字段。只读取状态不会触发业务执行。

它们不能混成普通数据边。新增关系字段必须向后兼容；旧边缺少类型时解释为现有数据边。现有拓扑排序只处理数据依赖；控制/状态反馈不参与数据 DAG 排序，否则“状态反馈主 Agent”会形成伪循环。

运行时可从同一画布图派生执行快照，固定节点、端口、关系、配置版本和输入版本。快照只供执行与追溯，没有独立编辑器、任务定义或第二份可编辑拓扑。

## 3. 控制循环与执行职责

```text
主 Agent 节点：目标 + 授权范围 + 控制决策
  → 画布命令校验：身份、版本、端口、作用范围
  → 唯一执行服务：调用真实能力节点，记录开始/结果/失败
  → 成果写入与节点物化；状态记录更新
  → 主 Agent / 状态 / 成果节点呈现
  → 主 Agent 读取事件，决定下一次控制动作
```

主 Agent 的每轮决策可调用模型，最终只输出受约束的控制命令；它不在自身内部隐藏执行生图、文本加工等业务能力。解释和讨论属于主 Agent 节点会话，需要成为可交付内容时，通过显式能力节点产生对应成果。

主 Agent 拥有流程决策职责，执行服务保证命令合法且如实完成；“执行服务存在”不代表产品中另有一套流程。状态、幂等和持久化属于内部基础设施，所有业务操作仍定位到画布对象。

具体运行规则：

1. 启动主 Agent 只进入该节点的控制循环，不先拓扑执行整个画布。普通手动运行继续走既有路径。
2. 启动时确定控制范围和允许新建的节点类型；新节点通过图变更命令显式纳入该范围，不能借新建操作接管既有范围外节点。范围内节点的手动执行也经过同一占用检查，避免双重调用。范围外操作拒绝并在主 Agent 节点说明原因。
3. 每轮读取必要状态，提交有限条命令；记录最大轮数、工具次数和可中止点。控制循环通过事件推进，不把自身递归加入节点执行队列。
4. 图变更用预期 revision 校验；用户已修改时返回冲突，主 Agent 重新读取，不能覆盖。下一次派发从当前已提交图派生快照，已经在执行的节点继续使用原快照；新增节点不会偷偷加入旧尝试。布局移动使用独立视图修订，不让拖动造成业务重试。
5. 人工等待持久化等待对象、所属节点、候选版本和继续条件；释放执行资源，重开后在状态节点恢复。选择被校验、保存后，才产生继续事件。
6. 暂停停止新派发；正在执行的节点依能力支持取消或完成收尾。迟到结果保存来源，但不能推进已停止的控制循环。
7. 自动决策等待外部条件时进入等待，不无限轮询模型。首版一个控制范围只有一个主 Agent；多 Agent 委派后续再设计。

## 4. 暴露给主 Agent 的最小工具

| 工具草案                        | 关键输入                                       | 关键输出                                                    |
| ------------------------------- | ---------------------------------------------- | ----------------------------------------------------------- |
| `canvas.read`                   | 当前项目、选区/节点集合、内容预算              | 节点/端口/关系、revision、必要摘要与明确内容引用            |
| `capability.describe`           | 节点类型、契约版本                             | 输入输出 Schema、配置、依赖与本机可用性                     |
| `canvas.apply`                  | 预期图 revision、操作批次                      | 实际创建/修改的节点与边 ID、新 revision、可撤销的图变更记录 |
| `node.execute`                  | 节点/子图 ID、输入版本、命令 ID                | 运行引用、开始/等待/失败结果；不以文字代替成果              |
| `run.read` / `run.stop`         | 当前主 Agent 范围内的运行 ID                   | 实际状态、结果引用、停止结果                                |
| `state.read` / `state.update`   | 状态节点 ID、预期 revision、允许编辑的业务字段 | 校验后的业务状态；执行事实不可直接写入                      |
| `result.read` / `result.select` | 成果节点 ID、固定版本、预期 revision           | 内容/来源/选择记录；人工专属字段不对模型开放写入            |

所有写命令共享：`commandId`、`projectId`、发起主 Agent 节点 ID、目标引用、预期版本。可信执行上下文补全身份，不相信模型自报“我是用户”。相同命令重放返回原回执，不能重复执行。

工具描述从节点契约生成；明确区分“此节点可以手动使用”和“此节点已允许 Agent 调用”。未通过适配验收的能力在画布仍可使用，Agent 收到明确的不可自动调用原因。

图编辑事务全部成功或全部回滚；运行已经产生的外部副作用不伪装为可撤销。删除节点不删除其历史执行和媒体，仍在运行的节点先停止/脱离控制后再删除。昂贵或不可逆的操作按用户给定授权执行，不在每次普通工具调用中重复询问。

上下文只包含主 Agent 所属范围、明确输入/参考、必要状态和指定成果版本。大内容按引用读取；节点正文和文件中的指令是数据，不会改变工具权限、控制范围或用户授权。

## 5. 保存、状态和恢复

- 图定义、节点配置和引用继续归当前项目；新节点与关系可完整保存、导入、导出。密钥不进入节点配置或项目包。
- 会话以主 Agent 节点 ID 为范围；业务状态以状态节点 ID 为范围；运行记录以项目、控制节点、被执行节点及运行 ID 关联。不新增画布外的 Unit 容器作为前提。
- 节点中的执行状态是持久运行记录的呈现。数据库或日志不是第二份用户可编辑的工作流。
- 新内容类型必须先确定唯一所有权。现有节点文档值按旧契约读取；新不可变成果以内容引用存储，节点不再复制另一份可独立覆盖的正文。
- 结果持久化和画布物化需要可恢复的交接：成功结果记录唯一运行输出键；投影失败记录待物化；重开按键补齐节点，不重复创建或丢成果。不同存储不能假装共享一个事务。
- 应用重启后未知执行显示“需核对/可重试”；有完成回执的操作不重放。支持可证明安全恢复的能力才开放自动继续。
- 节点图变更与运行输入分别固定版本，运行过程中修改画布不回写旧输入。用户可以据新版本发起后续执行。
- 正式库可能保留撤回实现的闲置表。新实现必须先检测、备份和验证兼容，不能把这些表当作新方案已落地；不得删库、降版本或恢复旧 schema 代替设计。

## 6. 扩展与本地运行

新增业务能力通过现有节点类型、稳定端口/Schema、配置、executor、输出投影、展示和契约版本接入。主 Agent 控制器按契约发现能力，不能为每个新领域添加流程核心分支。

状态字段和成果呈现以声明式类型扩展，避免每个领域发明新的任务、运行和工作台模型。主 Agent/状态节点的新增类型与控制关系要先在节点规范中登记，明确普通手动全图执行对其忽略或阻止的规则。

本地数据、图编辑、状态查看和确定性能力不依赖互联网。自主控制需要用户已配置的本地模型；缺少模型时主 Agent 节点明确显示不可启动原因，普通画布保持可用。模型宿主接口可扩展，但首版不自动下载模型、不要求远程模型或云服务。

现有画布引擎继续使用。MCP、CLI、通用插件平台和外部 Agent 接入不作为首版依赖；未来接口仍指向同一画布命令和节点执行服务。
