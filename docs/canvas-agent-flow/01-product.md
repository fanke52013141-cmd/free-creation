# 产品与节点交互

依据：[产品约束](README.md)。本页是设计，新增节点均待实现。

## 1. 节点角色

| 角色          | 用户看到什么                                                   | 用户能做什么                                | 边界                                                               |
| ------------- | -------------------------------------------------------------- | ------------------------------------------- | ------------------------------------------------------------------ |
| 主 Agent 节点 | 目标、当前控制动作、所属范围、下一步、讨论记录、开始/暂停/停止 | 给出要求、修改安排、查看每次操作定位、接管  | 负责规划与控制，业务加工交给能力节点                               |
| 材料节点      | 文本、JSON、图片、音频、视频或文件                             | 上传、编辑、连线、指定参考范围              | 复用已有类型，不再建立画布外材料列表作为唯一入口                   |
| 能力节点      | 明确的输入、配置、执行状态和输出                               | 配置、单独运行、重试、接管                  | 使用已有节点契约和执行器，不被主 Agent 内部隐藏调用取代            |
| 成果节点      | 实际内容、来源、版本、候选/已选状态                            | 查看、编辑为新版本、选择、连接到下游        | 是节点角色；优先复用现有内容类型，只有缺少表达能力时才新增节点类型 |
| 状态节点      | 控制范围、实际进度、等待原因、业务变量、选定成果、错误定位     | 修改允许编辑的业务字段、作出选择、继续/暂停 | 执行状态只读；用户选择和业务字段通过明确命令修改                   |

首版一个控制范围只允许一个运行中的主 Agent。普通画布和未受控节点继续手动使用；不要求所有项目都创建主 Agent。专业子 Agent 后续若引入，也必须是可定位的节点，使用同样的身份、范围与运行规则。

主 Agent 节点中的计划列表引用真实节点 ID。计划尚未落成节点时显示“拟创建”，不显示正在执行；提交图变更后才允许执行。Agent 需要调用新的业务能力时，先在画布建立相应节点及输入关系。

## 2. 状态节点是一项可用功能

示例：状态节点标题“方案选择”，内部显示当前两份候选的节点引用、等待用户选择、选择操作，以及选择后的下一节点。点击候选定位到对应成果节点；选择后显示被选版本和操作者。

状态分为两类，界面必须区分：

- **执行事实**：正在执行的节点、失败、停止、待恢复、完成数量。由执行服务提供；主 Agent 和用户都不能直接把失败改成成功。
- **业务状态**：用户选定的方案、允许继续的条件、已确认的偏好。按字段声明类型、编辑者和作用范围；支持人或主 Agent 发起受控修改。

通用暂停/继续是控制命令，作用于已标明的主 Agent 运行范围；状态节点不是第二个调度器。主 Agent 负责决定要做什么，执行服务负责校验与执行，状态节点承载这次协作的可见状态和人工操作。

不要求每个底层变量、日志或内部尝试都成为一个节点。节点只承载用户需要查看、编辑、连接或参与的状态。

## 3. 在画布内交互

1. 主 Agent 节点内输入目标。可展开节点进行长对话，保持节点身份和画布上下文；不导航到独立聊天项目。
2. Agent 提议的创建、修改和连线在画布对应位置呈现。执行范围、将调用的能力以及等待点可见。
3. 授权范围内的常规操作连续进行，不要求每一步重复确认；删除已有内容、覆盖用户修改或超出范围时，先在相关节点显示变更并取得授权。
4. 执行中的节点显示实际状态；新增结果成为可定位成果。背景执行不自动移动用户视角。
5. 用户在成果节点编辑，在状态节点选择或继续，也可在主 Agent 节点提出修改要求。
6. 关闭节点展开视图、切换选区或保存重开，不改变内容归属或执行事实。

现行节点指针、双击编辑、隐藏滚动条、单排引用、身份色规则继续适用。新增控制/状态关系需要相应的端口或连接标识；其样式与交互在节点规范中登记，不通过整卡拦截鼠标事件规避画布手势。

## 4. 四条用户路径

| 路径         | 画布内过程                                                                              | 成功条件                                                           |
| ------------ | --------------------------------------------------------------------------------------- | ------------------------------------------------------------------ |
| 从零组织     | 放入材料 → 创建主 Agent 节点 → 给出目标 → 主 Agent 创建能力节点与连接 → 执行 → 成果节点 | 每个业务执行和成果都能定位；不靠聊天文字冒充结果                   |
| 人机共同修改 | 用户修改成果 → 保存新版本 → 主 Agent 读取新版本 → 仅执行选定后续节点                    | 保留旧版本来源；不能覆盖用户的新修改或让全图无故重跑               |
| 等待人参与   | 能力产出候选 → 状态节点显示等待 → 用户在画布选择 → 主 Agent 继续                        | 等待不依赖长期挂起的聊天请求；拒绝候选可以继续改，不强制终止整个图 |
| 失败与重开   | 节点失败/关闭应用 → 重开画布 → 状态节点显示真实状态 → 用户修正或继续                    | 不假装所有运行仍在进行；不重复已完成的业务操作                     |

## 5. 成果、选择与引用

- 执行输出先持久化为结果引用，再物化到画布；失败时显示恢复状态，不显示虚假的成功卡片。
- 一份业务成果只有一份内容来源。节点展示引用它，不能同时维护互相覆盖的节点正文副本与后台正文副本。
- 当前已有内容节点仍按现行内容所有权工作；版本能力逐种内容接入，不能一次迁移全部旧项目。
- 用户编辑已采用结果形成新版本。下游的本次执行固定实际读取版本，旧记录不随当前选区变化。
- “选择结果”不等于“下游已经完成”。需要等待时由状态节点明确阻断，主 Agent 在选择事件发生后重新核对条件并继续。
- 成果数量多时可在原画布组合/折叠；折叠是视图操作，来源、版本和连接保持可查。检索或列表只能作为辅助定位入口。
