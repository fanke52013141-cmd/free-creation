# Agent 节点与画布协调规范

日期：2026-10-11。状态：设计规范，尚未实现。依据用户最新指导：上帝 Agent 构建系统，主 Agent 协调流程、产物和最小输入，专业 Agent 节点执行复杂任务。本文修正此前把构建与协调混为一谈的方案。

## 1. 三种 Agent 职责

| 角色       | 责任                                                                             | 控制边界                                                                                               |
| ---------- | -------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| 上帝 Agent | 与用户讨论并构建/修改整套图；定义 Agent 的职责、工具、输入输出、状态机和协作关系 | 生成并提交图变更，校验可执行性；构建完成不等于已执行。运行中的结构修改需新图修订，不改写正在执行的输入 |
| 主 Agent   | 协调已构建 Flow；分配任务、选择必要输入、安排执行、收集产物、发起交接和重做      | 管理已授权范围；不能伪造成功、越过人工确认、静默改写专业 Agent 职责                                    |
| 专业 Agent | 处理本节点的复杂任务；规划局部步骤、调用允许的工具、检查结果、补充或重试         | 自己的任务范围、预算和工具白名单；返回产物或明确的阻塞/失败，不接管整个 Flow                           |

首版建议复用同一 Agent 节点类型承载“协调者”和“执行者”角色；角色决定工具权限和交互，不只是提示词名字。显示名称可为“主 Agent”“研究 Agent”等，稳定类型仍为 Agent。上帝 Agent 是用户使用的构建角色，其是否也落为 Agent 节点尚未确定；实现前明确入口，不能自行认定为画布外工作台。

正常运行中的图由上帝 Agent 或用户编辑；主 Agent 的调整限于已声明范围内的任务、输入和执行安排。发现结构能力不足时提交可见的图变更建议，不自动取得整图构建权限。

## 2. Agent 与已有 AI 节点的区别

| 节点          | 执行语义                                                                              | 完成判定                                                         |
| ------------- | ------------------------------------------------------------------------------------- | ---------------------------------------------------------------- |
| AI 对话       | 用户驱动的多轮交流；现有节点也有明确的生图技能，并非完全没有工具                      | 本轮回复生成；不等于复杂任务完成                                 |
| AI 处理       | 单次、可复跑的文本/Markdown/JSON 转换                                                 | 指定输出生成并通过契约校验                                       |
| Agent（新增） | 目标驱动的多步循环：读取输入 → 决定动作 → 调用工具 → 观察结果 → 检查要求 → 继续或等待 | 输出契约有效、完成条件满足；或明确进入等待、失败、取消、预算耗尽 |

Agent 不是加长提示词的聊天框，也不是无限自动对话。它有独立会话、任务实例、输入快照、工具记录、产物与状态；不同 Agent 不共用一份聊天和执行状态。专业 Agent 可以完成内容任务，主 Agent 的协调模式不隐藏完成所有专业工作。

工具通过已有能力节点调用已验收的实现；每次业务调用关联真实能力节点，其执行记录可展开，输入、结果与来源可在画布定位。普通内部读取或模型推理不必为每轮新建节点；最终成果必须有画布承载。

## 3. 首版需要哪些节点

| 内容       | 决策                                                       | 理由                                                                                 |
| ---------- | ---------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| Agent 节点 | 必须新增一个类型，支持协调者/执行者角色                    | 现有对话和单次处理不能表达自主多步任务、等待和工具调用恢复                           |
| 状态机节点 | 必须新增；承载状态字段、合法迁移、触发事件、条件和人工操作 | 仅显示进度的状态卡不够；需要保存整个 Flow 的生命周期和业务阶段                       |
| 结果承载   | 优先扩展已有文本、JSON、文件、图片、音频、视频资产节点     | 现有文档与媒体节点能承载内容；先补来源、版本、候选选择和固定引用，不另造通用结果黑盒 |
| 输入       | 复用已有材料节点和端口                                     | 主 Agent 根据任务为每次执行编制最小输入，不要求每个节点都出现上传控件                |
| 人工确认   | 首版由状态机节点和相关成果节点承载                         | 若后续确实需要独立可复用审核步骤，再新增审核节点                                     |
| 条件/路由  | 首版由状态机的声明式迁移和主 Agent 调度表达                | 不为一个状态字段立即增加一批控制节点；复杂稳定分支确有需求时再补                     |
| 子流程     | 复用真实组合/子图，补齐对外端口和执行边界                  | 折叠组合目前主要是视图能力，不能直接宣称已有完整可恢复子流程                         |

“文件节点”不是结果管理本身。文件可以保存结果正文，但文件路径不能代替版本、来源、已选状态、Schema 和下游固定引用。文本结果应支持直接查看与编辑；文件用于实际文件成果和导出，不能要求所有文本都先导出才能交接。

## 4. 统一协调契约

既有节点契约继续规定实际数据端口与执行器；增加以下协调协议后，才可声明被 Agent 自动协调。字段名为草案，类型实现前与现有结构逐项对齐，不在本次直接加入 Schema。

| 要求 ID    | 必须声明/记录                                                           | 用途                                                                             |
| ---------- | ----------------------------------------------------------------------- | -------------------------------------------------------------------------------- |
| CN-01 身份 | projectId、nodeId、nodeType、contractVersion、角色                      | 上帝 Agent 按类型建图，主 Agent 按稳定 ID 寻址                                   |
| CN-02 能力 | 配置 Schema、数据端口、工具权限、本机依赖、可调度性及原因               | 从同一注册来源派生构建/调度工具描述；不因节点可创建就允许自动运行                |
| CN-03 任务 | taskId、目标、完成条件、负责 Agent 节点、控制范围、预算                 | 同一 Agent 多次任务隔离；任务记录依附真实节点，没有第二份可编辑任务图            |
| CN-04 输入 | inputManifest：输入版本、来源端口、字段/片段选择、用途、大小/上下文预算 | 主 Agent 决定最小必要输入；专业 Agent 请求更多内容时返回补充请求，不自行读取全图 |
| CN-05 执行 | 预期 revision、commandId、runId/attemptId、开始/停止/恢复语义、占用范围 | 防止重复执行、过期覆盖和多执行者竞争                                             |
| CN-06 状态 | 独立节点状态、Flow 状态、合法迁移、事件来源、等待原因                   | 全局状态不覆盖各节点状态；不允许任意 setStatus                                   |
| CN-07 结果 | 类型/Schema、成果节点 ID、固定版本、来源任务/尝试、校验与选择记录       | 结果可在画布查看连接，讨论消息不会自动成为正式成果                               |
| CN-08 交接 | 提供者/接收者节点与端口、选定版本、就绪条件、人工等待策略               | 产物已生成、已选择、下游完成分别记录                                             |
| CN-09 恢复 | 已完成回执、工具中断点、待物化结果、需要人工核对的操作                  | 重开还原真实事实；未知副作用不能自动重放                                         |

任务状态建议为 ready/running/waiting/completed/failed/cancelled；主 Agent 暂停是控制状态，不把所有任务都强行写成 paused。专业 Agent 多步中间状态由其任务记录承载；现有一次性执行器需明确适配，不能把 waiting 当成 done。

建图和协调都遵循这套协议：上帝 Agent 创建的是节点实例、类型化关系和声明配置；主 Agent 创建的是依附节点的任务实例、输入清单和运行命令。两者不得各维护一套工具注册表或流程事实。

## 5. 状态机节点的实际语义

首版一个 Flow 控制范围绑定一个状态机节点；可用于记录整体生命周期和业务阶段。状态机节点配置声明状态、事件、条件与迁移，卡片显示实际当前状态、对应 Agent 和成果、等待理由及可执行的人工作业。

例：待启动 → 协调中 → 等待选择 → 协调中 → 已完成；任何运行阶段都可按明确规则失败或取消。它是 Flow 的一个状态机，不是把多个 Agent 的内部状态合并成一份。

- 权威状态是一份持久化状态机实例，节点引用并呈现它；不在 props 和后台同时维护两份可编辑 currentState。
- 主 Agent 可提交开始/等待/继续等事件，用户可提交选择/确认事件，执行服务可提交真实开始/完成/失败事件。
- 迁移条件确定性校验，来源角色必须匹配；同一事件去重并检查 revision。完成迁移必须满足声明的交付条件，不能由模型自称成功。
- 主 Agent 根据迁移后的状态协调下一任务；状态机校验规则并记录事实，不再次独立派发同一任务。
- 执行状态与业务阶段分别命名。规则只使用声明式可验证条件，首版不允许任意脚本在状态机内运行。
- 某个专业 Agent 失败是否令全局失败由规则决定；其他独立节点的状态保留。恢复回到合法阶段，不抹除历史。

## 6. 对用户三个问题的结论与门槛

| 问题                          | 当前结论                                                          | 成立门槛                                                                           |
| ----------------------------- | ----------------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| 现有节点能否被主 Agent 协调？ | 有端口、Schema、executor 和输出基础；尚不能宣称全部可自动协调     | 每类适配并通过 CN-01～09 的适用项，公布支持/不支持原因；先验证文本、JSON、数据处理 |
| 节点能否承载任务流程？        | 可以按节点/真实子图承载，但现有一次执行记录不等于自主任务生命周期 | Agent/状态机协议、输入清单、等待/恢复和交接齐备；不依赖旧数据 DAG 表达全部控制关系 |
| 上帝 Agent 能否通过节点构建？ | 可复用创建、配置、连线操作；尚无统一构建工具和完整新类型          | 契约可发现、图变更可校验/撤销、跨角色关系检查、建图可保存/重开并真实执行           |

当前证据：`src/shared/engine/executor-types.ts` 的结果状态为 done/skipped/failed；`src/renderer/src/engine/runRecord.ts` 提供节点运行记录；`src/shared/engine/executors/aiProcess.ts` 返回 artifactOutputPorts；`src/renderer/src/engine/executor.ts` 调用 materializeDocumentArtifact。文档成果落图已有基础，版本选择和 Agent 协调未据此宣称完成。

## 7. 后续实现的通过条件

1. 上帝 Agent 按契约建立主 Agent、两个专业 Agent、状态机及成果关系；无效类型、权限和端口在提交前明确拒绝。
2. 主 Agent 为两个专业 Agent 分别分配任务与最小输入；一个任务无法读到另一个未授权的会话或材料。
3. 专业 Agent 至少完成“调用工具 → 检查结果 → 再调用/等待”路径，不能以两条聊天回复冒充任务运行。
4. 成果由现有内容节点承载，来源和版本可查；用户修改生成新版本，旧任务输入保持固定。
5. 状态机记录等待、人工选择、继续、失败与完成；单节点状态和全局状态可区分；不重复派发。
6. 保存重开后节点、关系、任务和状态一致，已完成工具调用不重放；人工拒绝持久化。
7. 原 28 种节点与手动画布不减少；每项支持状态有实际证据。以上均为后续验收，不是本次已通过测试。
