## 2. 执行原则与退出规则

1. 每个新测试开始前，登记它要关闭的主用例、具体验收标准、运行版本和预期请求数。
2. 已有证据覆盖的参数不重复跑；先做“主用例标准—证据”映射，只有缺口需要新测试。
3. 一条补充子场景通过后，立即核对是否满足父用例全部标准；满足则升级父项状态，不满足则列出剩余条件。
4. 失败时先保存最小复现和故障证据，修复后只重跑相关回归；历史失败保留，但明确标注已修复或已被后续结果取代。
5. 真实供应商调用不从本机 fixture 静默切换。先冻结供应商、模型、单次请求预算、总预算和停止线，再按用例单独执行。
6. 暂缓或阻塞条件未具备时维持原状态，不为追求通过率降低验收标准。

## 4. 控制关系连线问题的具体判断

截图中的“允许处理”橙色虚线属于 Agent 控制关系，表达 Agent 的授权范围，不是普通数据边。现行 C1 文档要求控制关系以带标签和箭头的虚线显示，但没有要求端点接在节点顶部。当前实现将两端都锚定在节点顶部中点，所以这是连线几何和视觉路由问题；修正只应改变显示锚点与曲线路径，不改变关系配置、授权范围或数据 DAG。

## 5. 近期执行次序与交付物

1. 先生成主用例缺口映射，确认已通过子场景是否足以关闭 REL-03，并列出 CFG-03 与 REL-02 尚缺的具体格子。
2. 修正控制关系连线，并用几种节点相对位置验证视觉结果。
3. 按映射完成 CFG-03、REL-03、REL-02；每个主项完成后马上更新主用例状态。
4. 最后执行 REL-08；真实模型和设备专项只有在前置条件具备时单独推进。

每轮结束更新三样内容：主用例状态、唯一缺口/依赖、证据链接。不要只增加台账记录而不说明父用例为什么仍未关闭。
