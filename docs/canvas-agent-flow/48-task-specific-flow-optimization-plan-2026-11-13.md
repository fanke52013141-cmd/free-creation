# 特定任务 Agent Flow：现状复核与优化方案

日期：2026-11-13（Asia/Shanghai）。状态：**评审稿，尚未实施**。

目标：让用户围绕一类稳定任务，反复使用和打磨同一条流程；每阶段只接收必要输入，按固定方法工作，形成约定产物，人能围绕实际成果讨论、修改、选择和交接。

## 2. 主要差距与优先级

| ID | 差距 | 代码事实 | 用户影响 | 优先级 |
| --- | --- | --- | --- | --- |
| G1 | 最小输入还停留在资产级选择 | `runtime-model.ts` 的 decide 解析 directInputs、全部 target 输入、committed 输出和已加载 Skill；262144 字节超限即拒绝；固定输入契约只有端口与资产引用 | 大材料、重复成果和多轮工具结果仍可能挤占注意力 | P0 |
| G2 | 调度指令与实际生成指令未统一 | `desktop-host.ts` 将分派目标/完成条件追加到 Agent goal；`runtime.ts` 的普通 execute 主要提交 targetId 与固定输入；`aiProcess.ts` 使用自身 config.system/config.agent 和输入端口 | 在 Agent 中修订要求或反馈，不保证实际写作模型收到它；容易出现“讨论了但成稿没改” | P0 |
| G3 | 共创模型缺少实际工作对象 | `desktop-host.ts` discuss 仅传 goal/history/message；`runtime-model.ts` discuss 同样只发送三者 | 用户围绕当前稿件提意见，模型可能看不到稿件；采用讨论结果的链路零散 | P0 |

| G5 | 正式结果与阶段合格成果没有统一绑定 | finish 校验真实引用；完成条件主要为文字；AI 处理/human-task 调度目前限 text | “有真实文本”不等于“符合特定任务输出格式与验收条件” | P0 |
| G6 | 目标、硬约束、人工决定没有稳定的传递规则 | 已有固定版本，但没有完整的阶段级约束包及决策采用协议 | 上游共识可能在下游被遗漏、概括失真或覆盖 | P1 |
| G7 | 返工影响范围不够面向任务 | 已有明确审核返工，但普通阶段修订、下游过期、分支沿用缺统一产品语义 | 用户改中间结论后，不清楚哪些结果仍有效、哪些需要重做 | P1 |

| G9 | 含人工等待的组合尚不能承载完整任务 | `run-composite.ts` 明确拒绝 human-task；普通 adapter 不接 composite | 不能直接把整条人机 Flow 当现有组合节点封装后承诺可恢复运行 | P2，条件必做 |

## 3. 目标产品与首条验收任务

### 3.1 角色和权限

| 角色 | 应做的事 | 不应由它自行决定的事 |
| --- | --- | --- |
| 外部上帝 Agent | 与用户设计任务、修改真实画布、配置阶段/输入/输出/方法/人工点、提供差异预览 | 静默改写运行中的流程版本、扩权或将建图成功当任务完成 |
| 主 Agent | 读阶段事实、按声明规则协调、处理阻塞、建议补充输入或返工、向用户解释进度 | 临时重定义阶段目标、越过交付条件、无条件扩大上下文 |
| 专业 Agent | 在一个阶段内分析、生成、调用工具、自检和共创 | 读取全图聊天、修改别的阶段、凭文字宣称完成 |
| 状态机与宿主 | 校验业务事件、前置条件、输出和权限；持久化迁移事实 | 与主 Agent 再各自派发一次相同任务 |
| 用户 | 提供材料、提出方向、修改成果、采用/拒绝候选、改变方法或流程 | 被迫通过改提示词、改 JSON 或反复确认按钮才能表达业务选择 |

固定任务的含义是阶段和规则可预期，不要求每次输出字节相同。纯 AI 阶段正常自主完成；只在声明的共创/人工阶段，或明确无法推进时等待用户。

### 3.2 先验收一条三阶段路径，再扩成完整任务

第一条开发贯穿路径：**整理材料 → 围绕整理成果共创 → 基于已采用成果生成交付稿**。

必须实际展示：第二阶段模型看得到成果；用户修改会生成新版本；第三阶段只接收已采用版本、必要事实和硬约束；中途关闭应用后仍能继续；旧成果和讨论可追溯。

建议首个完整任务采用“资料型文章写作”，便于观察信息丢失和观点偏移。若以开发规则可检验性为主，可换成 PRD 撰写，底层协议不变。

| 阶段 | 最小输入 | 方法与输出 | 人如何参与 | 进入下一阶段条件 |
| --- | --- | --- | --- | --- |
| 任务定义 | 用户目标、受众、原始材料目录 | `task.brief@1`：目标/范围/长度/硬约束/需确认项 | 共同界定问题、修改范围 | 必填条件明确；声明需人工确认时已采用 |
| 资料整理 | 已采用 brief、被选资料或检索范围 | `research.evidence@1`：事实、出处、定位、冲突、未知项 | 补文件、排除不可信来源 | 来源引用可解析，证据格式有效 |
| 观点共创 | brief 中相关约束、证据表 | `writing.position@1`：核心观点、依据、反例、取舍 | 讨论、改观点、保留少数意见、选定方向 | 有已采用观点版本；必需人工作业已完成 |
| 大纲 | 已采用观点、必要证据、结构要求 | `writing.outline@1`：章节/论点/证据引用 | 修改章节与侧重 | 必需论点有落点；大纲通过声明的检查 |
| 成稿 | 已采用大纲、指定证据片段、写作方法 | 正文＋结构化交付说明 | 直接改稿、要求局部重写 | 正文/必需字段有效，引用和硬约束通过检查 |
| 审核定稿 | 当前稿件、验收规则、相关原始证据 | 同源审核报告、定稿版本 | 裁决事实争议、接受最终版本 | 固定版本审核通过；需要人工签收时已有对应记录 |

上述 Schema 名称是拟定业务契约，需登记实现后才可使用。不得把 `json.any` 当作这些阶段的完整交付约束。

## 4. 阶段契约与确定性流转

### 4.1 仍以画布为唯一流程定义

- 阶段配置依附实际 Agent/人工任务等节点；数据依赖复用真实端口连线。
- 无数据传递的先后/条件关系，使用显式、可见、可校验的控制关系；新增关系类型须同包更新呈现、契约、导入导出和三入口。
- 状态机声明业务阶段和合法事件，引用真实节点身份。运行时可以生成只读执行计划或索引，不能成为第二份用户可编辑的 DAG。
- 运行记录、任务、资产和决定保存事实；节点 meta 只作权威记录的投影，不允许另设一份可编辑 currentState。

### 4.2 建议的阶段声明

| 内容 | 必须表达 | 校验方式 |
| --- | --- | --- |
| 身份与职责 | 稳定 nodeId/stageKey、阶段目标、负责角色、参与模式 | 来自固定图版本；运行时不由模型重写 |
| 输入 | 来源端口、必填性、Schema、可选字段/片段、用途、预算 | 依赖可用、固定引用合法、选择器有效、大小可接受 |
| 方法 | Skill/提示词版本、执行节点绑定、允许工具、适用范围 | 固定版本与权限白名单；方法不隐式授予工具 |
| 输出 | 稳定业务 outputKey、承载节点/端口、类型/Schema、必需项 | 注册投影＋业务结构校验＋明确验收条件 |
| 人工参与 | 自主/共创/纯人工，何时等待，哪些决定必须显式采用 | 绑定具体 task/等待修订/候选版本，不从聊天猜测同意 |
| 进入与退出 | 依赖、已采用版本、审核、人工决定、条件分支 | 声明式条件解释器，不执行任意用户脚本 |
| 失败策略 | 缺输入、质量拒绝、技术失败、unknown、取消的处理 | 各自稳定原因与可恢复动作，不统一变成“重试” |
| 有界执行 | 模型/工具/质量返工预算、阶段超时 | 请求或副作用前预留；恢复不能重置预算 |

“有结果”“已采用”“校验通过”“阶段完成”必须区分。既有资产库的 committed 表示持久化事实，不能直接替代业务上的 accepted。

### 4.3 固定流程的调度规则

增加显式选择的任务型执行模式，沿用现有 coordinator 服务和命令账本。旧 Flow 保持旧语义，新模式不默认迁移存量项目。

1. 按真实连线和控制关系计算候选阶段。
2. 校验前置交付、业务条件、人工决定、预算及占用。
3. 固定 ContextManifest 与执行说明，生成 task/command 身份。
4. 调用现有公共执行器，落正式产物和回执。
5. 通过阶段验收后提交状态事件，再释放下游。

有唯一合法下一步时由程序推进；多条已声明独立分支按稳定顺序/预算调度。只有业务明确允许判断的分支才请求主 Agent 提出选择，宿主再次验证。主 Agent 仍负责协调与解释，但无需为了“下一步已经确定”反复调用模型。

阶段执行身份也要显式适配：专业阶段复用 specialist 宿主；纯人工阶段通过登记的适配器复用 human-task 的权威提交与等待；确定性转换复用公共执行命令。当前 coordinator 仅接收 specialist 子节点的限制需要在本包明确扩展并测试，不能仅在 UI 中标“纯人工”，背后仍强制调用一个模型才能等待人。

条件首版建议限于：字段存在/类型/值比较、集合大小、所引用交付是否已采用、指定版本审核是否通过、指定人工决定是否存在。结构合法无法证明事实真实，事实准确性仍需来源核对、AI 审核与人的判断。

停止、等待、失败、返工必须有声明的迁移；完成事件校验的是具体交付记录，不能仅凭事件名称直接置完成。

## 5. 最小必要上下文：从引用选择升级为输入编制

### 5.1 一次任务固定一份 ContextManifest

建议新增版本化共享契约，至少包含：

| 字段组 | 内容 |
| --- | --- |
| 身份 | project/flowRun/stage/task、定义修订、manifestVersion/hash |
| 不可丢约束 | 当前目标、范围、与本阶段相关的硬约束及已采用人工决定引用 |
| 业务输入 | sourceNode/port、asset/version、用途、required、选择器及其解析版本 |
| 方法 | Skill/方法版本与本次需要的资源片段 |
| 共创或返工 | 当前工作稿版本、被拒版本、对应反馈/审核版本 |
| 预算 | 模型上下文容量、阶段预算、输出预留、工具 Schema 开销、估算方法与版本 |
| 完整性 | 片段来源/hash、未纳入的可选材料、缺项和超限原因 |

Manifest 同时用于专业决策、实际生成和讨论，但三类请求按用途取各自必要部分；不将全部数据复制三次。下游不继承上游全部讨论历史。

### 5.2 编制步骤

1. **固定来源**：只读取声明范围内、已明确选择的资产版本；不把“最新版本”作为运行中可变指针。
2. **选择内容**：JSON 用明确字段路径；文本用持久化段落/片段 ID 或与内容摘要绑定的范围。缺字段要报缺失，不能退化为全文。
3. **去重并保序**：同一内容在 Agent 直接输入与 target 输入重复时，模型正文可共用一份；实际端口的顺序、基数和映射仍完整保存。
4. **保留关键约束**：目标、硬约束、已采用决定和必要证据优先；摘要不能改写否定、数值、例外和来源关系。
5. **按需取更多**：增加有界的“请求补充材料”动作，说明所需片段及用途；在声明来源内取数，超出范围则等待补充/授权并生成新修订。
6. **预算校验**：完整计算指令、工具描述、输入与输出预留；超过预算先缩减可选材料，必需内容仍超限则停止并显示原因。
7. **可核对**：用户可在详情查看“本阶段实际采用了哪些内容”；默认显示摘要与大小，明确打开才显示正文。正文预览属于本地业务读取，不进入日志或诊断包。

不能简单截取前 N 字，也不能为了降低 token 数删除必要证据。长文摘要若需要模型生成，应作为明确的预处理节点/模板产物，保存来源和版本；不在每次请求中偷偷再摘要。

### 5.3 预算与会话增长控制

- 阶段输入上限取“阶段配置预算”和“模型容量扣除输出/框架预留”中的较小值。
- Token 数需明确是官方 usage、匹配 tokenizer 的估计还是保守近似；不能把字节数称为 token。
- 初版试点可分别给整理、观点、大纲、写作设置不同预算，以真实样本调参；不对所有模型硬套同一阈值。
- 工具结果按类型选择必要字段和已选版本，历史结果保存在账本，需要时受控读取。
- 讨论保留完整可查历史；工作上下文采用固定稿件＋已采用决定＋近期必要对话。归纳出的决定在用户采用前标为建议，不静默升级为事实。
- 主 Agent 接收阶段状态、缺项、成果类型/引用和必要决策摘要；不默认读取所有专业阶段全文。

原有 128/256 KiB 限制作为兼容与传输兜底保留，不能用它替代阶段预算管理。

## 6. 让方法论和反馈真正进入内容生产

### 6.1 统一执行说明

在现有 command/runtime 契约上扩展版本化的执行说明（暂称 ExecutionEnvelope）：阶段目标、已固定方法版本、ContextManifest 引用、输出要求、已采用人工意见和当前返工反馈。

- 宿主根据已保存配置与任务快照构造并校验；不允许模型传任意 system prompt 覆盖对象、工具权限或节点配置。
- 将执行说明的摘要纳入命令意图签名与持久化，unknown 恢复复用原说明；不能恢复时重新临时拼一份。
- AI 处理等支持该能力的公共执行器显式消费说明。手动 GUI、CLI/MCP、Agent 调度共用同一构造/校验规则。
- 节点原配置与阶段说明的优先关系必须可解释：系统/安全边界 → 固定阶段职责与硬约束 → 已采用决定/返工反馈 → 业务输入。彼此冲突时拒绝或要求修订，不悄悄覆盖。
- 方法绑定拆清用途：协调策略绑定主 Agent；内容生产方法绑定阶段并传到实际内容执行器。同一个方法可被两者按需引用，但内容正文不重复注入。

### 6.2 闭环验收

使用可检查请求的确定性模型夹具，验证最终生成请求确实包含本次固定方法、人工修改意见、正确版本稿件和输出约束；不包含未授权材料或其他节点聊天。

再用真实任务验证：“把写作方法从先结论后论据改为先案例后分析”，新版本实际输出采用新方法；旧任务恢复仍用旧方法。仅断言 Agent 的 goal 发生变化，不算这一项通过。

此包同时接通 AI 处理的 JSON/Markdown 调度：端口必须由保存配置稳定派生，投影、适配器、资产登记和外部输出读取同源。不要单独放开白名单而遗漏输出端口或 Schema。human-task 的 JSON 调度按同样规则适配。

## 7. 节点内共创：围绕工作稿完成一段任务

### 7.1 完整操作链

1. 打开阶段节点，看到本阶段目标、采用的输入和当前工作稿。
2. 生成候选或导入自己的草稿，明确标记“候选，尚未交给下一步”。
3. 用户选中段落、填写意见，或直接编辑工作稿。
4. 讨论请求携带当前工作稿版本、被选片段、相关输入、已采用决定及必要历史，能够回答具体内容问题。
5. Agent 给出建议或修改提案；用户可采用全部/选定修改，也可以继续讨论。
6. 采用的修改产生新候选版本，保留 parentVersion、修改来源和所依据的反馈。原版本不覆盖。
7. 用户点击“完成本阶段”时校验交付条件，明确提交该版本；才允许下游读取。

“保存草稿”“采用修改”“交付下一阶段”是不同业务动作。讨论文字不自动成为资产；建议的采用必须经声明的文本/JSON 承载节点、公共保存/执行/资产提交服务产生正式结果，不能由 UI 直接伪造 `nodeResult` 或 committed 回执。

### 7.2 阶段生命周期

建议在阶段运行记录中表达：待输入、可开始、执行中、待共创/人工、待审核、已交付、需更新、失败、取消；这些状态需与旧 task 状态显式映射，不直接把现有枚举全部替换。

- 共创可以发生在首次生成之前或之后，由阶段规则决定；不能要求先跑一次无用工具才允许讨论。
- 运行中可记笔记，生效修改须在安全暂停/结算边界创建新修订；pending/unknown 未核对时不能偷偷换输入再重发。
- 需要多轮共创时，每次采用/拒绝绑定具体稿件和 interactionRevision，避免永久的 `humanAccepted=true` 被误用为以后所有版本都已批准。
- 用户补充新材料时给出影响预览；范围内新增版本产生新任务修订，新增来源/权限则先修改定义，不直接改旧任务快照。
- 切换纯 AI/共创/人工参与方式属于定义变更。已开始任务保留原语义，显式新开运行或在声明的迁移点接续。

### 7.3 界面组织

卡片只呈现阶段名、当前状态、关键成果摘要和当前所需操作；长内容放节点展开/详情中，保持可定位到原节点。详情按“本次输入、工作稿、讨论与修改、交付检查、历史版本”组织，避免用户在多个设置面板间搬运正文。

至少提供这些可理解状态：缺哪些材料、AI 正在处理什么、需要用户决定什么、当前选择的是哪个版本、为什么不能交付、哪些下游结果将受影响。

复用公共节点组件；遵守单击选中/拖动、双击编辑、单排引用和始终隐藏滚动条等规范。正文预览必须完整可达。外部导入文件经受控 ingest/提取能力进入资产与端口，不能在讨论框中开放任意路径读取。

## 8. 阶段交付、过程防偏移与局部返工

### 8.1 正式交付应有独立验收事实

建议形成可持久化的阶段交付记录，绑定：定义版本、阶段/task、ContextManifest、方法版本、候选资产版本、结构校验结果、规则版本、审核结论、人工决定引用和实际提交时间。

交付记录引用现有不可变资产，不复制全文形成另一套结果库。程序从该记录确定下游可用版本，不能读取随机最新候选。

| 检查层 | 能保证的内容 | 不能据此宣称 |
| --- | --- | --- |
| 执行回执 | 实际执行/人工提交存在，结果来自声明路径 | 内容一定符合业务需求 |
| Schema 与规则 | 必需字段、类型、数量、引用、硬约束、指定决定有效 | 来源陈述真实、推理必然正确 |
| AI 审核 | 按固定标准检查所选版本并给出反馈 | 绝对正确或完整事实核验 |
| 人工采用 | 用户选择了具体版本/判断 | 未经过用户的后续版本也被批准 |

审核通过必须绑定同一候选版本与规则版本。新版、规则变化或必需决定变化后重新验收；技术失败没有有效“通过/不通过”结论。

### 8.2 防偏移规则

- 将目标、禁止事项、关键数字/定义、已采用观点作为有来源的约束，而非依赖一段越来越短的摘要。
- 每一阶段声明哪些上游决定必须保留、哪些内容允许改写、哪些变化必须回到用户。
- 输出涉及事实时保留 source/version/段落或结构路径；搜索摘要只是候选资料，不能默认为已核实证据。
- 重要取舍形成显式决定：“采用什么、为什么、作用于哪些阶段”。后续模型只能提出修改建议，不能静默覆盖已采用决定。
- 对可自动检查的规则用程序校验；主观风格与业务质量交给固定审核标准及用户，不把所有质量判断塞进通用状态机。

### 8.3 修改一个阶段之后

1. 预览影响：根据真实依赖、被消费的版本和字段选择，找出直接/间接受影响结果。
2. 旧结果保留且可查看，新定义/输入生成新修订；已经运行的旧任务仍固定原输入。
3. 受影响的下游标为“需更新”，禁止将过期结果当新版本交付。
4. 与变更无关的分支保留有效状态；存在 unknown/在途命令时先结算，不自动重发。
5. 用户明确选择从哪里继续，创建新的 attempt/task，并关联原任务和返工原因。
6. 同输入版本、方法版本、输出契约和依赖摘要都一致时，才可按规则复用旧成果；不能仅凭“节点曾成功”命中缓存。

这应扩展现有审核返工/命令去重体系。不得以“支持自由编辑”为理由简单取消 semanticRevision、scopeRevision 或占用检查。

## 9. 流程复用与方法论打磨

### 9.1 区分定义、调用与成果

- **定义版本**：真实画布的不可变快照，含阶段契约、方法和依赖版本。它从唯一画布定义生成，不可另行编辑。
- **一次调用**：使用某个定义版本和某组材料，创建独立 run/task/manifest；不会改模板。
- **本次成果**：按阶段保存资产、决定与交付；与其他调用隔离。
- **改方法**：修改编辑稿、比较差异并发布新定义/方法版本；旧运行恢复继续使用旧版。

首版可通过已有画布模板/项目流程复用和固定定义快照，完成“一套流程反复用”。不必先把全部流程塞进 composite 才能试用。

### 9.2 方法版本的内容

每阶段的方法包建议包含：适用任务、固定指令、资源/模板、输入输出要求、验收样例、常见失败和版本变更说明。首版沿用现有 Skill 包和固定内容机制，按需扩展元数据，不直接执行包内任意脚本。

升级时比较：流程结构、输入范围、输出 Schema、方法、审核标准、人工参与点、模型能力要求。旧输入不兼容时必须给出原因，不自动覆盖已发布版本。

### 9.3 composite 和后台执行的后续范围

若用户要把整条人机 Flow 封装成可嵌套节点，必须专包适配：内部阶段身份、持久人工等待、外部定位/提交、父子 run 关联、重开继续、交付投影和 unknown 核对。目前 fail-closed 行为保留，未适配前不提供会误导的发布/运行入口。

同样，已有 composite 后台执行不能外推为任意 Agent Flow 均可脱离桌面宿主运行。后台化只复用同一宿主与公共执行器，按任务样例验收，不建立另一份业务运行器。

| 定义阶段、输入输出与参与方式 | 节点/流程设置与变更预览 | 复用 `graph.patch`/图校验，扩展阶段配置 Schema | 图修订、端口、依赖、范围、运行占用 |
| 查看实际输入与预算 | 阶段输入详情 | 拟增 `flowStage.context.preview/get` | 项目/任务身份；默认摘要，正文显式读取；不写诊断正文 |
| 请求/提供补充材料 | 缺项面板、材料选择 | 拟增阶段补充请求/响应，复用素材 ingest 与资产操作 | 受控来源、manifest 修订、固定版本、不得扩大权限 |
| 围绕稿件讨论 | 共创详情 | 扩展 `flowAgent.cooperate` 或独立版本化讨论操作 | task/wait/interactionRevision、稿件版本、上下文白名单 |
| 保存/采用稿件 | 编辑器、候选版本选择 | 拟增 `flowStage.draft.save/adopt`，内部复用声明承载节点及资产服务 | 草稿基准版本、幂等、来源类型；不直接覆盖运行快照 |
| 完成本阶段 | 交付检查与提交 | 拟增 `flowStage.deliver` | 输出 Schema、规则、固定审核、已采用决定及并发状态 |
| 返工与局部继续 | 影响预览、确认继续 | 拟增 `flowStage.rework.preview/commit`，复用运行/核对服务 | 影响范围、预期版本、unknown、重复提交、预算 |
| 保存为流程版本/升级 | 模板与版本界面 | 复用并扩展对应版本/发布操作 | 兼容差异、固定依赖、旧运行不变 |

外部 Agent 可以提出、编辑和提交获授权的业务内容；需要真实人工参与的决定，通过与具体意图/版本绑定的授权或 prepare/status/await/complete 协作完成。记录 actor=external/human/AI 等真实来源，不允许传 `accepted:true` 就伪装用户已经看过。普通业务选择也不能一概变成仅 GUI 可做。

每包同步公共 Schema、Registry、CLI 帮助、MCP 工具、动作分母、节点矩阵、生成契约和 `change-impact.json`；必须说明实际行为与兼容结论，不能只刷新 hash 放行。

## 12. 版本、存储、恢复与旧项目兼容

1. **定义协议版本**：阶段/任务型模式是显式新配置；旧 `schemaVersion:1` 保留原解析与语义。所有新增字段先审查 `.strict()` 解析器，不能假设“加可选字段”天然兼容旧客户端。
2. **节点契约版本**：若改变端口/输出/必填性，按 NODE_CONTRACT_SPEC 决定升级及迁移；稳定端口修复也需快照和兼容比较，不能仅改适配器。
3. **命令版本**：ExecutionEnvelope、ContextManifest 等改变意图时使用明确的新版本或兼容解析；旧 unknown 命令不得按新规则重算输入再投递。
4. **数据迁移**：新阶段记录/决定/manifest 采用可验证迁移；旧数据缺失标为 legacy/unknown，禁止虚构原始输入、方法或已批准事实。
5. **保存提交**：正文编辑、资产提交、交付记录和画布投影分别定义提交点；用回执和待完成记录补齐跨文件/SQLite 的失败，不宣称天然跨存储原子。
6. **等待恢复**：保存 stage/task、固定稿件、interactionRevision 和下一步合法动作。重开后先核对，不自动重复生成或将候选变为定稿。
7. **版本冲突**：返回明确冲突与当前版本；不能自动拿最新修订覆盖原意图。运行中结构变化生成新定义，旧运行保持原快照。
8. **导入导出**：重映射阶段/节点/资产/媒体/决定引用和相对路径；不导入密钥与可继续行使权限的活动运行身份，历史作为只读事实。
9. **失败隔离**：日志失败不改变业务结果；业务账本或固定输入写入失败必须阻断后续副作用，两者不能混淆。

## 13. 如何证明达到了用户目标

### 13.1 必过行为场景

| 场景 | 通过标准 |
| --- | --- |
| 固定任务重复调用 | 相同定义产生相同阶段/合法分支规则；每次 run、输入和结果隔离 |
| 无关材料干扰 | 在未授权分支加入诱导文本和大量无关材料，当前阶段实际请求不包含它们 |
| 长输入 | 必需片段和来源完整；超预算可解释地等待补充/调整，不静默截断 |
| 方法/反馈生效 | 实际内容模型请求含正确固定方法与已采用意见，产物体现变更 |
| 多轮共创 | 至少 3 轮围绕实际稿件讨论、局部修改和比较，未交付稿不被下游消费 |
| 人工决定 | 对具体版本采用/拒绝；旧决定不能批准新稿；三入口规则一致 |
| 无效输出 | 缺字段、错误类型、伪造来源、未通过审核均不能完成阶段 |
| 语义偏移 | 故意改变必需观点/数字/限制，程序规则或审核能拦截，并定位到依据 |
| 局部返工 | 改中间阶段只影响实际依赖分支，旧版本保留，不自动重做已付费任务 |
| 停止/unknown | 取消后迟到输出不改变终态；unknown 先核对、没有盲目重放 |
| 关闭重开 | 等待、草稿、决定和版本恢复一致，恢复不增加已完成执行次数 |
| 模板/方法升级 | 新调用用新版，旧运行仍能按旧版恢复；不兼容升级明确拒绝 |
| 三入口 | 相同动作的输入、正式输出、拒绝、版本和恢复语义相同 |
| GUI 使用 | 实际鼠标/键盘可完成输入查看、讨论、编辑、采用、提交和返工；卡片选中/拖动/滚动不退化 |

### 13.2 任务质量评测

先固定首个领域的约 10 组样例，覆盖短材料、长材料、相互矛盾资料、证据不足、人工改方向、审核拒绝及恢复。每组建议重复 3 次，记录模型和方法版本；真实调用需另行确定模型与费用预算，本方案不产生调用。

比较当前流程与优化流程：

- **上下文**：各阶段实际输入估算/usage、材料命中率、重复内容比例、峰值、输出预留；压缩比例是辅助指标。
- **必要信息保留**：预先标注的必需事实、约束、来源是否进入正确阶段并保留到交付。
- **结果质量**：完整性、事实忠实度、目标一致性、格式合规、可用性；用固定评分表和人工抽检，AI 评分只作辅助。
- **人参与效果**：意见是否生效、改稿次数、重新解释背景次数、用户能否完成实质取舍；不能把点击确认次数当共创深度。
- **稳定性**：技术完成率、质量通过率、返工率分开统计；不能因能输出就记任务成功。
- **成本与耗时**：实际 usage 与请求次数；缺供应商 usage 时标未知/估算，不伪造精确费用。

硬性门槛建议为：契约/权限/人工门禁/版本/恢复案例全部通过；标注的必需信息无静默丢失；用户意见的版本绑定与实际生效全部可核对。质量评分和 token 改善目标在 AF-00 测得基线后冻结，避免先拍一个压缩百分比再以删内容达标。

### 13.3 工程门禁

各包先执行有意义的定向测试，再运行 `npm run guard:agent-parity`、`npm run verify:agent-access`、适用类型/契约/UI/桌面验收和完整 `npm run verify`。新增 acceptance 脚本名称实施时登记，不把拟定脚本写为已有通过证据。

真实计费模型、媒体、安装包、纯确定性夹具分别记证据。完整门禁失败时如实报告，先修复或明确阻断发布；“零新增失败”不能代替用户要求的完整通过。

### 14.2 实施每包时必须补齐的诊断

| 路径 | 复用/拟新增的阶段 | 允许的关联与计数 | 禁止记录 |
| --- | --- | --- | --- |
| 输入编制 | 编制开始/成功/拒绝及稳定原因 | project/stage/task、manifest hash、版本 ID、字段/片段数、字节/估算 token、缺项计数 | 目标、输入正文、字段值、原始文件路径 |

每包指定唯一终态拥有者，保留开始/终态、失败阶段及关联；复用公共节点/模型阶段时不重复记录。测试日志拒写不改变业务结果、秘密/正文不出现在实际诊断包，更新 `docs/LOGGING_COVERAGE.md`；历史无关联项如实标缺失，不补造。

## 15. 建议采用的实施裁决

| 事项 | 建议 | 适用理由 |
| --- | --- | --- |
| 首个领域 | 资料型文章写作；若主要服务开发交付则选 PRD 撰写 | 前者易观察内容偏移，后者易定义结构/完整性检查；先选一个，避免并行扩多个领域 |
| 首版工作范围 | 主画布的固定任务流程＋文本/JSON＋明确共创节点 | 覆盖核心痛点，沿用当前已验证基础 |
| 首条试用路径 | 整理材料→共创修改→采用后写作 | 能同时暴露上下文、反馈传递和成果交接问题 |
| 主控方式 | 新任务型模式按规则确定候选与顺序，模型负责声明内的判断和解释 | 减少不必要调度随机性，保留局部 Agent 能力 |
| 最小输入策略 | 优先确定性字段/片段选择与预算；模型摘要为显式可追溯预处理 | 避免压缩过程变成新的内容漂移来源 |
| 人工参与 | 每阶段可配；用户能实质编辑/选择，不强制所有阶段确认 | 保留纯 AI 效率与共创空间 |
| 扩展顺序 | 核心任务验收后，再扩媒体、并行规模和含人工的嵌套后台流程 | 当前瓶颈主要是内容与交接规则，不是节点数量 |

按上述顺序推进，保留已有可靠执行基础，把开发成果逐步收敛为可重复使用的具体任务。达到目标的判定对象应是“某类任务及其已验收流程版本”，不能用操作数、节点数或测试数替代。
