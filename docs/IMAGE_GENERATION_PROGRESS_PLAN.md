# 生图耗时预估与进度呈现方案

## 结论

不按“供应商”单独统计，也不把网络文章中的秒数写成固定进度。唯一可用于进度预估的数据是本机真实成功请求的端到端耗时（提交、供应商排队、轮询、下载并落为本地资产）。统计键采用：

`providerInstanceId + modelId + driver + aspectRatio + resolution + referenceImageBucket + outputCount`

其中 `referenceImageBucket` 为 `0 / 1 / 2–3 / 4+`。供应商实例必须保留在键中：同一供应商的不同网关、不同地域或不同账号并不具有相同队列耗时。模型、分辨率、参考图数量和批量数量也会显著影响时间，不能混成一个平均数。

官方 OpenAI 图片接口可提供进行中、局部图与完成事件，但当前应用的网关统一只在本地媒体资产落盘后返回结果；因此第一版进度以端到端实测为准，后续某个驱动支持事件流时再用真实事件提前替代估算进度。[OpenAI 图片流事件文档](https://platform.openai.com/docs/api-reference/images-streaming/image_generation/partial_image)

## 本地记录模型

在本地 SQLite 增加 `generation_latency_profiles`，不保存提示词、图片、API Key 或供应商 URL。每个 profile 保存：

| 字段 | 含义 |
| --- | --- |
| `profile_key` | 上述维度的哈希 / 稳定串 |
| `sample_count` | 成功样本数，最多保留最近 30 个 |
| `durations_json` | 最近 30 个端到端毫秒值 |
| `estimated_ms` | winsorized 均值：先剔除最低/最高 10% 后平均 |
| `updated_at` | 最近成功时间 |

只在单张图片真实完成并落盘后记录一次；取消、超时、网络错误、供应商拒绝和 mock 演示都不写入。多图运行逐张记录，`outputCount` 维度是本次批量数但每张仍有独立样本，便于把“9 张串行”与“1 张”区分。

查询按以下顺序回退：精确键 → 同供应商实例与模型（忽略画幅/参考图）→ 同 driver 与模型 → 初始保守默认值。UI 必须同时说明来源，例如“预估 28 秒（本机 12 次）”或“暂无本机样本，按保守预估”。

## 进度算法

单张图片的预估时间为 `E`，已过去时间为 `t`：

`progress = min(99, floor(t / E * 100))`

每 250ms 重绘一次。供应商在 `E` 前完成时直接展示真实图片，不等待进度条走完；超过 `E` 时固定显示 99%，文案改为“仍在等待供应商完成”，不制造 100% 的假完成。

批量 `N` 张是明确的顺序任务。已完成 `C` 张、当前一张进度 `p` 时：

`progress = min(99, floor((C + p / 100) / N * 100))`

覆盖层显示“正在生成第 `C + 1` / `N` 张 · 约 `E` 秒”，每张成功后立即在画布物化为独立图片资产。用户停止后，已完成图片保留，未开始图片不创建。

## 交付切片与验收

1. **数据层**：SQLite migration、profile repository、无敏感字段断言、profile 选择与回退单测。
2. **执行器**：在 `imageGenExecutor` 的成功分支记录单张耗时；批量的每张成功后独立落盘、独立物化。
3. **UI**：节点运行覆盖层显示定时百分比、批次序号、样本来源；完成 / 失败 / 取消立即停止计时器。
4. **真实验收**：同一供应商模型连续运行至少 5 次；验证早完成直出、超时卡 99%、取消无 profile 写入、切换 1k/4k 或参考图数量后命中不同 profile。

多图数量这一轮已先实现为节点 `config.count`（1–9），并以独立可追溯资产输出：1–4 张用 2 列，5–9 张用 3 列。它不等待耗时系统即可安全使用。
