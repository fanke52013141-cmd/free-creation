## 解读与边界

- 200 节点输入 P95 从约 103–125 ms 降到 53–59 ms；1000 节点仍约 967–1005 ms，性能问题尚未解决。
- 浏览器 baseline/after 为共享索引优化的前后记录；原生记录为后续代码状态，不能当作同一环境的前后对照。
- 浏览器比例是 deviceScaleFactor；原生比例是 Electron webContents zoom，均不等于 Windows 系统缩放。
- 输入和移动通过编辑器 API 驱动，再等待动画帧；不是物理键盘输入延迟、指针拖动延迟或用户操作耗时。
- 原生为 Electron 主进程加开发渲染页，保存走真实 IPC 与磁盘。JSON 字段 demoSaveMs 在原生记录中表示真实保存，名称沿用早期浏览器脚本。
- sampledHeapBytes 是采样 JS 堆，不是进程峰值 RSS。原生 processMemory 使用 Electron app.getAppMetrics，workingSetSize/peakWorkingSetSize/privateBytes 单位 KB；不同进程峰值不可直接相加为同时发生的总峰值。
- 首次可交互、快照体积和内存数据见原始 JSON；本轮不以简单帧等待推断用户可交互的完整产品 SLA。
- 后续优先采集真实 1000 节点混合项目的性能 profile，再评估可见区域渲染、订阅粒度和 DOM 成本。

原始证据：baseline.json、after.json、electron.json。复跑脚本 scripts/benchmark-optimization-ui.cjs，先启动 5191 浏览器开发服务；--electron 需要生产主进程 out 与 Electron 可用。
