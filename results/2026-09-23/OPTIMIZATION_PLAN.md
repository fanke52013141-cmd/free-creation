# Canvas Studio 测试整改与发布验收计划

> 基线：2026-09-23 候选 `53c738e`（Windows / Electron 39.8.10 / Node 24.11.0）。
> 原始证据：`results/2026-09-23/batch0-3/` 与 `ROLLUP.md`。本计划修订不改写这些基线报告。
> 目标：先把失败证据定界并恢复自动门禁，再完成当前支持范围的节点、连接、数据和桌面验收。

## 1. 基线与结论

| 项目 | 2026-09-23 基线 | 结论 |

| 契约测试 | 282 PASS | 仅代表契约子集通过，不代替全量测试 |

发布判断维持原结论：基线不是发布候选。原始失败记录见 [ROLLUP.md](./ROLLUP.md) 和 `batch0/`，任何修复只在新报告中追加结果、commit 和证据路径。

## 2. 执行红线

1. 基线报告只读。新增结果必须记录修复 commit、工作区是否干净、环境、命令、退出码和证据路径。
2. 单测失败先对照当前契约、实现和失败 diff 定界；不得仅为了变绿而放宽断言。
3. 新处理能力仍须遵循 `AGENTS.md` 与 `NODE_CONTRACT_SPEC.md`：独立节点或明确模板、明确端口、executor 和持久化测试；不能在 React 组件绕过 executor 执行模型。
4. 媒体导入导出仍必须覆盖 ID/相对路径重映射及 API Key 排除规则。
5. 经确认的产品修复需验证原失败、相邻回归和保存重开；若属 UI 几何问题，再附桌面截图或可复现几何断言。
6. 仅本地单用户场景。**不要求旧用户项目、旧数据库版本的历史迁移验收**；用干净数据目录和当前 schema 验证安装、保存、重开与恢复。不得因此移除当前版本运行所需的 SQLite 内部 schema 初始化或迁移代码。

### R1.1 单测 13 项逐条定界

| `selection-geometry.test.ts` / 2 | page/screen 坐标转换、tldraw handles 与选择框实际几何 | 以变换公式和桌面缩放截图核验，禁止只改数值断言凑绿 |
| `media-import-real.test.ts` / 1（B5） | 当前已可确定：不是“正文 5 字段变 4 字段”。正文断言在失败前已通过；实际失败是媒体 SQL 参数新增 `name`，而测试期望仍只有旧参数 | **先只更新测试期望**：增加 `asset.name`，再完整运行该文件验证 DOCX/XLSX/PPTX/PDF。若后续正文断言失败，再单独立文档解析缺陷；没有失败证据前不改导入业务代码 |

证据定位：`batch0/test-full.log` 中 B5 在 `test/media-import-real.test.ts:93` 的 `row.args` 断言失败，实际参数末尾多出文件名；`src/main/store/media.repo.ts` 的媒体插入已包含 `name`。原正文断言位于同一测试更早的位置并已通过。因此 B5 当前分类为**高置信度的过期测试期望**，不是已证实的文档抽取产品缺陷。

### R1.3 验证与通过条件

1. 在固定修复 commit 上运行 `pnpm verify`，保存完整日志和退出码。该脚本已经串联 lint、typecheck、全量 Vitest 和构建，不再重复单独跑四次相同门禁。
2. 单独运行 `pnpm test:contract` 并记录结果；单独运行节点矩阵在 R2.1 修好后验收，因为它不属于当前 `verify` 脚本。
3. 有测试断言更新时，报告列出失败前后差异、契约或行为依据以及更新后的完整测试结果。
4. 若出现真实产品缺陷，将修复代码和测试维护分开 commit，避免把“改断言”和“改业务逻辑”混成无法审查的一批。

## 4. R2：测试基建与数据夹具（P0-P1）

### R2.1 节点操作矩阵适配两级 Dock

- 脚本按 `ActiveNodeTypeId` 清单枚举节点；先点击对应 `.palette-category-item`（`aria-label="展开…节点"`），确认 `aria-expanded=true`，再定位 `aria-label="添加…节点"` 并创建。
- 每个节点输出明确的 PASS/FAIL/BLOCKED/N/A、失败步骤、节点类型和证据路径；不能把“创建成功”当成运行成功。
- 浏览器矩阵是浏览器证据。桌面 Electron 另做受控抽查，至少覆盖文本、媒体资产、远程节点空配置状态和一个复杂节点；不得混称为同一证据。
- 固化实际 `ActiveNodeTypeId` 数量与类型清单。当前报告提到 25 类，修复批次应以该 commit 的 registry 自动导出清单为准。

### R2.2 重复连线输入

- 无需用户提供旧项目。用**合成的当前 schema 夹具**构造 3 条相同端口重复关系和 1 条来自另一来源的关系。
- 首先确认产品契约是否规定去重；若规定，则验证来源数、实际请求引用数以及原始边数；若没有该契约，先将测试目标记为待定，不把它当作 P0 发布失败。
- 结果注明“合成异常图数据”，不描述为真实历史项目迁移或兼容。

### R2.3 资产导入与桌面闭环

- 推荐先保留真实后端 `importMedia`、SQLite 和磁盘读写自动化，再用受控桌面手工执行“选文件→预览→保存→重开”。
- 如需自动化系统原生文件对话框，优先在**仅测试进程**模拟主进程的 `dialog.showOpenDialog` 返回值；不得为此向正式 renderer/preload 暴露任意路径注入 IPC。
- 自动化证据与手工桌面证据分别标注。验证至少覆盖图片、视频、音频、可抽取文档、坏文件反馈和保存重开；覆盖不足的类型列为 NOT_RUN。

### R2.4 证据关联

每份修复报告必须包含：基线 commit、修复 commit、工作区状态、操作系统/应用/Node 版本、命令和退出码、通过/失败/阻塞清单、截图/日志路径。旧 PASS 被后续改动影响时必须复测或解释影响分析，不得仅复制旧 PASS。

## 5. R3：确认后的产品缺陷修复

R1 定界后只把确认为真实回归的项目列入此批。每项先写缺陷卡：触发条件、最短复现、实际与预期、影响范围和严重度。候选项为批量删除及连线、边遮挡绘制、多选几何，以及 lint 暴露出的 DataEdgeLayer 渲染状态问题。

B5 暂不列为产品缺陷；只有更新参数断言后，DOCX/XLSX/PPTX/PDF 的正文或资产行为仍失败，才另开文档导入缺陷。

## 6. R4：远程供应商验收（凭据与预算未具备时保持 BLOCKED）

开始前建立明确预算：供应商、模型、操作、最大请求数和金额上限。测试按最小调用执行；达到上限或发生余额、审核、限流错误即停。不得重试掩盖失败。

支持的远程节点按供应商 × 模型 × 操作记录成功调用、参数生效、校验失败、运行记录、产物入库和保存重开。覆盖文本、生图、P图、视频、配音、语音克隆/音色设计。日志脱敏；项目导出扫描 API Key。

缺少凭据或预算时，逐项记 BLOCKED，并在发布结论中明确未完成的功能。BLOCKED 保留在覆盖清单和分母中，不得写成通过或失败。

## 7. R5：发布验收门槛与范围

### 必须完成的本地发布门槛

- `pnpm verify` 全绿，契约门禁与节点矩阵分别通过。
- 按当前 registry 清单完成所有可创建节点的 UI 创建、关键操作、合法/非法关联和保存重开验证；所有 P0/P1 关闭或有明确 N/A 依据。
- 完成适用的本地 E2E、真实本地媒体处理、资产导入后端与桌面闭环、导出导入媒体重映射、崩溃/磁盘故障测试副本验证。
- 完成 Windows 显示矩阵（100/125/150/200% × 1280×720/1920×1080 × 深浅主题）、100/500/1000 节点性能抽样、大媒体滚动和 2 小时稳定性测试；报告硬件、数据量、测量口径及异常。
- 完成干净数据目录的安装、当前 schema 初始化、项目保存重开和恢复验证。

### 明确排除的历史兼容门槛

- 不执行 v5 旧库升级、不要求旧项目 migration，也不将其列为发布阻塞项。相关状态在报告中标记 N/A（用户没有历史项目且已明确无需兼容）。
- 当前版本的正常 schema 初始化、当前版本运行中的保存恢复，以及用户当前项目的导入导出数据安全要求仍然适用。

### 远程功能声明

- 若发布声明包含“远程模型生成能力已验收”，R4 的真实供应商闭环必须完成。
- 若 R4 仍 BLOCKED，只能发布为远程能力未验收的本地候选，并逐项标明限制；不得据此宣称完整功能发布验收通过。

最终报告覆盖 PASS、FAIL、BLOCKED、NOT_RUN、N/A，附节点清单、E2E 清单、缺陷关闭状态和证据索引。

## 8. 顺序、停止条件与交付

| 顺序 | 批次 | 完成标志 | 停止条件 |
